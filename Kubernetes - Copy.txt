Kubernetes Introduction
----------------------------------
Kubernetes is a open source container orchestration platform used to automate the deployment , scaling , networking , and management of containerised applications.

It groups machines into a cluster and runs containers efficiently across them 
It hepls manage containers in prod environments 
it monitors application health and restarts failed containers 
it can scale application up or down based on need
it supports delcarative management using YAML files
 
Features of Kubernetes
. Automates deployment and scaling and management
. Scalability --> easily scale applications up or down based on demand 
. Self-healing (restarts failed containers) - --> Automatically restarts , replaces , reschedules failed containers
. Load balancing (distributes traffic across containers) and service discovery(automatically discovers and endpoints)
. Rolling updates and rollback -- updates app without downtime and roll back if needed 
. Storage orchestration
. Secret and configuration management and high availability and reliability.
. Efficient resource utilization and Runs on any environment (On-prem, Cloud, Hybrid)






Docker and Kubernetes are not competitors.

They solve different problems.
Docker builds and runs containers. (Builder + Runner)
Kubernetes manages thousands of containers. (Like Manager)

Problems: difficult to scale , difficult to recover from failures , manual deployments , downtime , manual monitoring
AWS solved some of these problems using : Auto Scaling Group , Launch Templates , Target Groups , Load Balancer but that was for VMs.

Then Docker came : Docker solved a major problem instead of saying Install java, nodejs and python and configure.. we simply create and image and run container and Now application runs exactly the same everywhere.

Problems with docker :
Single Host Failure :  One Docker Host --> if host creashed ---> All containers stopped. Docker cannot automatically recreate containers on another machine. 
Auto Scaling : Docker will not automatically create containers if traffic increases u should manually run so Not practical in production.
Load Balancing : Suppose if u have 3 container.. How will requests be distributed ...Docker itself doesn't provide production-grade load balancing between multiple application containers.
Self Healing : Suppose Container crashes. Docker stops it. Now what? Docker doesn't continuously monitor application health and replace failed containers across a cluster. Someone has to restart it (or configure simple restart policies on the same host). Production requires much more.
Multi Host Management :  Suppose company has multiple hosts 
Each host has 50 containers. Total 250 containers. Who will manage them? How do we know which host has free CPU? which host has free memory? where should a new container run? Docker doesn't provide cluster-wide scheduling.
Rolling Updates : if Application currently running with v1 if i want v2 version to deploy Without orchestration You manually Stop Run Check Repeat Risk of downtime.
High Availability : If one machine dies Application should still work. Docker alone cannot provide this across multiple machines.
Configuration Management  :  Where should Database URL, Username ,Password ,API Keys be stored? Hardcoding is not good. Need centralized configuration.
Service Discovery : Suppose Cart needs Catalogue. If Catalogue IP changes What happens? Applications shouldn't depend on IP addresses. Need service discovery.
Desired State : Production says Always run 5 containers. One crashes. Docker won't ensure the desired number of running containers across the environment. Someone has to intervene.

. Hard to manage multiple containers manually was very difficult and error prone 
. No auto scaling and high risk of downtime and failures
. No self-healing if container fails
. No load balancing

· Difficult to manage networking and storage


So what do we need?  ---> Orchestration


orchestration:
Orchestration means automatically coordinating and managing the lifecycle of workloads according to a desired state.

Container orchestration: 
Container orchestration means automatically managing the deployment, scheduling, scaling, networking, health, recovery and lifecycle of containers across multiple machines in a cluster.

Orchestration means Kubernetes automatically managing tasks such as deploying Pods, scheduling them on worker nodes, maintaining the required number of replicas, restarting or replacing failed Pods, scaling applications, providing service discovery and load balancing, and performing rolling updates and rollbacks. 

What exactly does orchestration handle?
The main responsibilities are deployment, scheduling, scaling, networking, health monitoring, self-healing, updates, rollback, and lifecycle management.


Tasks of orchestration
. Deploy: Create and deploy containers.
. Schedule: Decide where containers will run.
. Monitor: Check the health and status.
. Scale: Increase or decrease the number of containers.
. Heal: Restart, replace, and recover containers.
. Network: Connect containers and expose services.
. Update: Roll out updates and roll back if needed.





In our project, we used Kubernetes as the container orchestration platform to manage our microservices running across multiple worker nodes. Docker was mainly used for building and packaging the application images, which we pushed to the container registry, while Kubernetes handled the deployment and containers through Pods. We used Deployments and ReplicaSets to maintain the desired number of replicas and provide self-healing, Services for service discovery and load balancing, ConfigMaps and Secrets for externalized configuration and sensitive data, and resource requests and limits to control CPU and memory usage. Kubernetes also helped us with scaling, rolling updates, high availability, and automatic recovery when Pods failed, so we didn't have to manually manage individual containers across the cluster.

Why don't you use Docker alone in production?
Docker is excellent for building and running containers, 
but it is not designed to orchestrate containers across multiple servers. 
In production we need high availability, automatic scaling, self-healing, rolling updates, service discovery, load balancing, and centralized management. Kubernetes provides these orchestration capabilities while Docker is primarily used to build container images.


Docker can absolutely run containers. In fact, that's its primary job. However, Docker alone is not sufficient for managing large-scale production environments with hundreds or thousands of containers across multiple servers. That's where Kubernetes comes in.

A Pod is the smallest deployable unit in Kubernetes. 
A pod can contain one or more containers that share the same network (namespace, network ip and nodeport ), storage volumes , and configuration.
Pods are ephemeral i.e., can be created, destroyed or recreated and allow multiple container work together 

Types of pods:

Init container and side car container 


Pod States/lifecycle:
--------------------------
1)Pending   		----> 	The Pod has been accepted by Kubernetes, but one or more containers have not yet started
This can include:

Waiting for scheduling
Waiting for resources
Pulling the image
Waiting for volumes

2)Running			----> The Pod has been bound to a node, and all containers have been created; at least one container is still running or starting/restarting.
Because Pod phase Running does not necessarily mean the application is healthy. A container can be running while its readiness probe is failing.

3)Succeeded     ----> All containers in the Pod have terminated successfully and will not be restarted. 
This is common with Jobs/batch workloads rather than continuously running microservices.
4)Failed 				----> All containers in the Pod have terminated, and at least one container terminated unsuccessfully.
5)Unknown 		----> The Kubernetes control plane cannot obtain the current state of the Pod, usually because it cannot communicate with the node/Kubelet.



Scheduled    	---> It means the Scheduler has selected a node for the Pod.
Pulling 			---> images are being pulled by kubelet

Why multiple container in pod :
 
Multi-container patterns :
---------------------------------
1)Side-car pattern:

A Pod is the smallest deployable unit in Kubernetes, and it can contain one or more containers. In most real-time projects, we usually have one container per Pod, but Kubernetes supports multiple containers in the same Pod when they need to work together closely. All containers inside a Pod share the same ===> IP address, network namespace, and storage volumes <===, so they can communicate with each other using localhost and access the same shared files. 
A common real-time example is the Sidecar pattern. Suppose the main container is running the Catalogue application and continuously serving user requests. We don't want the main application container to spend CPU and memory pushing log files to ELK because that affects application performance. Instead, we add a second container called a Sidecar container(Fluent Bit sidecar container) in the same Pod. The main container simply writes logs to the shared volume, and the Sidecar container reads those logs from the shared storage and pushes them to ELK. This keeps the main application focused only on serving requests while the Sidecar handles log collection. Since both containers are in the same Pod, they can easily share the same network and storage. 


Manifest files:
Main Container → Catalogue Application
Sidecar Container → Fluent Bit (push logs to ELK)

apiVersion: v1
kind: Pod
metadata:
  name: catalogue-pod

spec:
  volumes:
    - name: log-volume
      emptyDir: {}

  containers:
  - name: catalogue
    image: catalogue:v1
    volumeMounts:
      - name: log-volume
        mountPath: /app/logs

  - name: fluent-bit
    image: fluent/fluent-bit:latest
    volumeMounts:
      - name: log-volume
        mountPath: /app/logs

How it works :  Catalogue Container ---> write logs to /app/logs/app.log ---> in shared volume ---> Fluent Bit pushes logs to ---> ELK 

2)Proxy pattern: 

Suppose our main container is running the Catalogue application, and we want every incoming request to be validated before it reaches the application. Instead of implementing authentication, authorization, rate limiting, SSL termination, or request filtering inside the application, we deploy a Proxy container in the same Pod it sits bw the user and main application container. All client requests first reach the Proxy container, which inspects and validates them. If the request is valid, it forwards it to the main application container using localhost(multiple containers in same pod communicate using localhost); otherwise, it rejects the request. Since both containers share the same network namespace and IP address, communication between them is very fast. This approach keeps the application code simple while the Proxy container handles security and traffic management. 
In production environments, technologies such as Envoy or NGINX are commonly used as Proxy containers in a Pod.

A Proxy container sits in front of the application and handles traffic before forwarding it to the main container.Incoming requests first reached the Envoy proxy, which performed authentication, SSL termination, and rate limiting before forwarding valid requests to the application container using localhost.

Every request must
Authenticate JWT token
Apply Rate Limiting
Terminate SSL
Add Security Headers

Instead of coding all this inside the application, we deploy an Envoy or NGINX proxy.
If the request is valid ---> Forward to Catalogue ---> If invalid ---> Reject immediately.

3)Init Container (Real-Time Example)

Init container runs only once before the main application container starts. Suppose our Catalogue application requires a database connection, configuration files, or some initialization scripts before it can start successfully. Instead of adding all these checks inside the application code, we use an Init container. The Init container first verifies that the database is reachable, downloads required configuration files, creates necessary directories, or performs initialization tasks. Only after the Init container completes successfully does Kubernetes start the main application container. If the Init container fails, the main container never starts. This ensures the application always starts in a ready and consistent state. In production, Init containers are commonly used for database readiness checks, configuration setup, schema migrations, and downloading required files before the application starts.

An Init container performs initialization tasks before the application starts.

Real-Time Example – Database Readiness
Suppose Catalogue depends on MongoDB.If MongoDB is not ready,the application fails during startup. Instead of retrying forever, we use an Init container.

We used Init containers to perform dependency checks before starting the application. For example, the Init container waited until MongoDB was reachable. Once the database became available, Kubernetes automatically started the main application container.

What are Labels?
Labels are key-value pairs attached to Kubernetes objects for identification, organization, and selection. They are used by Kubernetes resources like Services and Deployments to locate matching Pods.

What are Annotations?
Annotations are key-value pairs used to store descriptive metadata such as build numbers, Git commits, deployment timestamps, or owner information. They are intended for tools and humans, not for selecting resources.

Give one production use case for Labels.
"In our project, we labeled Pods with values such as app=catalogue, env=prod, and version=v1. Kubernetes Services used these labels to route traffic to the correct Pods, and we also used them to filter resources during troubleshooting."

Give one production use case for Annotations.
We stored deployment metadata such as Jenkins build number, Git commit ID, deployment timestamp, and deployment owner in annotations. This made it easy to trace which build was running in production.


If labels are changed, what happens?"
If a Pod's labels no longer match a Service's selector, the Service immediately stops routing traffic to that Pod. Similarly, if a Deployment's selector doesn't match its Pods, it may create new Pods because it believes the desired ones don't exist. That's why labels must be planned carefully and not changed arbitrarily in production.

Resource requests and limits : 
---------------------------------------
Resource Requests and Limits define how much CPU and Memory a container requires and the maximum amount it is allowed to use.
Resource requests and limits are configured on containers, not directly on Pods.

There are two terms:
Requests
Limits


Why do we need Resource Limits?
Suppose one Kubernetes Worker Node has:  8 CPU and 16 GB RAM
Now you deploy three applications ---> catalogue, cart and user 
Suppose the Cart application suddenly consumes: 90% CPU and 15 GB RAM so other application and node performance will go down 

To prevent one container from consuming all resources, Kubernetes allows us to define Requests and Limits.

Request : Request is the minimum amount of CPU and Memory that Kubernetes guarantees to a container.
Example
resources:
  requests:
    cpu: "500m"               # 0.5 CPU 
    memory: "512Mi"   #512 mb 
	
Scheduler says: I will place this Pod only on a node that has at least 0.5 CPU and 512Mi memory available.


Limit:   Limit is the maximum amount of CPU and Memory a container is allowed to consume.
Example
resources:
  limits:
    cpu: "1"
    memory: "1Gi"        #1 CPU and 1 GB RAM


Example:
spec:
 container:
 - name: resourcerequestandlimitcontainer
   image: nginx
   ports:
   - containerPort: 80
   resources:
    requests:
      cpu: "100m"
      memory: "68Mi"
    limits:
      cpu: "200m"
      memory: "100Mi"
	  
	  
What happens during Scheduling?
Suppose

Worker-1 : Available
CPU = 200m
Memory = 400Mi

But in manifest file u mention 
Request
CPU = 500m
Memory = 512Mi

Scheduler says ❌ Cannot schedule. Need another node.

What happens if Limit is crossed?

CPU 

Suppose
Limit ---> 1 CPU
Application tries ---> 2 CPU

Kubernetes ---> Throttles CPU.Application becomes slower. Pod is not killed.

Memory

Suppose
Limit --- > 1Gi
Application uses  ----> 2Gi

Kernel ---> OOM Killer ---> Container terminated. Pod restarts.

Interviewer
CPU ---> Throttle
Memory ---> OOMKilled


How to Check container resources :    kubectl describe pod catalogue

Requests and Limits are configured on individual containers. Since a Pod can contain multiple containers, each container can have different resource requirements.
Request is the minimum guaranteed resource used by the Kubernetes Scheduler to place the Pod on a node. Limit is the maximum resource the container can consume during execution.
What happens if CPU Limit is exceeded ----> Kubernetes throttles the CPU.
What happens if Memory Limit is exceeded ----> The container is terminated by the Linux OOM Killer and Kubernetes restarts it (if managed by a Deployment/ReplicaSet).
If a Pod has two containers, where do you configure resources  ---> for each container we will specify 

In our Kubernetes deployments, we configured CPU and memory requests and limits for each container. Requests ensured that the Kubernetes Scheduler placed Pods only on nodes with sufficient resources, while limits prevented a container from consuming excessive CPU or memory. If CPU usage exceeded the limit, the container was throttled, whereas exceeding the memory limit resulted in an OOMKilled event and Kubernetes recreated the container. Configuring appropriate requests and limits helped us achieve stable resource utilization and prevented one application from impacting others on the same worker node.

Why do we need Services?
Pods are ephemeral, so their IP addresses change when they are recreated. Services provide a stable endpoint, service discovery, and load balancing, allowing applications to communicate reliably without depending on Pod IPs.

How does a Service identify Pods?
Using Labels and Selectors. The Service selector matches Pod labels and automatically routes traffic to the matching Pods.

Does a Service create Pods?
No. Deployments create Pods. Services only expose and load balance them.

In our Kubernetes deployments, every microservice was exposed through a Kubernetes Service instead of accessing Pods directly. Since Pods are ephemeral and their IP addresses change after restarts or rollouts, Services provided a stable Cluster IP and DNS name for communication between microservices. Services used label selectors to identify the appropriate Pods and automatically distributed traffic across healthy replicas, ensuring reliable service discovery and load balancing within the cluster.

ReplicaSet:
--------------
A ReplicaSet is a Kubernetes controller that ensures the desired number of   Pods are running at all times.

For example:  
replicas: 3   =====> means Kubernetes should maintain 3 Pods. ReplicaSet continuously maintains the desired number.
If one Pod dies: ReplicaSet notices that only 2 Pods are running and creates a replacement pod automatically So the desired count becomes 3 again.

ReplicaSet's Main Responsibilities
Maintain replica count/desired count 
Replace failed Pods --> if pod fails recreate replacement pod 
Select Pods using labels

Example:

apiVersion: apps/v1
kind: ReplicaSet

metadata:
  name: catalogue-rs

spec:
  replicas: 3

  selector:
    matchLabels:
      app: catalogue           #this labels should match the pod labels then only replica set can manage/control pods  
											#It tells the ReplicaSet controller: "Go look across the cluster and manage any Pod that has the tag app: catalogue.

  template:										#pod start point
    metadata:
      labels:
        app: catalogue         #pod labels 
    spec:
      containers:
      - name: catalogue
        image: catalogue:v1
		ports:
        - containerPort: 8080
		

If the labels do not match perfectly, the ReplicaSet will not be able to track or manage those pods		
		
		
Commands:

kubectl get replicasets   or kubectl get rs    ---> get list if replicasets
kubectl describe rs catalogue-rs                   ---> describe replica means all info about that 



ReplicaSet vs Deployment
| ReplicaSet                               | Deployment                      |
| ---------------------------------------- | ------------------------------- |
| Maintains desired number of Pods         | Manages application releases/lifecycle    |
| Creates/replaces Pods                    | Creates and manages ReplicaSets |
| Supports scaling                         | Supports scaling                |
| Self-healing of replica count            | Rolling updates                 |
| No proper application rollout management | Rolling updates & rollbacks     |
| Usually managed by Deployment	             | Common production resource      |

		
		
Then Why Do We Need Deployment?
Flow --->  Deployment ---> ReplicaSet ---> pods		
Deployment manages the ReplicaSet. ReplicaSet manages the Pods.

Example: Updating the Application

What is a ReplicaSet and why do we use it?

A ReplicaSet is a Kubernetes controller responsible for maintaining the desired number of identical Pods. For example, if we configure three replicas and one Pod fails, the ReplicaSet detects that the actual number has dropped to two and creates a replacement Pod. It uses label selectors to identify the Pods it manages. In our production deployments, we generally don't create ReplicaSets directly; we use Deployments, which create and manage ReplicaSets and provide additional capabilities such as rolling updates and rollbacks.

Deployment = manages releases
ReplicaSet = maintains replica count
Pod = runs the container

Deployment:
-----------------
A Deployment is a Kubernetes resource that manages the desired state and lifecycle of application Pods through ReplicaSets. It provides declarative updates, scaling, rolling updates, rollbacks, and self-healing.


The most important relationship is:   Deployment ---> replicaset ---> Pod ---> containers 


Why do we need Deployment?
Suppose your Catalogue application is running ----->  catalogue:v1 ------> with 3 replicas: i.e., 3 pods 
Now u want to release ---> catalogue: v2  ---> You don't want to manually delete the old Pods and create new ones.

Deployment

   └── New ReplicaSet → v2

It gradually replaces v1 Pods with v2 Pods. That's a Rolling Update.

step : 1 ---->  Create new replicaset and old replica set is there and pods are running 
when u apply updated manifest file by default if performs ---> rolling update feature 

step: 2 
Rolling update :  we mentioned replica : 3 in manifest file 
It gradually shifts traffic/workload from old Pods to new Pods according to the rollout strategy.
set 1
in new replicaset it create the new pod 1 with updated image i.e., new version catalogue:v2 
in old replicaset it down and removes the pod 1 which is running with catalogue:v1

in new replicaset it create the new pod 2 with updated image i.e., new version catalogue:v2
in old replicaset it down and removes the pod 2 which is running with catalogue:v1

Self-Healing :  Desired = 3 if pod 2 dies it detects  ---> The ReplicaSet managed by the Deployment notices that only 2 Pods exist. So the Deployment indirectly provides self-healing through its ReplicaSet.
Scaling : 
Suppose traffic increases. 
You currently have: replicas: 3

You can scale to 5:   kubectl scale deployment catalogue --replicas=5

You can also change: replicas: 5 and apply the manifest.

Rollback
Suppose v2 has a bug. You can check rollout history:

kubectl rollout history deployment catalogue
Then rollback: kubectl rollout undo deployment catalogue

Kubernetes can return the application to the previous revision.This is one of the major reasons we use Deployment rather than directly creating ReplicaSets.

Check Rollout status :  kubectl rollout status deployment catalogue

Real Production Flow :   Dockerfile ---> Docker Image ---> ECR ---> Deployment YAML ---> Kubernetes Deployment ---> ReplicaSet ---> Pods ---> Containers

What is a Kubernetes Deployment?
A Deployment is a Kubernetes resource used to manage the lifecycle and desired state of application Pods. It manages ReplicaSets, which in turn maintain the required number of Pods.

In our projects, we used Deployments for microservices because they provided replica management, self-healing through ReplicaSets, rolling updates, scaling, and rollback capabilities. 
For example, when we released a new version of the Catalogue service, we updated the image version in the Deployment and Kubernetes created a new ReplicaSet and gradually replaced the old Pods with the new version.
