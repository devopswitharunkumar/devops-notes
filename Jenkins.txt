Jenkins Pipeline Types : 
------------------------------
Jenkins supports two types of pipelines:
1 Declarative Pipeline 
2 Scripted Pipeline

Declarative Pipeline
--------------------------
Declarative Pipeline is a structured pipeline syntax to make CI/CD pipelines easier to write, maintain, read. 
It follows a predefined syntax with sections like pipeline, agent, stages, stage, steps, post, and environment blocks etc.
Ex:
pipeline {
    agent any
    stages {
        stage('Build') {
            steps {
                sh 'mvn clean package'
            }
        }
        stage('Test') {
            steps {
                sh 'mvn test'
            }
        }
    }
    post {
        success {
            echo "Deployment Successful"
        }
    }
}

Advantages
Easy to read and understand, Standard structure across teams, Built-in features like:  post , environment , parameters , options , when , agent , Better validation before execution. , Easier for team collaboration and maintenance.

Real-Time Usage

In my current project, we primarily use Declarative Pipelines. Our CI pipelines are defined declaratively with stages such as Checkout, Build, Unit Testing, SonarQube Analysis, Artifact Publishing to Nexus, and Deployment Trigger. Declarative syntax makes the pipelines more readable and easier for the team to maintain.


Scripted Pipeline
----------------------
Scripted Pipeline is based on entirely on Groovy. It provides complete programming flexibility and is suitable for implementing complex pipeline logic, dynamic workflows, loops, conditional execution, and reusable functions.

node {

    stage('Build') {
        sh 'mvn clean package'
    }

    if (env.BRANCH_NAME == 'main') {

        stage('Deploy') {
            sh './deploy.sh'
        }
    }
}

Advantages
Full Groovy programming capabilities.
Supports: Loops , Conditions , Exception handling , Dynamic stage generation , Complex workflows , More flexible than Declarative Pipeline.

Limitations
More difficult to read and maintain.
Requires good Groovy knowledge.
Easier to introduce coding mistakes.
Less standardized across teams


Real-Time Scenario :  Suppose your application has 20 microservices. 
-------------------------------------------------------------------------------------------
Instead of writing 20 deployment stages manually:
stage('Catalogue')
stage('User')
stage('Cart')
...

A Scripted Pipeline can dynamically generate stages in a loop:

def services = ['catalogue','user','cart']

services.each { service ->
    stage(service) {
        build job: service
    }
}
This is one situation where Scripted Pipeline is useful.

Agent vs Node
Node: Any machine (controller or agent) that Jenkins knows about and can schedule work on.
Agent: The execution process running on a node that performs the build.

In everyday Jenkins conversations, people often use Node and Agent interchangeably, but technically a node is the machine/resource, while the agent is the process connected to the controller that executes the job.

Post block:  optional to define in pipeline syntax
--------------
The post block defines actions that should be executed after the pipeline or a stage completes, regardless of whether the build succeeds, fails, or becomes unstable. 
It is commonly used for notifications, cleaning the workspace, archiving artifacts, publishing reports, and triggering follow-up actions.

Why do we need post?
Suppose your pipeline is: --> checkout git --> clone code --> build --> test --> docker build ---> Deploy
lets say Docker build is failed --->  How will you notify the team? or How will you clean the workspace?  or  How will you archive logs? That's why we use post.

If Docker build fails so failure condition will trigger and sent notification to required team 

Ex:
post {
    success {
        echo "Deployment Successful"
    }
}

Conditions
always	 ---> It will run regardless of  Pipeline Success? or Pipeline Failed? or Pipeline Aborted? --> run every case 
success    ---> It will run if the current Pipeline’s or stage’s is "success" status, typically denoted by blue or green in the web UI.
failure      ---> It will run if the current Pipeline’s or stage’s is "failed" status, typically denoted by red in the web UI. or Runs only when the pipeline fails.
unstable  ---> Runs when the build is unstable. like build is succeeded but some test cases failed 
aborted   --->  Suppose someone clicks stop build that is the case of aborted 
changed  ---> Runs if build result changed. is some code or something changes status of pipeline it will run
fixed        ---> Only run if the current Pipeline’s run is successful and the previous run failed or was unstable.
cleanup  ---> Run the steps in this post condition after every other post condition has been evaluated, regardless of the Pipeline or stage’s status.

Email Example
post {
	success {
			mail(
					to: "team@company.com",
					subject: "Build Successful",
					body: "Deployment Completed"
			)
	}
}
Slack Example
post {
	failure {
		slackSend(
		message: "Deployment Failed"
		)
	}
}
Publish JUnit Report
post {
	always {
	junit '**/target/surefire-reports/*.xml'
	}
}

Options Block
-------------------
The options block is used to configure the behavior of a Jenkins Pipeline. It controls execution settings such as timeouts, concurrent builds, log retention, timestamps, and retry behavior.

Why Options?

Suppose Pipeline Runs Forever. Need Timeout. 
Suppose Developer Clicks Build 10 Times. Need Disable Concurrent Builds. 
Suppose 1000 Builds. Need Delete Old Builds. That's Options.

Ex:
1. lets say application runs 2-3 hrs some times because or erros ot should not be like that for that we mention time line
options{
	timeout(time:30, unit:'MINUTES')
}
it will run till 30 mins time and after that pipeline will fail because of timeout 

Examples :
-------------
The main purpose of timeout is not only to stop errors, but also to prevent the pipeline from hanging indefinitely when a stage gets stuck and never completes.
Example 1: Waiting for User Input (Most Common)
input "Approve Production Deployment"      --> if approver forgot toapprove The pipeline will remain in Running state forever. To avoid this: If no approval is given within 30 minutes, Jenkins automatically aborts the pipeline.

Example 3: SSH Connection Hangs
sh "ssh app-server"
The server is unreachable due to a network issue. Instead of immediately failing, the SSH command keeps waiting for a response. The pipeline stays in the Running state without moving to the next stage.The timeout stops the pipeline after the specified duration.

Example 4: SonarQube Scan Hangs
sh "sonar-scanner"
If the SonarQube server is overloaded or not responding, the scanner may wait indefinitely.

Interview Answer (4+ Years)

"We use the timeout option to prevent the pipeline from running indefinitely. Sometimes a stage such as Terraform Apply, SonarQube Scan, waiting for manual approval, or a network connection may hang instead of failing. In such cases, the pipeline remains in the Running state and blocks Jenkins resources. By configuring a timeout, Jenkins automatically aborts the pipeline if it exceeds the specified duration, improving resource utilization and preventing stuck builds."

when:
-------
The when directive is used to execute a stage conditionally. 
Jenkins evaluates the specified condition before entering the stage. If the condition evaluates to true, the stage executes; otherwise, Jenkins skips the stage. 
This helps build dynamic and reusable pipelines.
Ex:
pipeline {
	agent any
		parameters {
				choice (name: 'action', choices: ['Apply', 'Destroy'])
			}
		stage('Apply Stage') {
			when {
				expression {
					params.action == 'Apply'
				}
			}
			input {
				message "Do You Want to Continue ?"
				ok "proceed"
			}
			steps {
			sh """
				cd "${Module_No}"
				terraform apply -auto-approve
			"""
			}
		}	
		stage('Destroy Stage') {
			when {
				expression {
					params.action == 'Destroy'
				}
			}
			input {
				message "Do You Want to Continue ?"
				ok "proceed"
			}
			steps {
			sh """
				cd "${Module_No}"
				terraform destroy -auto-approve
			"""
			}
		}
	}

"In our Jenkins Declarative Pipelines, we used the when directive to control stage execution based on conditions such as Git branches, deployment environments, and pipeline parameters. For example, Docker image creation was performed for all branches, but deployment to production was executed only when the build originated from the main branch and the selected environment was PROD. This prevented accidental deployments and allowed us to maintain a single reusable pipeline for multiple environments."

Nexus: 
--------
Nexus is a centralized artifact repository used to store, manage, version, and distribute build artifacts such as JARs, WARs, Docker images, npm packages, Maven dependencies, Helm charts, and other binaries. 
It acts as a single source of truth for all software artifacts in the CI/CD pipeline
nexus built on java we need java on nexus

Why do we need Nexus?
Suppose your Java application is built.
Developer ---> Git Push ---> Jenkins Build ---> payment.jar -----> Now deployment needs payment.jar

Where is it stored?
Without Nexus === Jenkins Workspace ----> Deleted after cleanup ----> Artifact Lost Not good.

Instead
Developer ---> Git ---> Jenkins ---> Build ---> payment.jar ---> Nexus Repository ---> Deployment Server Downloads ---> Deploy

Nexus becomes the central storage for build artifacts.

What is an Artifact --->  An artifact is the output of a build process.

Examples:
Java --->  payment.jar , shipping.jar ,  user.war
Docker ----> payment:v1.0
Python ---> .whl
NodeJS --> .tgz
Helm  ---> payment-1.0.0.tgz


Why not store JAR in Git?
Because Git is for Source Code Not Binary Files ---> Binary files , Large , Cannot diff easily , Increase repository size, Slow cloning so we store them in Nexus 

Types of Repositories
Nexus supports multiple repository formats. ----> Maven , Docker , npm , NuGet , PyPI , Helm , Raw

Maven Repository      ----> jar, war, pom, zip Ex : payment-1.0.jar
Docker Repository     ----> stores Docker Images Example : payment:v1.0
npm Repository         ----> Stores NodeJS Packages
Helm Repository        ----> stores Helm Charts
Raw Repository          ---->  atores anything like   ---> zip, war , pdf , tar.gz , scripts , configs etc......


Repository Types
1. Hosted Repository   : Stores artifacts created inside your organization.  Ex: payment.jar ---> uploaded ----> organization
2. Proxy Repository      : Suppose Maven needs spring-boot.jar Normally  Maven Central ---> internet ---> Download  and Every developer downloads again. but we can cache that and upload to nexus so 2nd devloper gets that from nexus not from internet
3. Group Repository     : Combines Hosted and Proxy into one URL. Instead of configuring use that URL

Where did you use Nexus?

Interview Answer

"We used Nexus as the centralized artifact repository in our CI/CD pipeline. After Maven successfully built the application, Jenkins uploaded the generated JAR files to Nexus. During deployments, instead of using artifacts from the Jenkins workspace, deployment jobs downloaded the required version from Nexus. This ensured version consistency, simplified rollbacks, reduced dependency on Jenkins workspaces, and provided a single source of truth for build artifacts."


Why do we need Nexus?

To centrally store versioned build artifacts, enable artifact reuse, simplify rollbacks, reduce build dependencies, and improve CI/CD reliability.

Why not deploy directly from Jenkins?

Jenkins workspaces are temporary and can be cleaned or removed. By storing artifacts in Nexus, deployments always use a versioned, immutable artifact from a centralized repository, ensuring consistency across environments.

4+ Years Interview Answer

"In our CI/CD pipeline, Jenkins built the application using Maven and uploaded the generated artifacts to Nexus Repository Manager. Nexus served as the centralized repository for versioned artifacts. Deployment pipelines downloaded the required artifact version from Nexus rather than relying on Jenkins workspaces. We also configured Nexus proxy repositories to cache external Maven dependencies, reducing internet dependency and improving build performance. This approach provided traceability, simplified rollbacks, and ensured that the same tested artifact was promoted across DEV, SIT, UAT, and PROD environments."

SonarQube:
--------------
SonarQube is a Static Code Analysis tool.
It analyzes your source code without executing it and identifies:

Bugs
Vulnerabilities
Security Hotspots
Code Smells
Duplicate Code
Test Coverage (when integrated with coverage tools)

Its goal is to improve code quality and code security before deployment.

Why do we use SonarQube?
Imagine a Java developer writes:
String password = "admin123";

The application compiles successfully. The build also succeeds.
But SonarQube reports: Hardcoded password detected. So instead of discovering this in production, SonarQube catches it during CI.

Where does SonarQube fit?

Developer--->GitHub--->Jenkins--->Git Checkout--->Maven Compile ---> Unit Test ---> SonarQube Analysis ---> Quality Gate ---> Build Docker Image ---> Push to Nexus ---> Terraform  ---> Deploy

Notice that SonarQube runs before building the Docker image or deploying. If code quality is poor, the pipeline stops early.

-------------------------------------
Suppose you're working on the Catalogue Service. Developer pushes code. GitHub triggers Jenkins.

Jenkins stages:

Checkout ---> Compile ---> Test ---> SonarQube ---> Quality Gate ---> uild Docker Image ---> Push to Nexus ---> Deploy

If SonarQube detects serious issues: Security Vulnerability or Critical Bug : the pipeline fails. Nothing is deployed.

How Jenkins talks to SonarQube
Jenkins ----sonar scanner--->SonarQube Server ---> Analyzes Source Code ---> Stores Results ---> Returns Quality Gate
Jenkins only sends the code. SonarQube performs the analysis.

2. SonarQube Server : Analyzes the code. Usually runs on EC2.

Example : http://54.xx.xx.xx:9000

4. Quality Gate

If passed Pipeline continues. Otherwise Pipeline fails and pipeline stops

How Jenkins uses Quality Gate
Your Jenkins pipeline typically has two stages.

Stage 1: Analysis
stage('SonarQube Analysis') {
    steps {
        withSonarQubeEnv('SonarQube') {
            sh 'sonar-scanner'
        }
    }
}
Here, sonar-scanner uploads the project to the SonarQube server.

stage('Quality Gate') {
    steps {
        timeout(time: 5, unit: 'MINUTES') {
            waitForQualityGate abortPipeline: true
        }
    }
}

This stage waits until SonarQube finishes analyzing the project.

Developer pushes code. ---> Jenkins executes ----> sonar-scanner ----> SonarQube starts analysis. ----> SonarQube compares results with the Quality Gate rules. ----> SonarQube sends the result back to Jenkins. Example: Status = OK or Status = ERROR ---> Jenkins receives the response. If: Status = OK Pipeline continues. If: Status = ERROR ------> Pipeline fails immediately.

What is the difference between sonar.qualitygate.wait=true and waitForQualityGate()?

"sonar.qualitygate.wait=true is a Sonar Scanner property that makes the scanner wait until the SonarQube server finishes analysis and returns the Quality Gate result. 
In contrast, waitForQualityGate() is a Jenkins Pipeline step provided by the SonarQube Jenkins plugin. It lets the scanner finish quickly, and then Jenkins waits for the Quality Gate result, 
typically using a webhook from SonarQube. In Jenkins-based CI/CD pipelines, waitForQualityGate() is the preferred approach because it's better integrated with the pipeline and avoids keeping the scanner process blocked unnecessarily."

Change Management Process :
----------------------------------------
"In every real company, especially banking, healthcare, insurance, telecom, and fintech projects, we cannot deploy directly to Production. Every Production deployment must go through a Change Management process to ensure the deployment is safe, approved, auditable, and can be rolled back if any issue occurs."

Overall Flow
Business Requirement --->Development ---> DEV Testing ---> SIT Testing ---> UAT Testing ---> Raise Change Request (CR) ---> Approvals ---> Production Deployment ---> Post Deployment Validation ---> Close Change Request

Step 1: Development Phase .... Suppose the business wants a new feature.

Example: Add a new payment validation in the Catalogue application.

Developer will
Create feature branch
Develop the feature
Commit code
Raise Pull Request
Merge after review

Then the Jenkins pipeline starts.
Pipeline stages:
Git Checkout ----> Build ----> Unit Testing ----> SonarQube ----> Security Scan ----> Package ----> Deploy to DEV

Step 2: Testing in Multiple Environments
We never deploy directly to Production. The application moves through multiple environments.
Developer ---> DEV ---> SIT ---> UAT ---> Production

Each environment has its own purpose.

CIT1/DEV   : Developers verify -----> Build succes , Unit tests , Smoke testing basically
SIT               : QA Team performs Functional Testing , Regression Testing , Integration Testing
UAT             : Business users verify, Business functionality,User Acceptance Testing and  

Only after business approval can we move to Production.


Step 3: Why Change Management?

Production is very sensitive : If we deploy directly, Banking transactions may fail. Customers may not access the application. Business loses money. Therefore every company follows a Change Management process.

Step 4: Raise Change Request (CR)
After UAT is successful, DevOps Engineers raise a Change Request (CR).
This is created in ---> Jira Service Management , ServiceNow , BMC Remedy
Every company has its own tool. 

Example
CR Number CHG00012345

Step 5: What Information Goes into the CR?
A Change Request contains: 
Project Code (Ex: RoboShop), 
Application Name (Example : Catalogue) , 
Jira Story ID (Example JIRA-4567) and This links the deployment to the development work.
Version (Example : 2.3.1)
Deployment Date
Deployment Time
Environment : Production
Jenkins Build URL ---> Attach Build #120 i.e., attach build results 
Test Results
Attach
Unit Test Report
SonarQube Report
Security Scan Report
QA Report

Deployment Plan : Stop Application ---> Backup ---> Deploy ---> Restart ---> Verify
Rollback Plan : If deployment fails : Deploy Previous Build or Helm Rollback or Terraform Rollback

Validation Plan :
Example : Login ---> API Testing ---> Database Check ---> Smoke Testing ---> Business Validation

Step 6: CR Status
Initially : NEW ---> Pending Approval ---> Approved ---> Scheduled ---> Implemented ---> Finally ---> Closed

Step 7: Approval Process
The Change Request goes through multiple approvals.

DevOps Engineer ---> Team Lead ---> Delivery Manager ---> Client / Product Owner ---> CAB Approval

1)Team Lead verifies
Jira Story
Build
Version
Test Reports
Deployment Plan

2)Delivery Manager verifies
Business impact
Deployment window
Risk

3)Client Approval : Some companies also require client approval before Production deployment.

4)CAB = Change Advisory Board

Members include
Project Manager
Delivery Manager
Infrastructure Team
Security Team
Database Team
Business Owner

Only after CAB approval is the Production deployment allowed.

Step 8: Jira and Jenkins Integration

The CR is integrated with Jenkins.
Jira ---> Change Request ---> Approval ---> Trigger Production Pipeline ---> Jenkins Pipeline

The Production pipeline will start only after:
CR is approved . Scheduled deployment time has arrived Otherwise Jenkins will not deploy.

Step 9: Production Deployment
DevOps Engineer starts deployment.

Pipeline
Checkout ---> Download Artifact ---> Deploy ---> Restart Services ---> Health Check
or
Helm Upgrade ---> Rolling Update ---> Smoke Test
or
Terraform Apply ---> Infrastructure Update ---> Verification

Step 10: Post Deployment Testing

After deployment

Application team performs

Smoke Testing
Sanity Testing
API Testing
Login Testing
Database Validation
Business Validation

Only after successful validation is the deployment declared successful.

Step 11: Rollback
Suppose deployment fails. Then DevOps follows the rollback plan.

Example
Deploy Previous Artifact
or
helm rollback
or
kubectl rollout undo and Rollback should already be documented in the Change Request before deployment starts.

Step 12: Close the Change Request
After successful deployment,

Update

Actual Start Time
Actual End Time
Deployment Status
Validation Result

Then close the CR.

Production Pipeline

Generally :    DEV Pipeline --->SIT Pipeline ---> UAT Pipeline  ---> Separate Production Pipeline through CR process

The Production pipeline usually has:

Additional approvals
Restricted access
Manual confirmation
Change Request validation
Audit logging

Only authorized DevOps engineers or Release Managers can execute it.

Real Interview Answer (4+ Years DevOps)

"In our project, after development and successful testing in DEV, SIT, and UAT, the DevOps team raised a Change Request in Jira Service Management or ServiceNow. The CR included the project code, application name, Jira story ID, application version, deployment schedule, implementation plan, rollback plan, validation plan, Jenkins build URL, and testing reports such as QA, SonarQube, and security scan results. The request then went through approvals from the Team Lead, Delivery Manager, and, where required, the client and Change Advisory Board (CAB). Once approved and during the scheduled maintenance window, the Production Jenkins pipeline was triggered. The deployment was performed using our CI/CD pipeline, followed by smoke testing, API validation, and business verification. If any issue occurred, we executed the predefined rollback plan. After successful validation, we updated the CR with deployment results and closed it. This process ensured that every production deployment was fully approved, traceable, auditable, and low risk."

Functional testing:
------------------------

Functional Testing means checking whether the application works according to the business requirements. It focuses on what the application does, not how it is implemented.
or
Functional testing is the process of verifying that every feature of an application behaves as expected according to the business requirements and functional specifications.

Example (RoboShop Catalogue Service)

Suppose your Catalogue service provides product information. that is an 
API : GET /products
During functional testing, QA verifies:

✅ API returns HTTP 200
✅ Product list is displayed
✅ Product name is correct
✅ Price is correct
✅ Required fields are present
✅ Search works correctly
✅ Filters work correctly

Another Example:  Banking Example
Suppose you work on an online banking application.

Feature: Fund Transfer

Functional testing checks:

User logs in successfully.
User enters account details.
Amount is entered.
OTP is validated.
Money is transferred.
Transaction history is updated.
Account balance is reduced.
Confirmation message is displayed.

If all these business functions work correctly, the functional test passes.

Functional Testing vs Smoke Testing

| Smoke Testing                                                      													 						| Functional Testing                                                   |
| ------------------------------------------------------------------- | -------------------------------------------------------------------- |
| Checks whether the application starts and basic functionality works				 | Checks every business feature in detail                              |
| Quick test                                                         																			 | Detailed test                                                        |
| Performed after deployment                                        												  | Performed after smoke testing                                        |
| Example: Login page opens                                          												 | Example: Login, Add Product, Delete Product, Checkout, Payment, etc. |


Functional Testing vs Sanity Testing

| Functional Testing           | Sanity Testing                        |
| ---------------------------- | ------------------------------------- |
| Tests complete functionality | Tests only the modified functionality |
| Covers all features          | Covers only the affected feature      |
| More comprehensive           | Faster and more focused               |

Interview: Explain Your Jenkins Pipeline
Answer

"In my current project, we use Jenkins Declarative Pipelines with Shared Libraries to standardize the CI/CD process across multiple microservices. 
Instead of writing the same logic in every Jenkinsfile, we created reusable functions in a Shared Library, and each application's Jenkinsfile simply passes configuration such as the component name and application name."


CI Pipeline Flow:
1. Agent Selection

agent {
    node {
        label 'Agent-1'
    }
}

"The pipeline executes on a dedicated Jenkins agent instead of the Jenkins controller. The agent is preconfigured with tools like Git, Terraform, Node.js, AWS CLI, and has the required permissions. Using agents distributes the workload and avoids overloading the Jenkins master."

2. Parameters

parameters {
	 choice(name:'environment', choices:['dev','prod'])
	 booleanParam(name:'Deploy')
}

Explain

"The pipeline accepts the deployment environment (Dev or Prod) and a Deploy flag. If Deploy is false, the pipeline performs only CI activities like build and artifact publication. If true, it triggers the CD pipeline after publishing the artifact."


3. Environment Variables

environment {
    packageVersion=''
}

Explain

"We use environment variables to store values that are required across multiple stages. In our case, the application version extracted from package.json is reused during artifact publication and deployment."

4. Get Version stage 
readJSON file:"package.json"
Explain

"We read the application version dynamically from package.json. This avoids hardcoding the version and ensures the artifact uploaded to Nexus matches the application's actual version."

5. Install Dependencies stage
npm install
Explain

"The pipeline installs the required Node.js runtime and downloads all project dependencies using npm install. This prepares the application for build and testing."

6. Unit Testing stage

echo "Unit Testing"
Explain

"In production, this stage runs automated unit tests. In our lab setup, it contains a placeholder, but in enterprise projects this stage executes the application's unit test suite before proceeding."

7. SonarQube Scan stage
sonar-scanner
Explain

"After the build, we perform static code analysis using SonarQube to identify bugs, code smells, and security vulnerabilities. The Quality Gate must pass before the artifact is promoted."

(Mention that in your current practice project it is mocked with echo, but in real projects it runs sonar-scanner.)

8. Build Package
zip catalogue.zip --> usinf zip command 

Explain

"Once validation is complete, we package the application into a ZIP artifact, excluding unnecessary files such as the .git directory. This package is what gets deployed."

9. Publish Artifact

nexusArtifactUploader()  --> usinf this block we can push zip file to nexus 

Explain

"The generated artifact is uploaded to the Nexus Repository Manager. We use versioning so every build is stored uniquely, allowing us to roll back to previous versions if required."

10. Trigger CD Pipeline

Explain

"If deployment is requested, the CI pipeline triggers the CD pipeline and passes parameters such as the application version and target environment. The CD pipeline then deploys the same artifact to the selected environment."

CD Pipeline

1. Receive Parameters

version
environment
Explain

"The CD pipeline receives the artifact version and environment from the CI pipeline. This ensures the exact artifact produced during CI is deployed."

2. Terraform Init
terraform init
Explain

"Terraform initializes the working directory, downloads providers, and configures the remote backend for the selected environment."


3. Terraform Plan
terraform plan
Explain

"Terraform compares the desired infrastructure with the existing infrastructure and generates an execution plan showing the proposed changes."

4. Terraform Apply
terraform apply
Explain

"After reviewing the plan, Terraform provisions or updates AWS infrastructure such as EC2 instances, security groups, load balancer configuration, and application deployment."


Shared Library
Explain

"To avoid code duplication, we moved common pipeline logic into a Jenkins Shared Library. Each microservice Jenkinsfile simply invokes the shared library and passes a configuration map containing values like the component name. This improves maintainability and ensures all services follow the same CI/CD process."

Why Separate CI and CD?
Explain

"We separated CI and CD to keep build and deployment responsibilities independent. CI focuses on building, testing, code quality checks, and publishing artifacts, while CD is responsible for infrastructure provisioning and deployment. This separation makes the pipelines easier to maintain and allows the same artifact to be deployed across multiple environments."

Interviewer: Can you explain your Jenkinsfile?

Answer:

"In my project, we use a Declarative Jenkins Pipeline with a Shared Library. The Jenkinsfile is very lightweight because most of the common CI logic is implemented in the Shared Library, and each application passes only its configuration, such as the component name.
The pipeline starts by allocating a Jenkins agent where all the required tools like Git, Node.js, Terraform, AWS CLI, and Jenkins plugins are already installed.
Next, it accepts input parameters such as the target environment (Dev or Prod) and whether deployment should be triggered.
It then reads the application version dynamically from the package.json file to ensure the correct version is used throughout the pipeline.
After that, the pipeline installs project dependencies using npm install, executes unit tests, and performs SonarQube static code analysis to verify code quality.
Once the quality checks pass, it packages the application into a ZIP file and uploads the artifact to Nexus Repository Manager with versioning.
Finally, if deployment is selected, the CI pipeline triggers the CD pipeline by passing the application version and target environment. The CD pipeline then performs Terraform Init, Plan, and Apply to provision or update the infrastructure and deploy the application."

Short Version (2 minutes)

"A Jenkinsfile is a Pipeline as Code file written in Groovy that automates the CI/CD process. In my project, our Jenkinsfile runs on a Jenkins agent, installs dependencies, executes unit tests, performs SonarQube analysis, packages the application, publishes the artifact to Nexus, and finally triggers the CD pipeline. The CD pipeline receives the artifact version and environment from the CI pipeline and uses Terraform to deploy the application to the target AWS environment. We also use Jenkins Shared Libraries to avoid duplicating common pipeline logic across multiple microservices."




Jenkins Credentials
"Jenkins Credentials provide a secure way to store sensitive information such as usernames, passwords, SSH keys, API tokens, AWS access keys, and secret text. 
Instead of hardcoding these values in the Jenkinsfile, we store them securely in Jenkins and reference them using a Credentials ID."

Why do we use them?
Avoid hardcoding passwords in Jenkinsfiles.
Secure sensitive information.
Centralized credential management.
Easy to rotate passwords without changing pipeline code.


Types of Jenkins Credentials
| Type                               				    | Used For                        |
| ----------------------------- 				    | ------------------------------- |
| Username with Password            | Nexus, Git, Docker Registry     |
| Secret Text                                      | API Tokens, Sonar Token         |
| SSH Username with Private Key | GitHub SSH, Remote Server Login |
| Secret File                                       | kubeconfig, certificates        |
| Certificate                   					| SSL/TLS authentication          |


How to Create Credentials  ----> In Jenkins UI ----> Manage Jenkins ----> Credentials ----> System ----> Global Credentials ----> Add Credentials

Using Credentials in Pipeline

1. Username & Password (Nexus)
In Jenkins UI ----> Manage Jenkins ----> Credentials ----> System ----> Global Credentials ----> Add Credentials       -----> manually create first 
Username : admin
Password : admin123
Credential ID : nexus-login-credentials

In Pipeline 
withCredentials([
    usernamePassword(
        credentialsId: 'nexus-login-credentials',
        usernameVariable: 'USERNAME',
        passwordVariable: 'PASSWORD'
    )
]) {
    sh """
        curl -u $USERNAME:$PASSWORD http://nexus.example.com
    """
}

When this block executes:

Jenkins looks for nexus-login-credentials.
Retrieves the stored username and password.
Creates temporary environment variables:
USERNAME=admin
PASSWORD=admin123
Executes the shell command.
Removes those variables after the block finishes.

2. Secret Text (Sonar Token)

Credential Type : Secret Text
Credential ID : sonar-token
Secret : xxxxxxxxxxxxx

In Pipeline
withCredentials([
    string(credentialsId: 'sonar-token',
           variable: 'SONAR_TOKEN')
]) {

    sh """
        sonar-scanner -Dsonar.login=$SONAR_TOKEN
    """
}

nexusArtifactUploader(

    ...
)

So before running this pipeline, you must create a Jenkins credential with the ID: nexus-login-credentials
The nexusArtifactUploader plugin will automatically fetch the username and password from Jenkins. You don't need to write withCredentials() in this case because the plugin itself knows how to use the credentialsId.
