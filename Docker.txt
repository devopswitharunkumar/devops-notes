1. Physical Server
A Physical Server is an actual hardware machine with CPU, RAM, storage disk, and network resources on which an operating system installed and deploy applications directly.
it offers complete control and high security and full isolation but results in higher cost, lower resource utilization, and slower provisioning and need to maintain.
Only One application is deployed directly on one physical hardware machine.

2. Virtualization
Virtualization is the process of creating multiple isolated Virtual Machines on a single Physical Server using a Hypervisor. 
Each Virtual Machine has its own Guest OS , bin's and dependencies and lib's ,application running, and dedicated virtual resources
enabling better hardware utilization, isolation(each vm is isolated), and faster provisioning(1-3 mins) compared to Physical Servers.

multiple Virtual Machines on single Physical Server via Hypervisor

Hypervisor (used ESXi/KVM/Hyper-V)
A Hypervisor is the virtualization layer that abstracts the underlying physical hardware and allocates CPU, memory, storage, and network resources equally to multiple Virtual Machines while ensuring isolation between them.
or
A Hypervisor is software that creates, manages, and runs multiple Virtual Machines on a Physical Server.

3. Containerization
Containerization is an operating system-level virtualization technology in which applications and their dependencies are packaged into isolated containers. 
Unlike Virtual Machines, containers share the host operating system's kernel, making them lightweight, portable, faster to start, and more resource-efficient.
or
Containerization is a technology that packages an application along with its dependencies into a lightweight container that shares the same host OS kernel.


Initially applications were deployed directly on physical servers, but this caused high cost and poor resource utilization. 
Virtualization solved this by allowing multiple VMs to run on the same physical server using a hypervisor. However, each VM still required its own operating system, so VMs were relatively heavy. Containerization solved this by packaging the application and dependencies into lightweight containers that share the same host OS kernel. 
In my DevOps projects, we use Docker to containerize microservices and Kubernetes/EKS to deploy, scale and manage those containers.

Why do we get an error?
Suppose you install Docker on an EC2 instance. using a normal user like: ec2-user without root access  You may get an error like: permission denied while trying to connect to the Docker daemon socket at unix:///var/run/docker.sock

Why?
When Docker is installed, it creates a Docker Daemon and a Linux group called docker. The Docker socket (/var/run/docker.sock)  and the docker group is owned by the root user. 
A normal user who is not part of this group cannot communicate with the Docker Daemon and gets a permission denied error. 
To allow a non-root user to execute Docker commands, we add the user to the docker group using sudo usermod -aG docker <username>, and then refresh the user's group membership by logging out and logging in or by using newgrp docker.

Example:
ls -l /var/run/docker.sock

Output:
srw-rw---- 1 root docker ... /var/run/docker.sock

Notice: Owner → root and Group → docker
Only these users can communicate with the Docker Daemon: root -->  Users who belong to the docker group

Why doesn't docker ps talk directly to the Docker Engine?
Answer: Because the docker command is just the Docker Client. It sends requests through the Docker socket (/var/run/docker.sock) to the Docker Daemon, which performs the actual operations like listing containers, creating images, or starting containers.

Interview Answer (5 Years)
To access a running container, we use docker exec -it <container-name> /bin/bash. 
The exec command starts a new process inside the running container. 
The -i option keeps the session interactive, while -t allocates a terminal. 
This allows us to execute Linux commands, inspect application files, verify logs, troubleshoot issues, or check environment variables without affecting the main application process. 
If Bash is not available, such as in Alpine-based images, we use /bin/sh instead.

Dockerfile
--------------
A Dockerfile is a text file containing a set of instructions that Docker follows to automatically build a Docker image.
or
A Dockerfile is a declarative way of creating Docker images.

What does "Declarative" and imperative means?
Imperative Approach :  You tell Docker step-by-step commands to execute immediately
docker run,docker image etc.. You execute each command manually.
Ex: 
docker run ubuntu
apt install java
mkdir /app
cp application.jar /app
java -jar application.jar



Declarative Approach : Instead of executing commands one by one, you write all the instructions in a file.
Because we only describe: What we want i.e desired state. We don't tell Docker how to create image layers internally. Docker decides that itself. We simply declare the desired state.

Ex : 
FROM ubuntu
RUN apt update
RUN apt install openjdk-17-jdk -y
COPY application.jar /app/
CMD ["java","-jar","/app/application.jar"]

Now Docker reads the file and executes everything automatically. This file is called a Dockerfile.



Why do we use Dockerfile?
Imagine your project has 20 developers.
Without Dockerfile   : every developer must manually install: Java , Maven , Dependencies , Copy application , Start application ....Everyone might do it differently.
With Dockerfile         : everyone executes: docker build -t catalogue:v1 .  ---> Every developer gets exactly the same image.


Real-Time Project Example (RoboShop)
********************************
Suppose your Catalogue application/folder has:  package.json , server.js , Dockerfile all these files 

Dockerfile:

FROM node:18
WORKDIR /app
COPY . .
RUN npm install
EXPOSE 8080
CMD ["node","server.js"]

Build : docker build -t catalogue:v1 .    			 ---> build an images based on all instructions given in Docker file 
Run	  : docker run -d --name catalogue -p 8080:8080 catalogue:v1.0.0
Now your own application is running inside Docker.

Interview Answer (5 Years)

A Dockerfile is a text file that contains a sequence of instructions used to build a Docker image. 
It is called a declarative approach because we define the desired configuration, such as the base image, dependencies, application files, startup command, and exposed ports, while Docker handles the execution. 
In our project, every microservice had its own Dockerfile. Jenkins used the Dockerfile during the CI pipeline to build a versioned image, which was then pushed to the image registry and deployed to the target environment.

Docker first checks whether the specified image exists locally. If not it automatically pulls it from the configured registry. 
The base image provides the operating system, runtime, libraries, and other dependencies required by the application. 
All subsequent Dockerfile instructions create as new read only image layers on top of this base image. 
In our RoboShop project, for Node.js services like Catalogue, we used FROM node:18 so the image already contained Node.js and npm already installed, allowing us to focus only on copying the application code and installing project-specific dependencies.

Q1. Why is FROM mandatory?
Because Docker needs a starting point (base image) to build the new image.

Q2. Can a Dockerfile have multiple FROM instructions?
yes ---> This is called a Multi-Stage Build.

Q3. What happens if the base image is not present locally?
Docker automatically downloads it from the registry (such as Docker Hub) before continuing the build.

------
RUN instruction is used to execute commands during the image build process. The changes made by the command become part of the Docker image.
or
RUN executes commands while building the image and permanently saves the results in a new image layer.

Why do we need RUN? 
Suppose you have this Dockerfile  :  FROM ubuntu:24.04
Currently your image only has Ubuntu. But your application needs: Java, Maven, Git how do u install using RUN we install
Example:
RUN apt install openjdk-17-jdk -y
RUN apt install git -y

During image creation, Docker performs all installation steps. When the image is ready, Everything is already installed.

Internal Working : Suppose your Dockerfile is
FROM ubuntu:24.04
RUN apt update
RUN apt install nginx -y
You execute :-   docker build -t nginx-image:v1 .

Step 1 : Docker reads FROM ubuntu:24.04 creates ubuntu image 
Step 2 : Dockerfile has RUN apt update --> Docker does NOT execute the command directly on the image. instead  Docker creates a temporary writable container on basis of ubuntu 
Step 3 : Inside that temporary container Docker executes apt update
Step 4 : After execution completes, Docker takes a snapshot of the container filesystem. This snapshot becomes a new image layer on top of ubuntu image.
Step 5 : Temporary container is deleted. But the layer remains on top image
Step 6 : Docker reads the next instruction.  Again, Docker creates another temporary container. Executes and Creates another layer. Deletes the temporary container.

A filesystem is the structured directory of files and folders inside the container
snapshot is a frozen, read-only copy of those files captured at a specific moment in time.

Why temporary container? Because Docker images are read-only.
Docker cannot directly modify an image. Instead, It creates a temporary writable container, executes the command, saves the changes, then removes the temporary container.

Why don't we use CMD for installation?
Some beginners write CMD npm install This is wrong. Why? Because CMD executes when the container starts. That means Every time docker run Docker would execute npm install Imagine downloading 500 MB of dependencies every time the container starts.Very slow. Instead, Use RUN npm install Now dependencies are installed only once during image build.

CMD instruction is stored inside the image configuration manifest (a JSON file) as part of the image's metadata on your local disk.

⭐ Interview Tip
"Since both are metadata, why did Docker create two separate instructions?"

This separation allows Docker and orchestration tools to understand network-related information independently from business or operational metadata.

Interviewer:
Why not use ENV instead of ARG?
ARG is intended for values that are only required during the image build process, such as application versions or build numbers. 
ENV is intended for configuration values that the application needs while the container is running, such as database URLs, ports, or environment names. 
Using ARG for runtime configuration would not work because ARG values are discarded after the image is built.

Interview Answer (5 Years)
ONBUILD is used to register build triggers in a parent image. These instructions are not executed when the parent image is built. 
Instead, they are automatically executed when another Dockerfile uses that image in its FROM instruction. It is useful for creating reusable base images with common build steps. However, in most modern production projects, ONBUILD is used less frequently because it can hide build behavior and make Dockerfiles harder to understand.


Q1. Does ONBUILD execute during its own image build?
Answer: No. It is only stored as a trigger. It automatically execute those ONBUILD instructions when child image uses the parent image where ONBUILD instruction written 

Q2. When does ONBUILD execute?
When another Dockerfile uses the image as its parent image with the FROM instruction.


⭐ Interview Tip
Why is ONBUILD not very popular today?
ONBUILD can make Docker builds less transparent because instructions execute implicitly when a child image is built. 
In modern CI/CD pipelines, teams usually prefer explicit Dockerfiles where every build step is clearly visible and easier to maintain and troubleshoot.

Interview Answer
eth0 : 
eth0 is the primary network interface of a Linux machine/server. It receives the IP address from AWS or the physical network and is responsible for all communication between the server and external systems.


Now Docker Comes:
--------------------------
When u install Docker in ec2 
Suppose Your EC2 has : eth0 ----> 172.31.90.88

Now you install Docker.
Should all containers directly use eth0 ?
Answer ---> No.

Why?
Imagine 100 containers. If all of them use eth0 directly, there will be IP conflicts , Security issues , Difficult management So Docker creates its own network.

What is docker0?
Immediately after installing Docker, Docker automatically creates one virtual  network interface i.e., docker0 by default it is a default bridge network 
EX: Execute --> ifconfig --> u can see ---> docker0   ----> has ip of   ----> 172.17.0.1

docker0 : 
------------
The docker0 interface is the default virtual network bridge created automatically by the Docker engine when u install docker in ec2.
It enables isolated containers on the same host to discover and communicate with each other.
It manages a private network subnet (typically 172.17.0.0/16) and dynamically assigns a unique IP address to the virtual network interface (eth0) of each container connected to the default bridge network
It acts as the default gateway (172.17.0.1) for those containers means it takes the traffic from your containers and passes it out to the internet through your host machine's main network card (i.e., eth0).
		simply ---> when container wants to talk to internete it moves traffic from inside the container's world to the outside world by using eth0 NIC connected to AWS/internete

Docker says I won't directly connect containers to eth0. Instead "I'll create my own network. That network is docker0

Flow : internet ---> EC2 eth0 (i.e., 172.31.90.88) ---> Docker install --> create docker-0  (i.e., 172.17.0.1) --->  now docker-0 assign containers ip
container-1 :  172.17.0.2 
container-2 :  172.17.0.3    etc.....

Why docker0?
Suppose : There are 20 containers. Instead of giving AWS IP to every container(i.e., eth0), Docker creates its own private network. Inside that network, containers receive 172.17.x.x addresses.
All are inside Docker's private network.
Now Every container send requests to the docker-0 that is default docker network then Docker forwards them.

Real Example:
If catalogue want to connect with mongodb 
Suppose : MongoDB ---> 172.17.0.2 and Catalogue 172.17.0.3 ---> Catalogue wants MongoDB.

Request : Catalogue ---> 172.17.0.2 ---> docker0 ---> MongoDB
Everything stays inside Docker's private network. Internet is not involved.


Problem with Default Bridge Network :  it uses ip to communicate if container ip changes other container trying to connect with old ip so application fails and it cannot communicate using container name 
Suppose ---> docker run mongodb and docker run catalogue ---> Both use Default Bridge Network. Yes, they can communicate using IP. Example 172.17.0.2

Why does Docker create docker0?
docker0 is a virtual bridge network interface automatically created by Docker during installation. Instead of connecting containers directly to the host's physical interface (eth0), Docker isolates them in its own private network. The docker0 interface acts as the gateway for the default bridge network, assigns private IP addresses to containers, and forwards traffic between containers and the host network. In production, we usually create user-defined bridge networks because they provide better isolation and automatic DNS-based communication between containers.

Multi-Stage Builds
-------------------------
It is a docker build optimization technique where multiple FROM instructions are used in a single Dockerfile. One stage is used to build the application, and another stage is used to create the final lightweight image by copying only the required artifacts.

i.e., We use one Docker image to build the application and another Docker image to run the application.

Source Code

Docker Layers
------------------
Why Docker introduced Layers?
Before understanding Docker Layers, let's understand the problem. Suppose you have a Dockerfile.Insterd of create one layer big image 

What is Docker Layer ?
A Docker Layer is a read-only filesystem layer created for every Dockerfile instruction. Docker stacks these layers one above another to form the final Docker Image.
or
Every instruction in Dockerfile creates one layer.

Internal Working	 : Suppose Dockerfile

FROM node:20
RUN yum install git -y
COPY . .
RUN npm install
CMD ["node","server.js"]

FROM instruction is the layer 1
RUN instruction is the layer 2
etc ..layer 3, layer 4 and 5 etc....

All these layers together become Docker Image

Question:
Does Docker create one single big image?
Answer: No. Docker creates the image in multiple layers. Every instruction creates one layer. This is called Docker Layer Architecture.

Why read-only?
Docker Images should never change. If one image changes, all containers using it become inconsistent. Therefore every layer is read-only. When a container starts,Docker adds one writable layer on top.
Whenever application creates Everything goes into writable layer. Not image layers.

Interview Question
Which instructions create layers?
Almost every Dockerfile instruction creates a filesystem layer (such as FROM, RUN, COPY, ADD). Instructions like CMD, ENTRYPOINT, ENV, LABEL, EXPOSE, and WORKDIR mainly update image metadata or configuration. They still become part of the image history/configuration but don't necessarily add a new filesystem layer in modern BuildKit builds.

For interview purposes, it's safe to say:
Filesystem-changing instructions create layers, while configuration instructions mainly update image metadata.

Docker Layer Cache is the mechanism where Docker reuses previously built layers if the corresponding Dockerfile instruction and its inputs have not changed.

Simple If nothing changed, Docker doesn't rebuild that layer.

Docker checks Layer 2  ---> changes ? No ---> Reuse layer from Cache
Docker checks layer 3   ---> we changes server.js so copy should happen so ---> changed ? yes ---> rebuild that layer

1. Use Small Base Images
Use lightweight images like alpine or slim instead of full OS blueprints to drastically reduce image size, speed up deployment, and minimize the attack surface by eliminating unnecessary system utilities.
2. Use Multi-Stage Builds
Separate the compilation environment from the execution environment to discard heavy build-time tools (like Maven or Go compilers) and keep only the final application binary or JAR file in the production layer.
3. Order Dockerfile Instructions Properly
Place slow-changing instructions like COPY package.json and dependency installations before frequently changing application source code to maximize Docker layer cache reuse and reduce build pipeline times.
4. Combine Multiple RUN Commands
Chain commands using && and \ within a single RUN block to drastically reduce the total number of intermediate filesystem layers and eliminate redundant image metadata bloat.
5. Clean Package Cache
Always bundle package manager cache cleaning (e.g., && rm -rf /var/lib/apt/lists/* or && yum clean all) inside the same RUN layer that installs the software, preventing ephemeral package archives from getting baked into the image.

6. Use .dockerignore
Exclude large, irrelevant directories like .git, node_modules, and local logs from the initial build context to prevent slow uploads from the host disk to the Docker engine daemon.
7. Run Container as Non-Root User
Create a dedicated system user and switch to it using the USER instruction to enforce the principle of least privilege, preventing container breakout exploits from instantly gaining root access to the underlying host.
8. Don't Store Secrets Inside Images
Never bake hardcoded credentials or API keys into Dockerfiles or ENV parameters; instead, dynamically inject them at runtime using environment variables or dedicated systems like Kubernetes Secrets and HashiCorp Vault.
9. Use Specific Image Tags
Strictly avoid using the moving target :latest tag; pin explicit semantic versioning (e.g., node:20.11.0-alpine) to guarantee absolute build reproducibility and predictable behavior across production environments.
10. Use Named Volumes for Stateful Applications
Map persistent backend databases (like PostgreSQL or MongoDB) to Docker Named Volumes to securely decouple the critical data lifecycle from ephemeral application containers during updates.

11. Use Custom Networks
Isolate production application stacks inside dedicated user-defined bridge networks to leverage the engine's built-in DNS service discovery while completely blocking unauthorized inter-container communication.
12. Implement Health Checks
Configure embedded HEALTHCHECK instructions so the container runtime can natively monitor application responsiveness and automatically route or restart traffic away from frozen or zombie processes.
13. One Process Per ContainerEnforce a strict decoupling policy where each container manages a single process or microservice to enable granular horizontal auto-scaling, precise logging, and isolated process failure domains.
14. Use Image Scanning
Integrate automated scanning tools like Trivy, Aqua, or Snyk directly into the CI/CD pipeline to catch CVE software vulnerabilities and outdated packages before the image can be promoted to production registries.

Container Lifecycle:
-------------------------

Container Lifecycle refers to the different states a Docker container goes through from the time it is created until it is removed. 
It defines how a container is created, started, paused, stopped, restarted, and finally deleted.


Container States : 1) Created, 2) Running, 3) Pause and Unpause, 4)Exited/stopped , 5) Restarting , 6) Remove 

Stage 1 - Created
commad :  docker create nginx

What happens?
Docker Engine Checks whether the image exists , Creates the container , Allocates a Container ID , Creates a Writable Layer , Configures networking , Configures the filesystem. But the application is NOT started.

If u see --> docker ps -a 	
Container will exist but it is not in running state it is in created state 

Stage 2 - Running
Command : docker start container-id   
Now container will comes into running state 

Along with this command we also have other command --> instaead of doing both commands --->  create  + start  ---> docker run ---> do both at a time 
Combination of --->   docker create + docker start

if u do and see :  docker ps ----> Container status becomes Running

Stage 3 - Paused
command :  docker pause <containername/id>


Container still exists. 
Memory still exists. 
Network still exists. 
Application process is temporarily frozen. 
Docker uses Linux cgroups freezer to suspend the processes. No CPU is consumed. It is temporarily stopped. container becomes paused state

Resume :  docker unpause <containername/id> --> container becomes running state

Stage 4 - Exited / Stopped
Command : docker stop catalogue

Internal Working

Docker sends SIGTERM to the application. 
This is a graceful shutdown signal. Docker waits (default 10 seconds). If the application exits properly, Container becomes Exited

docker ps -a   ---> Exited state 

Stage 5 - Restart
commad :  docker restart catalogue
Docker executes : Stop ---> Start

Stage 6 - Removed
command : docker rm <container name/id>

Docker removes
Container ID , Writable Layer,  Container Metadata but Image will still exists.



docker stop vs docker kill
docker stop Sends SIGTERM Waits 10 Seconds Graceful Shutdown. Application gets time to save data.
docker kill Sends SIGKILL Immediately kills the process. No waiting. No graceful shutdown. Think Power Off vs Shutdown.



And if Execuion completes container will automatically exit 
Ex:  CMD ["echo","Hello"]  ---> docker run test it gives output and exits immediately because container job is done

Additional topics:
-----------------------

1. OCI (Open Container Initiative)
An open standard that defines how container images and runtimes should work so that images built by one tool can run on another (Docker, Podman, containerd, etc.).

2. OCI Image Specification
Defines the standard format for a container image (layers, metadata, manifest) so any OCI-compliant runtime can use it.

3. OCI Runtime Specification	
Defines how a runtime (like runc) should create and run a container using Linux kernel features.

4. BuildKit
A modern Docker image builder that provides faster builds, parallel execution, better caching, and secret management during image builds.

5. Buildx
An extension of BuildKit used to build images for multiple platforms such as AMD64 and ARM64 from a single Dockerfile.

6. Docker Context
Allows one Docker CLI to connect to different Docker Engines (local, remote server, Docker Desktop, etc.).
Ex:  docker context ls

7. .dockerignore
Similar to .gitignore. Specifies which files should not be sent to the Docker build context, reducing build time and image size. Ex: .git, node_modules,target , *.log etc...

8. Named Build Contexts
Allows multiple source directories to be used during a Docker build instead of only the current directory. Used mostly in advanced builds.

9. Rootless Docker
Runs Docker without root privileges, improving security by reducing the impact of container escapes.

10. Docker Logging Drivers
Control where container logs are stored.

Examples:
json-file (default)
syslog
fluentd
journald
awslogs


11. Restart Policies ---> Automatically restart containers if they stop.

Examples : types 
--restart=no
--restart=always
--restart=unless-stopped
--restart=on-failure

12. Resource Limits ---> Restrict container resource usage.

Example:
--memory=512m
--cpus=2

Prevents one container from consuming all host resources.

13. Docker Secrets
Securely stores sensitive data like passwords and API keys. Mainly used with Docker Swarm. In Kubernetes, Secrets are used instead.

14. Docker Content Trust
Verifies image authenticity using digital signatures, ensuring images haven't been tampered with.

15. Image Scanning ---> Checks images for vulnerabilities.

Popular tools:
Trivy
Docker Scout
Clair

Very common in DevSecOps pipelines.

16. Distroless Images
Contain only the application and required runtime. No shell, package manager, or unnecessary utilities.

Advantages:
Smaller image
Better security
Fewer vulnerabilities

17. Alpine vs Ubuntu vs UBI

Alpine → Very small (~5 MB), lightweight, security-focused.
Ubuntu → Larger, feature-rich, common for development.
UBI (Universal Base Image) → Red Hat-supported enterprise image, common in enterprise environments.

18. Scratch Image
 The smallest possible base image. Contains absolutely nothing. Used for statically compiled applications (mostly Go).
 
Example
Instructions :    FROM scratch
 
 
19. Root Filesystem (RootFS)
The filesystem inside a container. Created by combining all image layers plus one writable layer.

20. Union File System / OverlayFS
Docker combines multiple read-only image layers into a single unified filesystem using OverlayFS.
This is what makes Docker layering possible.


21. Copy-on-Write (CoW)

Containers share image layers.
When a file is modified, Docker copies only that file into the writable layer instead of changing the original image layer.
This saves disk space.

22. Dangling Images ---> Images without tags. Usually leftover images after rebuilding.

Remove them using: : docker image prune

23. Intermediate Images
Temporary images created during Docker builds. Used internally for layer creation and caching. Normally removed automatically.


24. Build Context

The directory sent to Docker during: docker build . The . represents the build context. Docker can only COPY or ADD files from this context.

25. Build Cache Invalidation

Docker reuses cached layers. If one layer changes, all subsequent layers are rebuilt.

Ex: That's why we write: like below to maximize cache reuse.
COPY package.json .
RUN npm install
COPY . .


26. Multi-Architecture Images
A single image can support multiple CPU architectures.

Examples:

amd64 (Intel/AMD)
arm64 (Apple Silicon, AWS Graviton)

Buildx is commonly used to create multi-architecture images.

Docker Resource Limits
-------------------------------
Why do we need Resource Limits?

Imagine a Linux server with : -->  CPU : 8 Cores and Memory : 16 GB

Now suppose we run three containers 
--> Container A (java), Container B (NodeJS),  and Container C (MYSQL). 
By default, Docker does not limit CPU or Memory.
Suppose : Container A suddenly starts consuming ---> Memory = 14 GB now remaining memory 2GB --> if we have diff/multiple applications in same host those containers start failing 
This is called Resource Starvation.

Solution:  We define limits.
Example : 
1. docker run --memory=512m --cpus=2 nginx    ----> Now Docker ensures Container cannot exceed			---> it is like hard limit 

2. docker run -d --name my-app -m 512m --memory-reservation 256m nginx
3. docker run -d --name my-app --cpus="2.0" --cpu-shares=512 nginx

--memory-reservation 256m and --cpu-shares=512  ----> refers to soft limit it can cross this line if container wants more and host has space but will pushed back to use same limit if server runs low but if container hits hard limit  --> 
in case of memory  ----> container dead -- OOM killed error --> container will be killed by linux kernel 
in case of cpu ---> High latency (requests take much longer to respond).Low performance and slow execution speed. High CPU Throttling metrics in your dashboards 

Meaning : Container cannot use more than 512 MB RAM

Internally : Docker Client ---> Docker Daemon ---> containerd ---> runc ---> Linux cgroups ---> Linux Kernel ---> Container

Notice : Docker itself doesn't limit CPU. Docker asks Linux to do it. Linux uses cgroups

What are cgroups?
cgroups (Control Groups) are a Linux kernel feature that limits, measures, and isolates resource usage such as CPU, Memory, Disk I/O, and Network for a group of processes.
or
cgroups control how much hardware resources a process or container can use.

Example :
Server Memory : 16 GB
Container A --> Limit : 512 MB
Container B  --> Limit : 1 GB
Container C --> Limit : 2 GB
Linux Kernel uses cgroups to enforce these limits.

Memory Limit
What happens internally?
Container starts ---> Application allocates memory ---> Linux cgroup monitors ---> Memory reaches 512 MB ---> Application requests ---> more memory ---> Linux denies ---> OOM Killer executes ---> Container stops


OOM Killer  : Out Of Memory.
Suppose : Limit 512 MB ---> Application tries ---> 700 MB ---> Linux kills the process ---> Container moves to Exited State.


Interview Question
What happens if container exceeds memory limit?
Linux cgroups detect that the container has exceeded its configured memory limit. The Linux OOM Killer terminates the container's main process, causing the container to stop.

CPU Limit
Command :  docker run --cpus=2 nginx

Suppose : Server has 8 CPU Cores
Container gets 2 CPUs So Container cannot consume more than 2 CPUs.

Internal Working : 
Linux Scheduler allocates CPU based on cgroups. Docker doesn't schedule CPU. Linux Kernel does.

Memory Swap : 
4. Command:  docker run --memory=512m --memory-swap=1g

Means RAM 512 MB Swap 512 MB Total Available 1 GB If RAM becomes full, Linux temporarily uses disk (swap).

Why avoid excessive swap?
Swap uses disk instead of RAM. Disk is much slower. Application performance drops significantly. That's why production environments usually minimize or disable swap for containers.

What if we don't specify limits?
Docker does not impose CPU or Memory limits. The container can consume as many resources as the host allows. This can impact other applications running on the same server.

Check Resource Usage :  
command : docker stats 
This command displays real-time CPU and memory usage for running containers.

Real Project Example
In our project, we monitored resource usage using docker stats during development and testing. For production deployments, resource limits were primarily defined in Kubernetes manifests rather than with Docker CLI options. This ensured that each microservice received appropriate CPU and memory allocations and prevented one service from exhausting node resources.

Why do we configure Resource Limits?
To prevent one container from consuming excessive CPU or memory and affecting other containers running on the same host.

Who actually limits CPU and Memory?
Not Docker. The Linux Kernel enforces resource limits using cgroups. Docker only configures them.

What happens if Memory Limit is exceeded?
Linux OOM Killer terminates the container's main process.The container stops.

What happens if CPU Limit is exceeded?
The container is throttled. It is not killed. The Linux scheduler restricts its CPU usage to the configured limit.


4+ Years Interview Answer

In Docker, resource limits are configured to prevent a container from consuming excessive host resources. We can limit memory using --memory and CPU using --cpus. Internally, Docker configures Linux cgroups, which enforce these limits. If a container exceeds its memory limit, the Linux OOM Killer terminates the main process, causing the container to stop. If it exceeds its CPU limit, the Linux scheduler throttles CPU usage rather than terminating the container. In our project, we monitored container resource consumption using docker stats, while production resource limits were managed through Kubernetes resource requests and limits, which use the same Linux cgroups mechanism underneath.

Why do we need Restart Policies?

Suppose you have deployed your application.
Host Machine
├── Catalogue Container
├── User Container
├── Cart Container
├── MySQL Container
└── Redis Container

Everything is working fine. Suddenly, Catalogue application crashes because of Java OutOfMemoryError , NullPointerException , Database Connection Failure , Application Bug. So Container becomes
Exited

Question:
Should we manually execute ---> docker start catalogue ---> every time? Imagine this happens at 2 AM. Nobody is available. Application remains down.


Solution
Docker Restart Policies tell Docker If the container stops, should I restart it automatically?

Internal Working : 
Suppose :  docker run --restart=always catalogue:v1

Internally : 
Docker Client ---> Docker Daemon ---> Container Running ---> Application Crashes ---> Docker Daemon Detects Exit ---> Checks Restart Policy ---> Restart Container

Notice : Docker Daemon continuously monitors containers.

Types of Restart Policies:
--------------------------------
There are 4 restart policies.
1)no
2)on-failure
3)always
4)unless-stopped


1. no (Default) :   
command :  docker run --restart=no nginx  or docker run nginx
This is the default behavior.  Application crashes ---> Container becomes Exited Docker does nothing. You must manually restart it.
Use Case

Mostly used : Testing , Temporary containers , One-time jobs

2. on-failure
Command : docker run --restart=on-failure nginx
Container automatically restarts only if application exits with a non-zero exit code.

Example:  Java Exception ---> Exit Code = 1 ---> Restart

Suppose : Application finishes successfully Exit Code = 0 Docker will NOT restart.

Maximum Retry : Docker tries 5 times restart. If still failing Container remains/goes to Exited state.
Ex:  docker run --restart=on-failure:5 nginx

Production Example : Batch Jobs , Data Migration , ETL Jobs , These should restart only on failures.

3. always
Command :  docker run --restart=always nginx

Container restarts every time it stops.

Reasons : Application Crash , Docker Daemon Restart , Host Reboot --> all times it restarts
Everything causes restart.

Production Example
Web Applications ,  Microservices , Nginx , Spring Boot ,  NodeJS and These should always be available.

4. unless-stopped
docker run --restart=unless-stopped nginx

This is almost same as always BUT If YOU manually stop using (docker stop container) the container
Docker remembers that. Even after Server Restart Docker does NOT restart the container.

Example
docker stop catalogue ---> happen Server Reboot ---> Container Still Stopped Because YOU intentionally stopped it.
But in always policy 
docker stop catalogue ---> happen Server Reboot ---> Container will restart


Suppose

docker run --restart=always catalogue

Application crashes ---> PID 1 exits ---> Container enters ---> Exited State ---> Docker Daemon notices ---> Reads Restart Policy ---> Restart Container ---> Application Running


Real Project Example
In development environments, we sometimes used --restart=unless-stopped so that application containers came back automatically after a server reboot but remained stopped if a developer had intentionally stopped them for maintenance.

In production, when applications were deployed on Kubernetes, we generally did not configure Docker restart policies because Kubernetes itself manages container restarts. The kubelet monitors containers and recreates them based on the Pod's restart policy. Therefore, restart management was handled by Kubernetes rather than Docker.


always                    --> Restarts even after manual stop followed by daemon/host restart
unless-stopped     --> Does not restart if the container was intentionally stopped by the user



Production Scenario :
---------------------------

One of your Spring Boot containers crashed because of Out Of Memory. How did it come back automatically?
Answer:

"The container had a restart policy configured. Docker Daemon detected that the container's main process exited and automatically restarted it based on the configured restart policy. In Kubernetes environments, the kubelet performs this responsibility instead of Docker."


4+ Years Interview Answer

"Docker Restart Policies define how Docker should behave when a container stops or crashes. Docker Daemon continuously monitors container states and applies the configured restart policy. The available policies are no, on-failure, always, and unless-stopped. For long-running applications such as Spring Boot or Nginx, always is commonly used so the service automatically recovers after crashes or host reboots. For one-time batch jobs, on-failure is preferred because the container should restart only if execution fails. In our Kubernetes environments, restart behavior was handled by the kubelet using Pod restart policies, so Docker restart policies were generally not required."

Docker Namespaces:
---------------------------

A Namespace is a Linux kernel mechanism that isolates resources like processes, networking, filesystems, hostname, users, etc., so that one container cannot directly see or interfere with another container or the host.


Namespaces are used to isolate system resources so that multiple containers can run securely on the same Linux host without affecting each other.


Docker uses two Linux features
Namespaces ----> Isolation
cgroups ----> Resource Limits

Namespaces answer ----> "What can this container see?"
cgroups answer ----> "How much resource can this container use?"

Suppose your laptop has these processes running:
Chrome , Redis , Docker , Nginx , Java Application etc....
How does Chrome know that MySQL exists --> it knows if u do ps -ef because all are in same host machine 
and Chrome (actually the OS) can see all running processes because they're all running on the same operating system.

Now imagine this situation :  You start an Nginx Docker container. Inside the container you run ---> run ---> ps -ef ---> shows only 

PID   COMMAND
1     nginx

Now you ask: Where is MySQL? Where is Redis? Where is systemd? You don't see them.

Why? This is where Namespace comes in.

Without namespaces ---> U can see every process which are in host machine 

With namespaces : On Host OS --> if u create container only container process id only visible that is by default (PID  1) for every container because all container are seperate and isolated 



Let's understand with a real example
PID : Example 
Suppose you start Nginx ------->  docker run nginx   -------> Now enter the container -------->  docker exec -it nginx bash   -------> Run ----> ps -ef ---->  PID 1 nginx 

You think Where is Docker? Where is MySQL? Where is Redis? ---> They are running on the same EC2. Why aren't they visible? Because Docker created a PID Namespace. This namespace hides all other processes. The container thinks "Only I exist."


Another example :  Network namespace example 

Suppose your EC2 has IP   ---->  172.31.10.20
Now create two containers  -----> catalogue and cart 
If there were no namespaces --->  both would try to use 172.31.10.20 (ec2 ip) Impossible.

Instead Docker gives them

Catalogu   ----> 172.18.0.2
MongoDB ----> 172.18.0.3

How ----> Using a Network Namespace. Each container has its own network stack.

A namespace a private view. The actual Linux kernel is still shared.

What exactly is isolated ----->  Linux can isolate different resources. Each isolation is called a Namespace.



Types of Namespaces : Docker mainly uses
PID Namespace
Network Namespace
Mount Namespace
UTS Namespace
IPC Namespace
User Namespace
Let's understand each.


1. PID Namespace :  It isolates Processes.
PID Namespace isolates processes by giving each container its own process ID (PID) space.

What does it isolate?
Running processes
Process IDs (PIDs)

The container sees only its own processes not Host Processes

Host has multiple processes and can see everything. but container sees only itseflf

2. Network Namespace
Network Namespace isolates networking resources by providing each container with its own network stack. Each container has its own IP.
Creates separate ip adddress for each container  ----> IP Address , Routing Table ,Network Interfaces , Ports , Firewall rules etc

3. Mount Namespace :  Filesystem isolation.
Mount Namespace isolates the filesystem by giving each container its own view of mounted directories and filesystems.

It isolates
Root filesystem
Mounted directories
Storage paths

Suppose host has :  /home , /etc ,  /var etc....
Container sees      : / , /etc , /usr,  /app

The container cannot see the host filesystem unless you explicitly mount it using a bind mount or volume.This is why containers have their own filesystem.

4. UTS Namespace  :   UTS = Unix Time Sharing.

UTS Namespace isolates system identifiers such as the hostname and domain name.
It isolates :
Hostname
Domain name


Example: 
In EC2 if u type : 
hostname ----> u will get this ---------->ip-172-31-44-207.ec2.internal
but id u type hostname in catalogue container ----> 02847a53fe2f ---> it shows container id as hostname 

Different hostname.

5. IPC Namespace :  IPC = Inter Process Communication.

Allows processes inside one container to communicate using shared memory, message queues, semaphores, while isolating them from IPC resources used by other containers.

Processes inside one container cannot access IPC resources from another container.

6. User Namespace :   Maps container users to different host users.
User Namespace isolates user and group IDs by mapping container users to different users on the host.

It isolates
User IDs (UID)
Group IDs (GID)

Example:
Inside container --->  root but
Host  --->  UID 1001

The container thinks it's running as root, but it can be mapped to an unprivileged user on the host for better security.

7. Cgroup Namespace
Cgroup Namespace isolates and exposes only the CPU, memory, and process limits assigned to that container instead of the host's full resource information. 
Related to resource control. 

It isolates
CPU limits
Memory limits
Resource usage information

This works together with Linux cgroups, which actually enforce the limits.

| Namespace | Isolates              |
| --------- | --------------------- |
| PID       | Processes             |
| Network   | IP, Ports, Interfaces |
| Mount     | Filesystem            |
| UTS       | Hostname              |
| IPC       | Process communication |

| Cgroup    | CPU/Memory limits     |


Interviewer: Why do we need namespaces in Docker?
"Docker containers share the host Linux kernel, so by default every process would be able to see all other processes, networks, filesystems, and host resources. Linux namespaces provide isolation by creating a separate view for each container. For example, a PID namespace isolates processes, a network namespace gives each container its own IP address and network stack, and a mount namespace gives each container its own filesystem view. This makes every container behave like an independent machine even though all containers share the same host kernel."

A container uses namespaces. Namespaces are a Linux kernel feature. Docker simply uses them to isolate containers.

Namespaces are Linux kernel features that provide isolation for containers. They create separate views of system resources such as processes, networking, filesystems, hostname, users, IPC, and resource information. Docker uses namespaces so that each container behaves like an independent machine while still sharing the host's Linux kernel.




Yes, by default every Docker container gets its own set of Linux namespaces. Docker creates separate namespaces for the container when it starts (unless you explicitly tell Docker to share a namespace).
Suppose you run two containers
docker run -d --name catalogue catalogue:v1
docker run -d --name mongodb mongodb:latest

Now Docker creates something like this: Every container gets

its own process list (PID Namespace)
its own network (Network Namespace)
its own filesystem view (Mount Namespace)
its own hostname (UTS Namespace)
its own IPC resources (IPC Namespace)

Does Docker create them manually ----> No.  Docker asks the Linux Kernel.  Ex: "Please create a new PID namespace."  Kernel creates it. ---> same for all 

What if there are 100 containers ----> Then approximately: 100 Containers in that we will have ---> PID namespace, Network Namespace, mount Namespace, UTS Namespace, and IPC Namespace and User NameSpace etc....

Instead :   Docker allows containers to share namespaces if you explicitly configure them.

Example :   docker run --network=host nginx
Here Docker does not create a separate Network Namespace. Instead, the container uses the host's network namespace.

Example :   docker run --pid=host nginx   ---> Now the container shares the host PID Namespace.


Interview Question
 Does every Docker container have all Linux namespaces?
"Yes, by default Docker creates separate Linux namespaces for every container, including PID, Network, Mount, UTS, IPC, and Cgroup namespaces. These namespaces provide isolation so each container has its own view of processes, networking, filesystem, hostname, and other resources. User namespaces are available as well, although they may not always be enabled depending on the Docker configuration. Docker can also be configured to share specific namespaces with the host, such as using --network=host or --pid=host, when isolation is intentionally reduced."



Namespaces are Linux kernel objects, not Docker objects.

Docker creates them, but Linux maintains them. Let's see how to check them.

Check all namespaces in container :
cmd :  lsns           --------> It lists all namespaces currently available on the Linux system.

Sample Output:

NS         TYPE   NPROCS   PID   USER   COMMAND
4026531836 pid       120     1   root   systemd
4026532440 net         5  1234   root   nginx
4026532441 mnt         5  1234   root   nginx
4026532442 uts         5  1234   root   nginx
4026532443 ipc         5  1234   root   nginx

| TYPE   | Meaning            |
| ------ | ------------------ |
| pid    | PID Namespace      |
| net    | Network Namespace  |
| mnt    | Mount Namespace    |
| uts    | Hostname Namespace |
| ipc    | IPC Namespace      |
| user   | User Namespace     |
| cgroup | Cgroup Namespace   |


Check a Specific Container :   docker inspect -f '{{.State.Pid}}' catalogue
To see All Namespaces
Every running process in Linux has a directory: :    /proc/<PID>/ns
This directory contains symbolic links to all the namespaces the process belongs to.

From Inside the Container :
commands:
docker exec -it catalogue bash
ls -l /proc/self/ns
self means the currently running process.
So this shows the namespaces of the process you're currently running inside the container.


Verify Individual Namespaces
PID Namespace :   
ps -ef   --->  You'll only see container processes.
Network Namespace
ip addr or ifconfig   ---> You'll see the container's network interfaces (typically eth0 and lo), not the host's.

UTS Namespace
hostname ---> Displays the container's hostname.

Mount Namespace
mount ---->  Shows the container's mounted filesystems.

IPC Namespace 
ipcs ---> Shows shared memory segments, message queues, and semaphores visible inside the container.

User Namespace
id ----> Displays the current user and group IDs.



Interview Question :  How do you verify that Docker has created separate namespaces?
"I first obtain the container's PID using docker inspect -f '{{.State.Pid}}' <container>. 
Then I inspect /proc/<PID>/ns on the host or /proc/self/ns from inside the container. 
These directories list the PID, Network, Mount, UTS, IPC, User, and Cgroup namespaces associated with the container's processes. 
I can also verify individual namespaces using commands like ps, ip addr, hostname, mount, and id."
