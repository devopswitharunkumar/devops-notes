Shell script disadvantages compared to Ansible :
----------------------------------------------------------------
1. Error handling and validation : 
Shell : You must manually check exit codes ($?) after individual commands run or use set -e.By default, a shell script keeps running even if line fails also we need check using exit status
Ansible : Ansible automatically stops a play if a module/role fails, logs errors like Ansible also tracks which hosts failed

2. Scalability issue : 
Shell : Hard to run manually in all servers by logging or lopping through arrays of ip's is complex  
Ansible : Ansible runs tasks parallelly in multiple servers. Control node uses SSH and  IP's mentioned in inventory file to login and execute tasks 2. You don't have to wait for Server 1 to finish before Server 2 starts.

3. Readability and maintenance : 
Shell : Complex logic(need to mention step by step) require unerstanding of linux and maintenance turns into hard 
Ansible : Ansible uses a declarative approach and Playbooks use clean, declarative English-like syntax

4. Cloud integration : 
Shell : Using shell to connect to external systems like aws or others requires AWS CLI commands and handling tokens is hard 
Ansible : Ansible interacts directly with Cloud APIs using Python SDKs behind the scenes, 

5. Security and secrets : 
Shell : Hardcodening like passwords and API tokens and others in script or passing them in CLI is not good practice 
Ansible : we have ansible vault to store passwords and Api tokens etc .. it provides AES-256 encryption..It secures sensitive files or variables, decrypting them only during runtime execution.

6. Idempotency : 
Shell : we need to check manually using if conditions or others.. there is no idempotency 
Ansible : Modules check the managed servers state first. If the configuration already matches the desired state, Ansible bypasses/ignores it.

Compared to shell scripting, Ansible provides better features like idempotency, inventory management, reusable roles, error handling, variables, templates, and easier management of large-scale environments.

Ansible :
------------
Ansible is an open-source agent-less configuration management tool used to configure servers, deploy aplications, and automate IT tasks.
Ansible is agentless automation tool, we don't need to install any additional software or agents on managed servers.
Ansible follows a push-based architecture where the control node(we need to install ansible package in this server) and connects to managed/target nodes using SSH for Linux or WinRM/Powershell for Windows, it automatically pushes the required modules, executes tasks defined in YAML playbooks on target nodes, collects the result, and removes temporary files in target servers.
It allows us to manage hundreds/thousands of servers from a single server(i.e.,controller node) we can login using SSH to hundreds of managed nodes/servers without manually logging into each server and perform tasks and required operations using SSH.
It is  idempotency : running the same automation script multiple times will produces the exact same result. if it already executed on server ansible notices and make no changes 

Core components are 
Inventory 	: A simple text file (in INI or YAML format) that lists the IP addresses or hostnames of the servers you want to manage. You can organize these servers into custom groups also if u want 
Modules  	: These are built-in standalone scripts designed to handle specific tasks, such as installing packages (apt, yum), managing services (service), or cloning repositories (git).
Playbooks	: The blueprints written in YAML syntax. Playbooks define the precise, ordered series of tasks that need to run across specific groups in your inventory.

Ansible follows push-based architecture. Managed nodes do not continuously check for changes. The control node initiates communication and pushes configurations whenever a playbook execution is triggered manually,or through CI/CD pipelines like Jenkins, or through scheduled automation(like crontab). There is no default polling interval because Ansible is agentless.

How it woks :
------------------
1)You run a playbook from the Control Node (Ex : ansible-playbook site.yml)
2)The Control Node wakes up and reads your ansibe.cfg, playbooks and inventory file to find the IP/hostname of the target nodes and replace dynamic values.
3)Ansible transforms your declarative YAML tasks into small, executable standalone scripts and wraps them into a ZIP-compressed Python file.
4)control node connect to those target nodes via SSH (for Linux) or WinRM (for Windows).
5)It copies the required modules (compressed zip Python scripts) over on the remote host's temporary directory directly (~/.ansible/tmp/).
6)The target node takes over, runs the pushed script using its local Python interpreter, determines the task state, and formats the output into a standardized JSON string.
7)Once execution done The remote host instantly deletes the temporary script file from ~/.ansible/tmp/, sends the JSON result payload back across the connection, and the Control Node prints the clean ok, changed, or failed output on your terminal.

By default Ansible follows push-based architecture where the control node connects to managed nodes through SSH and executes playbooks. However, Ansible also supports pull-based execution using ansible-pull. In this model, managed nodes have Ansible installed and periodically pull playbooks from a version control system like Git using cron or systemd timers and apply configurations locally.


| Push (Ansible)           					| Pull (Chef/Puppet)          |
| ------------------------ 					| ------------------------------- |
| Controller sends changes 		| Server fetches changes          |
| No agent                 					| Agent required                  |
| Uses SSH                 					| Uses agent communication        |
| Immediate execution      			| Scheduled execution      |
| Simple setup             					| More setup                      |
| Controller initiated     				| Node initiated                  |
| Good for deployments				| Good for continuous enforcement |

diff:
Ansible follows push based architecture by default. The control node connects to managed nodes using SSH and pushes modules/configurations so that we can execute playbooks. It does not require agents on target machines. 
In pull based architecture, in node server/target servers we need to install or run agents and those agents periodically connect to a controller server and pull their desired configuration, like Puppet or Chef. 

Push is better for immediate automation and deployments, while pull is useful for continuous configuration enforcement at very large scale

"Ansible control node connects to managed nodes using SSH. We define target servers in inventory, configure authentication using SSH keys or passwords, and Ansible pushes modules to target nodes, executes them, collects output, and removes temporary files in target nodes"

Addressing "Configuration Drift"
• In a Pull-based system, if someone manually edits a file on a server, the local agent will naturally catch it and overwrite it during its next automated check-in cycle.
• In a Push-based system (Ansible), you have to run your playbook again to correct that drift. However, as you mentioned earlier, you can use Ansible-Pull or hook Ansible up to a CI/CD pipeline (like GitLab CI or Jenkins) to achieve a similar automated enforcement effect.

- name: Use system facts to make decisions
  hosts: all
  gather_facts: true  # 👈 This defaults to true, turning on the automatic data collection
  tasks:
    - name: Show the operating system family discovered by Ansible
      ansible.builtin.debug:
        msg: "This server belongs to the {{ ansible_facts['os_family'] }} family."

    - name: Install Apache on RedHat/CentOS systems
      ansible.builtin.dnf:
        name: httpd
        state: present
      when: ansible_facts['os_family'] == "RedHat"  # 👈 Conditional check

    - name: Install Apache on Debian/Ubuntu systems
      ansible.builtin.apt:
        name: apache2
        state: present
      when: ansible_facts['os_family'] == "Debian"  # 👈 Conditional check
	  
🗂️ The Most Common Built-In Facts (Categorized)

🐧 1. Operating System & Distribution Facts ---> Used to write conditionals (when:) to handle different Linux flavors:
• ansible_facts['os_family'] – Major OS family (e.g., "RedHat", "Debian", "Windows").
• ansible_facts['distribution'] – Specific OS name (e.g., "CentOS", "Ubuntu", "Amazon").
• ansible_facts['distribution_version'] – The exact version number (e.g., "9.4", "22.04").
• ansible_facts['architecture'] – CPU architecture (e.g., "x86_64", "aarch64").

🌐 2. Networking & IP Address Facts
Used to bind configuration files to the correct server interfaces:
• ansible_facts['default_ipv4']['address'] – The primary IPv4 address used to route internet traffic.
• ansible_facts['all_ipv4_addresses'] – A list containing every IPv4 address bound to the host.
• ansible_facts['hostname'] – The short hostname of the server.
• ansible_facts['fqdn'] – The Fully Qualified Domain Name of the machine.
• ansible_facts['interfaces'] – A list of all network interface names (e.g., ["eth0", "lo"]).

🎛️ 3. Hardware & Memory Facts
Used to dynamically scale resource pools (like allocating RAM limits to a database):
• ansible_facts['memtotal_mb'] – Total physical RAM available on the server in Megabytes.
• ansible_facts['memfree_mb'] – Currently unallocated physical RAM available.
• ansible_facts['processor_vcpus'] – The total number of virtual CPU cores available.
• ansible_facts['mounts'] – A nested list detailing disk space, partitions, and paths (e.g., free space on /).

🐍 4. Environment & System Path Facts
• ansible_facts['env'] – A map containing the remote user's environment variables (like $PATH or $HOME).
• ansible_facts['python_version'] – The exact Python version running on the target machine.
• ansible_facts['date_time'] – The remote server's current date, time, and timezone tracking strings.

📝 How to access them cleanly in a Playbook
- name: Print out useful host facts
  hosts: all
  tasks:
    - name: Show OS and IP info
      ansible.builtin.debug:
        msg: "This server is running {{ ansible_facts['distribution'] }} and its main IP is {{ ansible_facts['default_ipv4']['address'] }}"

	  
11) Block level variables 
Block-level variables allow you to apply specific variables to a grouped collection of tasks(like for grou of tasks insted of applying them for all tasks) within your playbook rather than defining them for just a single task or the entire play.

- name: Understanding Block Level Variables
  hosts: localhost
  gather_facts: false
  
  # 1. Playbook Level Variable
  vars:
    environment_type: "production"
    app_port: 80

  tasks:
    # This task uses the global playbook variable
    - name: Task outside the block
      ansible.builtin.debug:
        msg: "The global environment is {{ environment_type }} on port {{ app_port }}"

 # 2. Block Level Grouping
    - name: Staging Deployment Block
      vars:
        environment_type: "staging"  # 👈 Overrides "production" for this block only
        db_name: "stage_db"          # 👈 New variable active only inside this block
      block:
        - name: First task inside the block
          ansible.builtin.debug:
            msg: "Deploying to {{ environment_type }} using database {{ db_name }} on port {{ app_port }}"

        - name: Second task inside the block (with its own task variable)
          vars:
            app_port: 8080           # 👈 Task level overrides block level
          ansible.builtin.debug:
            msg: "Deploying to {{ environment_type }} using database {{ db_name }} on port {{ app_port }}"

----------------------------
Variable precedence means the strict order of priority Ansible uses to decide which variable wins when the same variable name is defined in multiple places

If same variable exists in multiple places: below is the preference 

Prefernce of a taking variable in ansible(it will take the data either from one of them based on prefernce one by one it will check and take where ever data present)

variable precedence:
1. Extra vars (-e) ---> 2. Task vars ---> 3. Block vars ---> 4. Role vars ---> 5. vars_files ---> 6. Play vars / vars_prompt ---> 7. host_vars ---> 8. group_vars ---> 9. Inventory variables ---> 10. Role defaults

Ansible supports variables from multiple locations like inventory, group_vars, host_vars, playbooks, vars files, roles, prompts, and command line arguments. If the same variable exists in multiple places, Ansible follows variable precedence rules. Extra variables passed using -e have the highest priority, while role defaults have the lowest priority.

Variables in Ansible are used to make playbooks reusable and dynamic by avoiding hardcoded values. Variables can be defined at playbook, inventory, host, group, role, and command levels. Ansible uses Jinja2 syntax to access variables. We commonly use variables for environment-specific configurations, templates, deployments, and storing task output using register.

Conditions allow Ansible to execute tasks only when a specific criteria is satisfied and Conditions are implemented using the when keyword.
if condition true  --> Execute the task and
if condition false --> Skip the task

syntax --> when: condition

---------------

  hosts: web
  become: yes

    yum:
      name: nginx
      state: present
    when: install_nginx          --->  install_nginx: true then only  task will be executed first condition will be checked by ansible based on the result tasks will be executed or skipped decided
 
it will check when condition first --> if install_nginx is set to true then yum task will run else skipped

prod == prod so task execute if we give environment: dev so dev == prod it is false so skip the task

Register Variable in Ansible:
------------------------------------
register is used to capture and store the output/result of a task into a variable. This registered variable can be reused in later tasks for conditions, debugging, validations, and decision making.

Task executes ----> Output generated ----> register variable stores generated output ----> Use that output in next tasks

Why do we use register?

Main uses:
Store command output
Use output in conditions (when) by using register variable
Debug/print values
Validate/check task result
Control next task execution (ex register: count  in next condition when: condition.rc == "0"  if value 0 executes the tasks or else skipped)
Troubleshooting

ex:
- name: Check uptime
  ansible.builtin.command: uptime
  register: server_uptime
  
server_uptime ---> contains the complete task result.

in next task:
- name: Print uptime
  ansible.builtin.debug:
    msg: "{{ server_uptime.stdout }}"
	
Output:
10:25:30 up 5 days

What does register store?

Example: register: result

creates a dictionary:

  stdout:

  stderr:
    error output
  rc:
    return code
  changed:
    true/false
  failed:
    true/false
  start:
    start time
  end:
    end time

ROLES :
----------
Ansible roles provides a way to organize playbooks into a standard reusable folder structure. Instead of writing in single playbook roles separate tasks, vars, files, templates, handlers, and configurations into different folders. This improves code reusability, readability, and maintainability across multiple environments and avoids code duplication also 

Instead of writing everything in a big single YAML file, roles allow us to seperate automation logic into tasks,vars,files,templates,handlers,defaults,meta etc into separate folders or smaller reusable components.


in every directory main.yaml will be called directly by ansible

DRY Principal --> dont repeat your self

Structure:
-------------

roles/
    appname/               # this hierarchy represents a "role"	i.e., role name
        tasks/            #
            main.yml      #  <-- tasks file can include smaller files if warranted
        handlers/         #
            main.yml      #  <-- handlers file
        templates/        #  <-- files for use with the template resource
            ntp.conf.j2   #  <------- templates end in .j2
        files/            #
            bar.txt       #  <-- files for use with the copy resource
            foo.sh        #  <-- script files for use with the script resource
        vars/             #
            main.yml      #  <-- variables associated with this role
        defaults/         #
            main.yml      #  <-- default lower priority variables for this role
        meta/             #
            main.yml      #  <-- role dependencies
        library/          # roles can also include custom modules
        module_utils/     # roles can also include custom module_utils
        lookup_plugins/   # or other types of plugins, like lookup in this case

    webtier/              # same kind of structure as "common" was above, done for the webtier role
    monitoring/           # ""
    fooapp/               # ""

templates:
--------------
Templates in Ansible are used to create dynamic configuration files by replacing variables at runtime. Ansible uses the Jinja2 templating engine and template files usually have .j2 extension.

Instead of maintaining multiple configuration files for different environments like dev, test, and prod, we maintain a single template file and pass environment-specific values using variables(diff variables.yaml files for diff env like varibles-prod.yaml , variables-dev.yaml and same for inventory file).

Jinja2 :
Jinja2 is a highly popular templating engine for Python that is natively built into Ansible
Jinja2 is an interpretation engine that allows us to convert static configuration files into dynamic blueprints []. By using variables, loops, and conditional statements inside text files, Jinja2 evaluates and transforms templates on the fly before delivering the final, customized file to the target servers.

vars : used in shipping module
-------
vars folder in Ansible roles is used to store role specific variables and use those variable keys/names in tasks, templates, handlers, etc.(vars folder main.yaml)
i.e., if variables are used in only particular role we can create vars folder in that role(ex: shipping component) and mention them in main.yaml (role specific)
but if those variables are required for multiple module we keep them in variables.yaml it is outside of roles folder 

Instead of hardcoding values inside tasks, we keep them in vars folder in particular role 
It improves:
reusability
easy maintainability
avoiding duplicate values

ex: vars folder/main.yaml
MONGODB_HOST: mongodb.devopswitharun.online
APP_USER: roboshop
APP_LOCATION: /app
DOMAIN_NAME: devopswitharun.online

In Ansible roles, vars directory stores variables specific to that role. We keep values like application user, installation paths, package names, ports, and endpoints inside vars/main.yml instead of hardcoding them in tasks. This makes roles reusable and easier to maintain. For configurable values we prefer defaults, and for role-specific fixed values we use vars.

| defaults                            		| vars                    |
| -----------------------------------  | ----------------------- |
| Low priority                        	| High priority           |
| Easily overridden                   | Hard to override        |
| Default values                      | Fixed role values       |
| Recommended for configurable values | Internal role variables |

Example:
defaults/main.yml
PORT: 8080

Meaning: "I suggest this value, but you can change"
Override: ansible-playbook main.yml -e PORT=9090

vars/main.yml
JAVA_VERSION: 17
Meaning: "This role expects this value"

In our RoboShop project, we used the vars directory inside roles to maintain role-specific variables instead of hardcoding values. Variables like application paths, package versions, service names, and endpoints were stored in vars/main.yml and reused in tasks and templates. For values shared between multiple roles or environments, we used group_vars. For configurable default values, we used defaults.

ansible.builtin.import_role (Static)  --> this module pulls an entire role and it's structure contains(all folders like tasks, variables, handlers , templates etc.. ) into your play statically.
Ansible process this statement before the original (where we write import role)playbook actually starts running on your servers basically it treats like you copied and pasted them directly into your main playbook 



Best Used For --> Standard, predictable role deployment where you want the full role execution lifecycle (including its vars/ and handlers/) loaded immediately.
key behaviors:
1 --> Variables defined inside the role’s(import_role mentioned module) vars/main.yml are loaded immediately
2 --> You cannot use a standard loop (loop or with_items) on an import_role statement
3 --> If you add a when condition to import_role, Ansible applies that condition to every single individual task inside the role.

Ex: 
- name: Statically import the webserver role
  ansible.builtin.import_role:
    name: nginx_webserver
  when: environment == "production"

ansible.builtin.include_tasks (Dynamic) --> This module pulls in a specific list of tasks from a file dynamically
Ansible processes this statement at runtime (exactly when execution hits that specific step). It does not know what tasks are inside the file until it actually reads it during the play
--> You can loop over include_tasks. If you pass a list of 3 items, it will run that entire task file 3 separate times dynamically.
--> You can use runtime facts to choose which file to load (e.g., file: "{{ ansible_os_family }}.yml"). dynamic file names 
-->  If the when condition evaluates to false, Ansible skips the include statement entirely without reading the tasks inside
Ex:
- name: Dynamically include OS-specific tasks
  ansible.builtin.include_tasks:
    file: "{{ ansible_os_family }}.yml"  # e.g., RedHat.yml or Debian.yml

Ansibe vault :
------------------
Ansible Vault is a feature that allows u to encrypt sensitive data --> such as database passwords, API keys, tokens, SSL certificates and secrets directly inside Ansible projects.
Instead of hardcodening them as plain text credentials in playbooks, we encrypt them using Vault and Ansible decrypts them only when running the playbook.

What should be encrypted?
like --> Database passwords,SSH passwords,API tokens,Cloud credentials,Private keys,Application secrets,Certificates
so  secrets --> encrypt with vault --> commit encrypted file to git 

Ex:
without vault:  --> Anyone with repo access can see the secrets.

with vault: ---> Encrypted data.
$ANSIBLE_VAULT;1.1;AES256

6638646534383832
3532326639636134
6432663632366535

Vault commands:
----------------------
1. ansible-vault create <filename>.yaml      		  --> create vault  --> it asks to set new password 
2. ansible-vault view <filename>.yaml         		  --> view encrypted file contents
3. ansible-vault edit <filename>.yaml                    --> It decrypts the present content and opens the file with vim or nano and after edit it will re-encrypts when u save the data and close

6. ansible-vault rekey <filename>.yaml                 --> it allows u to change the master key vault password

Dynameic inventory :
----------------------------
Dynamic Inventory automatically fetches already created server details from external sources like AWS, Azure, GCP, Kubernetes, etc., instead of manually maintaining inventory.ini files.It dynamically discovers hosts at runtime.

Why do we need Dynamic Inventory?
Ex: In your RoboShop project currently we use static inventory and This works for small projects. But in companies there will be big billion days at that time autoscaling create resources/servers so to fecth the server ips and configure them needs dynamic inventory
Dynamic inventory only fetches existing ec2 servers/resources ip address and connect with them and gives them to Ansible for configuration. It does not create EC2 or Route53.
Dynamic inventory does not provision infrastructure. It queries cloud providers like AWS and fetches existing resources dynamically based on metadata like tags. Once hosts are discovered, Ansible executes roles/playbooks on those instances. Infrastructure provisioning is usually handled separately using Terraform.

Terraform = BUILD/CREATE servers in aws 
Dynamic Inventory = FIND server ip's and handover them to ansible
Ansible Roles = CONFIGURE servers

The Exception: When does the Control Node execute a task?
By default, tasks run on the managed nodes, but you can explicitly force a task to execute on the control node using two advanced keywords:
• local_action: Forces a specific step to run locally on the control node.
• delegate_to: localhost: Tells Ansible to execute the module on the control node instead of the target server.

By default, Ansible copies the converted Python script file over SSH, executes it, and deletes it on target servers. However, in large production environments, this disk I/O slows things down. 
To optimize this, we enable SSH Pipelining in ansible.cfg. Pipelining executes the Python modules directly in the target server's system memory(RAM) over the SSH stdin pipe without them ever writing an actual script file to the remote disk storage, heavily cutting down network overhead and execution time.
Ex:
[ssh_connection]
pipelining = True

SSH Pipelining

Without Pipelining (Default):
Opens multiple SSH connections per task (one to copy the file, one to run it).
Writes and deletes files constantly on the target machine's disk
Slower (noticeable delays on playbooks with hundreds of tasks).

Those script files will be available at task execution time in memory and Ansible controller node converts ansible modules/playbooks into python scripts and opens SSH connection and transfer the scripts instead of saving that stream as a file SSH daemon on the target server passes the raw script data directly into the standard input (stdin) of the Python interpreter running in memory and 
The Python interpreter loads the script string into a small buffer in the server's RAM and executes it instantly.	
As soon as the task finishes running and sends its results and python process closes and OS cleans up 

With Pipelining
Opens only one connection to stream and execute the code.
Zero disk writes. Everything happens instantly inside the RAM.
Significantly faster (can cut execution times by 30% to 50%).

.retry file :
--------------
A .retry file contains the list of hostnames of servers where an Ansible playbook failed, so it allows you to identify which hosts may need another run the playbook against those hosts rather than all inventory hosts.
Ex:
I have list of 4 servers in an inventory file to runn playbook in all servers and i ran a --> ansible-playbook -i inventory.ini deploy.yml
Now the result --> playbook executed successfully in server1 , server2 and server4 but in server 3 playbook execution failed --- in this case ansible create a file such as deploy.retry and which contains server hostsname whre execution failed 

deploy.retry  file content 										filename would be  --- <playbook name>.retry 
server 3

you can run the that retry file alone another time 
ansible-playbook -i inventory.ini deploy.yml --limit @deploy.retry

--limit @deploy.retry limits execution to the hosts listed in that retry file.

Important: Retry-file generation is configuration-dependent and is disabled by default in modern Ansible configurations. You can enable it with: mention this in inventory file 
[defaults]
retry_files_enabled = True

forks :
--------
forks controls how many hosts Ansible can work on concurrently. the default is 5 hosts 

Ex:  Suppose you need to install an application on 20 EC2 instances. Mention this in ansible.cfg file 
[defaults]
forks = 5

or 	at runtime 
ansible-playbook -i inventory.ini deploy.yml -f 10											#-f == forks 

Ansible can execute tasks across up to five hosts concurrently by default,It processes additional hosts as execution capacity becomes available.
