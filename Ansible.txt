Ansible:
-----------
Ansible is an open-source, agentless automation and configuration management tool used to configure servers, deploy aplications, and automate IT tasks.
It allows us to manage hundreds/thousands of servers from a single server(i.e.,controller node) we can login hundreds of managed nodes/servers without manually logging into each managed  server and perform tasks and required operations.
Ansible follows a push-based architecture where the control node(we need to install ansible package in this server) connects to managed nodes using SSH for Linux or WinRM for Windows, pushes the required modules, executes tasks defined in YAML playbooks, collects the result, and removes temporary files.
Since Ansible is agentless, we don't need to install any additional software or agents on managed servers.
Compared to shell scripting, Ansible provides better features like idempotency, inventory management, reusable roles, error handling, variables, templates, and easier management of large-scale environments.

We used inventories to manage servers, variables for environment-specific configurations, templates for dynamic configuration files, handlers for service restarts, and Ansible Vault/secret management for sensitive information.
This helped us achieve consistent deployments across multiple environments like dev, QA, and production.

The control node reads inventory and YAML playbooks, converts tasks into modules, transfers those modules to managed nodes, executes them, collects the results, and removes temporary files after execution.

Ansible follows push-based architecture. Managed nodes do not continuously check for changes. The control node initiates communication and pushes configurations whenever a playbook execution is triggered manually,or through CI/CD pipelines like Jenkins, or through scheduled automation(like crontab). There is no default polling interval because Ansible is agentless.

How it woks:
------------
1)You run a playbook from the Control Node (ansible-playbook site.yml).
2)The Control Node wakes up and reads your ansibe.cfg, playbooks and inventory file to find the IP/hostname of the target nodes.
3)It connects to those target nodes via SSH (for Linux) or WinRM (for Windows).
4)It copies the required Ansible modules (Python scripts) over to the remote host's temporary directory (~/.ansible/tmp/).
5)It executes the modules/tasks on the remote host, reads the JSON return payload i.e., takes the result, and cleans up the temporary files.

PULL based 
----------------
Target servers regularly connect to a contol/central server and pull their required configurations at every interval like ex 30 mins / 1 hr etc.
Servers decide WHEN to check updates

In pull-based configuration management, managed nodes have an agent installed. The agent(installed in managed node) periodically contacts the central/master server, checks if there are any configuration changes, downloads the required configuration, and applies it locally in managed nodes .
in central server --> Stores desired state

ex tools: puppet and chef

By default Ansible follows push-based architecture where the control node connects to managed nodes through SSH and executes playbooks. However, Ansible also supports pull-based execution using ansible-pull. In this model, managed nodes have Ansible installed and periodically pull playbooks from a version control system like Git using cron or systemd timers and apply configurations locally.


| Push (Ansible)           					| Pull (Chef/Puppet)          |
| ------------------------ 					| ------------------------------- |
| Controller sends changes 		| Server fetches changes          |
| No agent                 					| Agent required                  |
| Uses SSH                 					| Uses agent communication        |
| Immediate execution      			| Scheduled execution      |
| Simple setup             					| More setup                      |
| Controller initiated     				| Node initiated                  |
| Good for deployments				| Good for continuous enforcement |

diff:
Ansible follows push based architecture by default. The control node connects to managed nodes using SSH and pushes modules/configurations so that we can execute playbooks. It does not require agents on target machines. 
In pull based architecture, in node server/target servers we need to install or run agents and those agents periodically connect to a controller server and pull their desired configuration, like Puppet or Chef. 

Push is better for immediate automation and deployments, while pull is useful for continuous configuration enforcement at very large scale

A playbook defines the desired state of servers and tells Ansible what actions need to be performed or tells Ansible what has to execute on target servers.

Register Variable in Ansible:
------------------------------------
register is used to capture and store the output/result of a task into a variable. This registered variable can be reused in later tasks for conditions, debugging, validations, and decision making.

Task executes ----> Output generated ----> register variable stores generated output ----> Use that output in next tasks

Why do we use register?

Main uses:
Store command output
Use output in conditions (when) by using register variable
Debug/print values
Validate/check task result
Control next task execution (ex register: count  in next condition when: condition.rc == "0"  if value 0 executes the tasks or else skipped)
Troubleshooting

ex:
- name: Check uptime
  ansible.builtin.command: uptime
  register: server_uptime
  
server_uptime ---> contains the complete task result.

in next task:
- name: Print uptime
  ansible.builtin.debug:
    msg: "{{ server_uptime.stdout }}"
	
Output:
10:25:30 up 5 days

What does register store?

Example: register: result

creates a dictionary:
result:

  stderr:
    error output
  rc:
    return code
  changed:
    true/false
  failed:
    true/false
  start:
    start time
  end:
    end time

Ansible roles provide a reusable directory structure to organize automation code. Roles separate tasks, variables, files, templates, handlers, and configurations into different folders. This improves code reusability, readability, and maintainability across multiple environments.

Instead of writing one big playbook YAML file, roles allow us to split automation logic into tasks,variables,files,templates,handlers,defaults,meta etc into separate folders or smaller reusable components.

or 
Ansible roles provide a reusable directory structure to organize automation code. Roles separate tasks, variables, templates, files, and handlers, which improves reusability and maintainability. We use roles to avoid duplicate code and standardize configuration management across multiple environments.

in every directory main.yam will be called directly by ansible

DRY Principal --> dont repeat your self

roles/
    common/               # this hierarchy represents a "role"
        tasks/            #
            main.yml      #  <-- tasks file can include smaller files if warranted
        handlers/         #
            main.yml      #  <-- handlers file
        templates/        #  <-- files for use with the template resource
            ntp.conf.j2   #  <------- templates end in .j2
        files/            #
            bar.txt       #  <-- files for use with the copy resource
            foo.sh        #  <-- script files for use with the script resource
        vars/             #
            main.yml      #  <-- variables associated with this role
        defaults/         #
            main.yml      #  <-- default lower priority variables for this role
        meta/             #
            main.yml      #  <-- role dependencies
        library/          # roles can also include custom modules
        module_utils/     # roles can also include custom module_utils
        lookup_plugins/   # or other types of plugins, like lookup in this case

    webtier/              # same kind of structure as "common" was above, done for the webtier role
    monitoring/           # ""
    fooapp/               # ""

In Ansible roles, vars directory stores variables specific to that role. We keep values like application user, installation paths, package names, ports, and endpoints inside vars/main.yml instead of hardcoding them in tasks. This makes roles reusable and easier to maintain. For configurable values we prefer defaults, and for role-specific fixed values we use vars.

| defaults                            		| vars                    |
| -----------------------------------  | ----------------------- |
| Low priority                        	| High priority           |
| Easily overridden                   | Hard to override        |
| Default values                      | Fixed role values       |
| Recommended for configurable values | Internal role variables |

vars/main.yml

Meaning: "This role expects this value"

In our RoboShop project, we used the vars directory inside roles to maintain role-specific variables instead of hardcoding values. Variables like application paths, package versions, service names, and endpoints were stored in vars/main.yml and reused in tasks and templates. For values shared between multiple roles or environments, we used group_vars. For configurable default values, we used defaults.

Dynamic Inventory automatically fetches server details from external sources like AWS, Azure, GCP, Kubernetes, etc., instead of manually maintaining inventory.ini files.It dynamically discovers hosts at runtime.

Why do we need Dynamic Inventory?
ex: In your RoboShop project currently you use static inventory and This works for small projects.
but in companies there will be autoscaling at the time of big billion days autoscaling create resources to fecth the server ips and configure them needs dynamic inventory
Dynamic inventory only fetches existing ec2 servers/resources ip address and connect with them and gives them to Ansible for configuration. It does not create EC2 or Route53.
Dynamic inventory does not provision infrastructure. It queries cloud providers like AWS and fetches existing resources dynamically based on metadata like tags. Once hosts are discovered, Ansible executes roles/playbooks on those instances. Infrastructure provisioning is usually handled separately using Terraform.

Terraform = BUILD/CREATE servers in aws 

Dynamic Inventory = FIND server ip's and handover them to ansible

Ansible Roles = CONFIGURE servers

In our project we used Ansible dynamic inventory to automatically discover cloud resources instead of maintaining static inventory files. For AWS, we used the aws_ec2 inventory plugin, which fetches EC2 instances based on tags and groups them dynamically. This helped us handle auto scaling environments because newly created instances were automatically included during playbook execution.


Setup AWS dynamic inventory:
1)Install collection
ansible-galaxy collection install amazon.aws
2)Install boto libraries
pip3 install boto3 botocore           --> Because Ansible(uses python in background install python also ) and it uses boto3 and botocore to connect/talk to aws.
Step 3: Create inventory file
Instead of --> inventory.ini
Create: aws_ec2.yaml     or web.aws_ec2.yaml for web group of hosts 

content in file:
-------------------
plugin: amazon.aws.aws_ec2            --> Uses AWS EC2 inventory plugin. 
regions:
- us-east-1                                             --> Search EC2 in this region.
keyed_groups:
- key: tags.Component
  prefix: ""
filters:
  instance-state-name: running		  -->   Only running servers.Stopped servers ignored.			
compose:
  ansible_host: private_ip_address   --> Connect using private IP.
   
 run ansible-inventory -i aws_ec2.yaml --graph
 
 for this no inventory.ini needed 
 
 in ansible.cfg we can give like 
 
 [defaults]
inventory=aws_ec2.yaml

Real project usage  
Terraform --> creates EC2 with Tags --> AWS Dynamic Inventory --> finds/fetches servers --> Ansible Roles do --> Configure applications

dynamic inventory example for our roboshop project
Yes 👍. For your RoboShop project, because you already created all EC2 instances manually, you only need to replace static inventory.ini with AWS dynamic inventory.

No need to touch your roles (mongodb, catalogue, cart, web etc.). Only inventory part changes.

Your current flow:

Step 1: Add tags to your existing EC2 instances

Go AWS Console:

EC2 → Instance → Tags

Add:

mongodb EC2
Key: Component
Value: mongodb
catalogue EC2
Key: Component
Value: catalogue
web EC2
Key: Component
Value: web

Like this for all:

mongodb   Component=mongodb
redis     Component=redis
mysql     Component=mysql
rabbitmq  Component=rabbitmq
catalogue Component=catalogue
user      Component=user
cart      Component=cart
shipping  Component=shipping
payment   Component=payment
web       Component=web
Step 2: Install AWS inventory requirements

On Ansible controller:

ansible-galaxy collection install amazon.aws

Install boto:

pip3 install boto3 botocore
Step 3: Create dynamic inventory file

Remove dependency on:

inventory.ini ❌

Create:

vi aws_ec2.yaml

Add:

plugin: amazon.aws.aws_ec2

regions:
- us-east-1

filters:
  instance-state-name: running

keyed_groups:
- key: tags.Component
  prefix: ""

compose:
  ansible_host: private_ip_address
Step 4: Check AWS permissions

Your Ansible controller needs permission:

ec2:DescribeInstances

If controller is EC2, attach IAM role.

Example policy:

{
 "Effect": "Allow",
 "Action": [
   "ec2:DescribeInstances"
 ],
 "Resource": "*"
}
Step 5: Test dynamic inventory

Run:

ansible-inventory -i aws_ec2.yaml --graph

Step 6: Your main.yaml remains SAME

No change.

Your current:
