Terraform :	
---------------
Terraform is an open-source Infrastructure as a Code (IaC) tool developed by HashiCorp. It is used to provision, manage, and automate and destroy cloud resources using declarative configuration files(.tf files) written in HCL (HashiCorp Configuration Language).
Terraform supports multiple providers like AWS, Azure, GCP, Kubernetes, etc.

Project-Based Interview Answer (Recommended)
-----------------------------------------------------------------
In our project, we used Terraform to provision and manage AWS infrastructure such as EC2 instances, Route53 records, Security Groups, IAM Roles, and S3 backends. 
We used reusable modules, remote state with S3 and DynamoDB, and environment-specific tfvars files to manage Dev and Production like multiple environments. 
This helped us automate infrastructure provisioning, maintain consistency across environments, and support version-controlled infrastructure deployments.

3) Declarative way

4) State Management 
Terraform state is a file that stores metadata(info), resource IDs, and dependencies for all resources created and managed by Terraform(when u run apply cmd).It is Terraform's last known recorded state of infrastructure. State file is not exactly current cloud resources running state always. 
File name --> terraform.tfstate
It tracks the current state of infrastructure present in aws and allowing to understand terraform what resources are currently available so based on that data it compares and decides to create,update or delete the infra 

When u run terraform plan or apply it automatically triggers a background state refresh for comparision 
Desired state(.tf files) <----> current known state (.tfstate file) + Aws live resources data created by terraform <----> based on the comparision it decides to create or update or delete the infra 

How it queries the aws live infra running ?
It opens the existing state file and reads the resource id's --> send request or passes these id's to provider plugin --> Provider Plugin Converts Code into API Calls(The provider translates Terraform's request into the exact secure HTTPS API endpoints required by AWS) -->
Example: For an EC2 instance, the provider runs an AWS API command equivalent to DescribeInstances(InstanceIds=['i-0789xyz']).
AWS authenticates your request using your local AWS credentials (IAM role, environment variables, or AWS CLI profile). If approved aws queries backend infra and returns and data JSON payload back to terraform ---> Terraform stores this live data in temporary memory.  --> It compares this actual state against your desired .tf files


1. When you run terraform plan

1. Terraform loads your local .tf files and reads the existing .tfstate file.
2. It extracts the resource IDs (like i-0789xyz) from the state file.
3. It passes these IDs to the AWS Provider Plugin.
4. The plugin calls the AWS API (e.g., DescribeInstances) using your local credentials & Ask the AWS provider to refresh the resource's current attributes using AWS APIs.
5. AWS returns the current infrastructure data as a JSON payload.
6. In-Memory Save: Terraform stores this fresh payload in its temporary runtime memory.
7. The Comparison: It compares the Desired Code (.tf) vs. the Stale State File (.tfstate) vs. the Live Memory Data (AWS).
8. It shows you the diff output on your terminal screen (+, ~, -). The execution stops here. The actual state file on your disk is not modified yet.

2. When you run terraform apply

1. If you run terraform apply directly, it performs the exact same steps (1 to 7) listed above to refresh its memory and show you the plan preview.
2. The Prompt: It asks you: "Do you want to perform these actions? (yes/no)".
3. The Execution: If you type yes, the provider plugin sends the Write/Modify/Create API calls (like RunInstances or TerminateInstances) to AWS.
4. The Disk Write: Once AWS completes the changes and returns a success payload, Terraform takes that new live data from memory and permanently writes it down to your .tfstate file on the disk.


Ex: Terraform Compares b/w ---> Terraform Code i.e,. desired state (.tf configuration files) VS State File (.tfstate file)+ Real AWS (running resources in ex aws )
Then decides                      ---> Create?,Update?,Delete? resources 
Example:
1)In code we gave   EC2 = t3.small
2)in state file            EC2 = t3.micro       --> already created and running instance type info it is running with t3.micro
based on the state file info it will decide to update because both are diff values so it will update the resource

Configuration Drift :
When you run terraform plan or terraform apply , Terraform automatically first performs a state refresh (terraform refresh) in background by querying the actual AWS API to see actual status of cloud resorces if anyone manually changed things in the aws console.if changed the background refresh detects this variance (called Configuration Drift). It updates its temporary memory so it can compare your code against reality and then Terraform compares the desired configuration(.tf files) with the state file(.tfstate file) and actual cloud infrastructure(aws console infra), then decides whether resources need to be created, updated, or deleted. 
In production, we store state remotely using backends like AWS S3 with DynamoDB locking for collaboration.

Terraform automatically Reads existing state(.tfstate file) then Compares current state file (tfstate file + aws existing resource running) vs desired state(.tf files) then it decides to create/update/delete resources to Achieves desired state	

How it interacts with the Remote Backend If you are using a secure remote backend like AWS S3 with DynamoDB locking:
Acquires the Lock 											--> Terraform talks to DynamoDB to lock your state so no other engineer or CI/CD pipeline can run a build at the same time.
Downloads the State										--> It pulls the latest terraform.tfstate file from your S3 bucket into memory.
Performs the Refresh state	 						--> It runs the API checks against live AWS to verify if the resources in the S3 state file match real life.
compare and apply and Releases the Lock --> Once your plan or apply finishes, it uploads the updated state back to S3 and unlocks DynamoDB.

6) Dependency Management 
Terraform automatically understands dependencies. When one resource depends on another resource or attribute,Terraform automatically understands the relationship between resources and creates, updates, or deletes them in the correct order.

1. Automatic Resource Ordering : Terraform automatically constructs an internal === Directed Acyclic Graph (DAG) === to map out your infrastructure. It uses this graph to analyze your code, determine exactly which resources depend on others, and execute creation, updates, or deletions in the precise logical order required by the cloud provider.
2. Parallel Execution: If resources have no dependencies between each other (e.g., creating two completely separate S3 buckets), Terraform provisions them simultaneously in parallel to speed up deployment times.

In real infrastructure, some resources depend on others Terraform automatically handles this.

1. Implicit Dependency :  
An Implicit Dependency means you do not have to write any special configuration parameters to tell Terraform which resource to build first. Terraform automatically detects the relationship when one resource references an attribute (like an .id or .arn) of another resource inside its configuration block
Example : 
-------------
# 1. This resource defines the Security Group
resource "aws_security_group" "web_sg" {
  name        = "web-server-sg"
  description = "Allow HTTP traffic"
}

# 2. This resource defines the EC2 Instance
resource "aws_instance" "web_server" {
  ami           = "ami-12345"
  instance_type = "t3.micro"
  
  # LINKING HAPPENS HERE: 
  vpc_security_group_ids = [ aws_security_group.web_sg.id ] 								# this is called implict dependency because u referenced the ids of sg so SG will be created first then ec2 
}

Terraform understands: First create SG --> then create EC2 --> Because ec2 depends on SG id's 

During Destroy
Terraform follows reverse order ----> Delete EC2 --> Delete SG
Because EC2 cannot be removed while sg exists.

2. Explicit Dependency : we explicitly mention in .tf files this resource dependent on other resource.. create this first and wait for that to complete & then run dependent resource
Ex :   depends_on =  aws_security_group.web_sg

7)Modules
A module is a reusable collections of Terraform configuration files(.tf files) grouped together in a single directory and they are used to organize and reuse infrastructure code.
Instead of writing the same code multiple times for different projects/environments, we create a module once and call it wherever required with diff varibles file (like ex for prod we have  variables-prod.tfvars and for dev we have variables-dev.tfvars like this)

Types of modules:
1)Root Modules --> The primary directory containing .tf files where you run the core commands (i.e.,main.tf,variables.tf,provider.tf) This is root module.
2)Child Module  --> Any external module that is called inside your root module’s configuration file using a module block. Modules called by root module. (i.e.,modules/ec2,modules/vpc,modules/rds)

interview answer:
Terraform modules are reusable components used to organize and standardize infrastructure code. In our project we created modules for common resources like EC2, VPC, Security Groups, and Route53. The same modules were reused across dev, test, and production environments by passing different variable values(variables.tfvars file). Modules helped us follow DRY principles(dont repeat yourself), reduce duplicate code, and improve maintainability.

locals file : (i.e., locals.tf)
--------------
Terraform locals are used to define internal reusable variable values inside Terraform configuration files that can be referenced multiple times within the same module and locals can work with expressions and functions.

locals = Store calculated/reusable values inside Terraform code

syntax:
--------
locals {
  name = value
}

Variables vs local ✅
variables can be overriden at runtime and passes them from outside but locals cant Because local is internal completely private to the module.
In variables we cannot define expressions they are static and in local we can define expression and functions etc.. that you calculate once and reuse multiple times throughout your infrastructure code.
You cannot use functions, loops , ternary operators etc.. with variables but locals can calculate,transform and combine data using terraform functions and expressions

Think like:
Variables  → Inputs coming from outside
Locals       → Values calculated/created inside Terraform

Example 1: Without Locals ❌

With Locals ✅

Terraform State (.tfstate file) :
---------------------------------------
Terraform State is a file that stores information about all the infrastructure or resources created and managed by Terraform. It is the Terraform's last known/recorded state.  (last when u run apply cmd)
Terraform reads this file during every plan and apply operation to identify the existing infrastructure state, allowing it to determine whether resources need to be created, updated, or destroyed.

The Terraform state file, typically named terraform.tfstate and it is a JSON file that stores the current state(last time when u do apply cmd that run state) of your infrastructure.
Actual cloud may change(manually some body changes and no idea reg that infra in state file when u run again it will compare all and decide to create/update/delete ).

when run apply command:   
Terraform uses the state file to understand ---> What resources exist , what resources i need to create/update/destroy 

Ex: we have created ec2 with terraform code and it will store like 
terraform.tfstate
{
 "aws_instance.web": {
 "id":"i-123456789",
 "instance_type":"t3.micro"
 }
}


Why Terraform Needs State ---> Terraform works with two states 
1)Desired State  --> What you write in Terraform code (.tf files )     --> that means what resource u want to create/update/delete
ex: main.tf 
instance_type="t3.micro"  -->  You are telling Terraform: "I want EC2 with t3.micro"
ex: 
resource "aws_instance" "web" {
 ami = "ami-123"
 instance_type = "t3.micro"
}

2) Current State ---> Means: What currently exists in cloud and state file
Ex:
AWS currently: EC2
instance_type=t3.micro

terraform.tfstate:
instance_type=t3.micro

when u run plan/apply
Terraform compares:  Desired State (terraform code i.e., .tf files) VS Current State (terraform.tfstate + already existing infra in cloud)  ----> based on that it will decide whether its needs to be create/update/destroy resources

If both same: No changes --> Infrastructure is up-to-date

If different: Example: Change code:
Before:
instance_type="t3.micro"

After:
instance_type="t3.small"

Terraform checks:
Code(.tf files we updated to):
t3.small

State:(currently existing resource in aws )
t3.micro

Difference found ---> 
Plan: update instance
Apply:  Modify EC2 in aws and then Update info related to that in state file

Example: Someone manually deletes EC2 in AWS console

State file still says:
EC2 exists
i-12345

Terraform refreshes: terraform plan ---> Terraform checks AWS API: "EC2 missing" Then creates again.

State Management Flow --> When running

terraform init --> Downloads providers , Initializes backend , Configures state location
terraform plan
Flow: Read terraform code(configuration file .tf files) + Read terraform.tfstate(if already exists) + Refresh/query the actual AWS cloud infra state using AWS API ---> Compare ---> Show actions what need to be done 
whether  --->  + create or ~ update or  - destroy

terraform apply --> Creates/updates/deletes resources ---> after that it Updates info in terraform.tfstate

Step 2 (the refresh) actually writes modifications back to your terraform.tfstate file if it detects drift or missing resources.This ensures your state metadata perfectly aligns with cloud reality before presenting you with the action proposal.
if u dont want to do that u can use ----> -refresh=false      --> terraform.tf state will not modified if any changes detected

Configure Remote Backend:
------------------------------------
1)Create S3 bucket called      --> terraform-state-arun (bucket name it should be unique) and this bucket Stores terraform.tfstate file
2)DynamoDB Table                 --> terraform-lock-table (table name) ----> Partition key: LockID --> Used for locking. --> create 
3) Now in provider.tf place below code inside terraform block
terraform {
	backend "s3" {
		 bucket = "terraform-state-arun"
		 key = "roboshop/dev/terraform.tfstate
		 region = "us-east-1"
		 dynamodb_table = "terraform-lock-table"
	}
}
Run: terraform init -reconfigure ---> Terraform reconfigures remote backend.


What happens during apply with remote state?
Developer  1 runs:  terraform apply
Flow:
Terraform --> Check DynamoDB lock aquires it --> Lock state file --> Download tfstate from S3 --> Compare(desired state and current state(aws infra existing + tfstate file) --> decides to Create/update/delete AWS resources --> Upload updated state to S3 --> Remove lock 
--> until developer1 completes then only developer 2 cant run

Remote State Interview Answer ⭐⭐⭐
Terraform state file maintains mapping between Terraform configuration (.tf files) and real infrastructure existing in cloud. By default state is stored locally as terraform.tfstate. For team environments we configure remote backend like AWS S3 to store state centrally. DynamoDB is used for state locking to avoid multiple users modifying the same state at the same time.
Whenever terraform plan or apply runs, Terraform compares desired configuration with current state and performs required changes.

Interview Answer (4+ Years)
Terraform acquires a state lock before performing any operation that modifies infrastructure. When using an S3 backend with DynamoDB locking (or S3 native locking with newer versions), it prevents multiple users or pipelines from updating the same state file simultaneously. 
If a previous operation is interrupted, a stale lock may remain. In that case, we verify that no Terraform operation is still running and then use terraform force-unlock <LOCK_ID> or remove the stale lock entry before retrying.

3).terraform.lock.hcl (Dependency Lock File)
-----------------------------------------------------------
.terraform.lock.hcl is a dependency lock file created when u run terraform init. Basically which acts as a lock on your infrastructure's software dependencies
It stores the exact aws provider version downloaded and checksum(Cryptographic Hashes ) information that Terraform selected, so every developer or CI/CD pipeline running ur code uses the exact same cloud provider version and modules.

Basically when u run terraform init without mentioning version in provider block {} Terraform will automatically download the latest available version 
without lock file if you run terraform init today and a teammate runs terraform init next week, they may get the newer version of the AWS provider so we may get issues like breaking changes 
.terraform.lock.hcl file stops this from happening
when teamate clones or other running ur code and run terraform init --> terraform first checks whether lock file is there are not if not there it will automatically download some version automatically and create new lock file but if already lock file exists instead of looking for new version on online, it pulls the exact version listed in the lock file and verifies the download against the cryptographic hashes to ensure the code hasn't been altered or tampered with

But if u want to new version and u dont want to install lock file version then u need to upgrade
terraform init -upgrade			-- it downloads the new version instead of lock file version and upate the lock file with newer version number 

checksum --> when u run terraform init it will download AWS plugin files into your hidden .terraform folder, calculates their fingerprint (checksum), and saves it into the .terraform.lock.hcl file.
Next time you run terraform init (or on a teammate's machine): Terraform downloads the plugin files again, calculates their fingerprint, and compares it to the checksum saved in the lock file. If they match perfectly, it proves the file is safe, secure, and has not been altered or hacked.

A multi-environment approach means using the same Terraform project to manage multiple environments, such as Dev, QA/SIT, UAT, and Production, while keeping their infrastructure and state separate.

Advantages of a multi-environment approach
1. Isolation: Changes in Dev should not accidentally modify Prod infrastructure. Separate AWS accounts and state backends provide stronger isolation than simply using different .tfvars files.
2. Cost optimization and different configurations: Dev can use smaller EC2 instances and fewer availability zones, or turn off non-production resources when they are not needed. Prod can use larger instances, Multi-AZ deployments, and higher availability configurations.
3. Separate state files: Terraform tracks each environment's infrastructure independently, reducing the risk of one environment's operations affecting another environment's state.
4. Controlled deployments: Test changes in Dev, validate them in SIT/UAT, and then promote the approved changes to Prod through the CI/CD pipeline.
5. Security, access control, and compliance (RBAC/IAM): Restrict who can access and modify production infrastructure, and enforce approval and audit requirements.

Interview Answer
There are three common ways to manage multiple environments in Terraform. The most common approach is using separate .tfvars files along with separate remote backends for each environment, such as Dev, QA, and Production. This allows us to reuse the same Terraform code while supplying different variable values and maintaining separate state files. Terraform Workspaces provide separate state files within the same backend and are suitable for simpler use cases, but they become difficult to manage when many environment-specific variables exist. Some organizations use separate repositories for each environment when complete isolation is required, but this leads to code duplication. In most enterprise projects, we use reusable modules with environment-specific .tfvars files and separate remote state backends because this approach is scalable, maintainable, and safer.

But u can change this behavior wit ----> on-failure = continue

tainted -- meaning it is a semi-configured, broken resource

2. Destruction_time : Runs during resource deletion we need to mention this explicitly when = destroy means this provisioner block runs before the resource destroyed
Ex: 	
	provisioner "local-exec" {
		when = destroy
		command = "echo ansible_user=ec2-user >> inventory.ini"
    }
If the destroy time provisioner block failes terraform completey stop the destruction process of resource so resource will not be destroyed and stays in running 
If u remove this bloc before destroy this block will not run obviously

3. on-failure = continue
Normally if provisioner fails it will complete abort the creation or destruction of resource and taint the resource and recreates it on the next run but if u define this condition in provisioner block it will ignore the error got and print that error on the terminal instead of stopping the process still it will continue to create the resorce at creation time and destroy the resource at destruction time  
Ex: 
 provisioner "local-exec" {
    when       = destroy
    command    = "echo 'Removing server' >> cleanup.log"
    on_failure = continue  # If writing to cleanup.log fails, still delete the instance from AWS!
  }

4. on-failure = fail  -- default behavior

2) remote-exec
--------------------
To execute commands/scripts on the remote ec2 server by logging into resource (ex: EC2) using SSH after resource is created

Flow ----> terraform apply ---> Create EC2 ---> login using into ec2 using SSH (i.e., connection block)---> Execute Linux Commands on remote server

Example:

	ami="ami-123"
	instance_type="t3.micro"
	vpc_security_group_ids = [aws_security_group.allow_all.id]

	connection {                                #by using this bloc it will connect to remote server 
		type="ssh"
		user="ec2-user"
		private_key=file("mykey.pem")  or password = "DevOps321
		host=self.public_ip                     #self means current resource ec2 ip in which block we returned provisioner   if other using module module.<ref name>.<ip>
	}

	provisioner "remote-exec" {
		inline=[
		"sudo yum install nginx -y",
		"sudo systemctl enable nginx",
		"sudo systemctl start nginx"
		]
	}
}

Flow : terraform apply ---> Create EC2 ---> connect using SSH info(i.e.,using connection block details) ---> yum install nginx ---> systemctl start nginx

Without connection block --------> Terraform doesn't know: Which server? and Which user? and Which SSH key?

-----------------------------------
User Data													Provisioners
--------------                                                ---------------------
Runs when EC2 boots					Runs after Terraform creates resource
Executed by EC2							Executed by Terraform

User Data is an EC2 bootstrap mechanism where we provide a script that executes during the instance's initial startup. 
I use it for basic initialization such as installing bootstrap packages or starting required agents. Terraform provisioners, such as local-exec and remote-exec, allow Terraform to execute commands during the resource lifecycle. 
Local-exec runs on the Terraform execution machine, while remote-exec connects to the target machine and executes commands there. 
I use provisioners cautiously and prefer tools like Ansible for detailed server configuration

Why do we use time_sleep?
Without it: terraform creates a ec2 resource immediately ansible command run but ec2 still in booting and SSH not ready so it fails 
Without it: Terraform ---> Create EC2 ---> Wait 60 seconds ---> SSH Ready ---> Run Ansible ---> Success

Is time_sleep always used in companies?
In enterprise projects, teams usually prefer: Cloud-init/User Data for initial bootstrapping.
CI/CD pipelines (Jenkins, GitHub Actions, Azure DevOps) that wait until the instance is healthy before triggering Ansible.
Ansible retry mechanisms (wait_for_connection, retries, delays) instead of a fixed sleep.
For example, in Ansible:Ansible retry mechanisms (wait_for_connection
- name: Wait for SSH
  wait_for_connection:
    timeout: 300
This is generally better than sleeping for a fixed 60 seconds because the playbook proceeds as soon as the server is actually ready.

Interview Answer (4+ Years)
We can use the time_sleep resource when there is a dependency on infrastructure becoming fully ready before executing the next step. For example, after Terraform creates an EC2 instance, the operating system and SSH service may still be initializing. If Ansible runs immediately, SSH connections can fail. By introducing a time_sleep resource with depends_on, Terraform waits for a specified duration before executing a null_resource with a local-exec provisioner. In enterprise environments, however, fixed sleeps are usually replaced with health checks or Ansible's wait_for_connection for a more reliable solution.

Modules :
-------------
Terraform module are reusable collection of terraform configuration files that are grouped together to create and manage cloud infrastructure.

Module = Reusable Terraform Code
Instead of writing the same EC2, VPC, Security Group, or RDS code repeatedly for dev, test, stage, and prod, we write the infrastructure logic once inside a module and call that module multiple times with different input values (diff env specific value files).

Advantages :
-----------------
Code Reusability (DRY - Don't Repeat Yourself)    --> instead of writing same code files multiple time we can write once as a module and reuse them where ever required 
Organizing( Clean Architecture)  --> without modules our main.tf contains 1000's of lines which is heavy to manage and read but by using module we can write cleam formatted code in a organized manner 
Encapsulation  (Hidden Complexity / Private Logic)  --> Who ever wants to just use the resource and deploy their application they dont required to know the inside logic and rules and iam policies . They just call the module and feed the variable values based on the preferences.

Types of Modules :

IP CIDR(Classless Inter-Domain Routing) Block Range :
-----------------------------------------------------------------------
We define IP address range for vpc using Classless Inter-Domain Routing notation.
or 
A CIDR block defines the network boundary and allocation capacity of our VPC architectures
When you create a VPC, you must specify an IP address range for the VPC in the form of a CIDR block.
In AWS, allowed IPv4 range sizes are between a /16 (65,536 addresses) and /24 (256 addresses) and/28 (16 addresses) --> in between u can give any number like /24 etc

An IPv4 address is always exactly 32 bits long : A number between 0 and 32 that indicates how many bits of the IP address are used for the network portion and remaining bits are used for the host portion.

Example:
10.0.0.0/16 	--> 65,536 addresses we can allocate and 
0.0       --> host portion    ---> individual machines that is hosts 
/16      --> network portion (locking the first 16 bits / first two octets 10.0.)    ---> how many bits are locked for network

10.0.0.0/16 provides a range of 10.0.0.0 to 10.0.255.255(65,536 IPs) -->  means 2^16 = 65,536 total IP addresses.

10.0.1.0/24  --> In 32 bits we gave 24 for network portion (32-24) and now we have 8 for host --> 2 ^ 8 = 256 IPv4 addresses
AWS reserves five IPv4 addresses in each subnet by default, so 251 are available for resources in a /24.


AWS provides a set of IP address ranges designated for private use, which are specified by RFC 1918 and are not routable over the internet. These CIDR ranges are:

10.0.0.0/8 (10.0.0.0 - 10.255.255.255)
172.16.0.0/12 (172.16.0.0 - 172.31.255.255)
192.168.0.0/16 (192.168.0.0 - 192.168.255.255)

So basically
Four octets means a sequence of 32 bits divided into four distinct 8-bit groups used to write an Internet Protocol Version 4 (IPv4) address.

Octete  ---> An octet is a unit of digital information consisting strictly of 8 bits.
					 Each 8-bit group can hold values from 0 to 255 in decimal form (or 00000000 to 11111111 in binary).
					  An IPv4 address is 32 bits long total, which equals 4 octets.

Why 255 instead of 2^8 = 256 means 
The range is 0 to 255 simply because computers start counting at 0 instead of 1					 

The AWS 5-IP Reservation Rule (Interview Gold) by default AWS steals 5 IPs from every single subnet you create. 
If you buy a /24 subnet (256 IPs), you can only use 251 IPs because AWS reserves these exact paths for internal infrastructure:
.0 - Network Address.
.1 - AWS VPC Router (Default Gateway).
.2 - AWS DNS Server (Amazon Provided DNS).
.3 - Reserved by AWS for future routing capabilities.
.255 - Network Broadcast Address (AWS doesn't support broadcast, but reserves it anyway).


Subnet :   sub-network
-----------
A subnet defines smaller IP range created inside a VPC that belongs entirely within a single Availability Zone (AZ) or logical subdivisions of a VPC’s IP address range 
For diff availability zones we need to create public and private subnets and We create subnets to organize and place resources across Availability Zones and control routing.

They divide large networks into smaller, isolated zones for better organization and control.
Distributing subnets across multiple AZs ensures fault tolerance and operational continuity.

1. Public subnet : network which routes the traffic from internet both inbound and outbound traffic through interner gateway
This allows resources within this subnet to have public IP addresses and accept direct (inbound and outbound traffic) i.e., bi-directional traffic to and from the public internet.
Bi-directional (Inbound + Outbound)
Application Load Balancers (ALBs), Nginx Proxies, Bastion Hosts

A public subnet is a subnet whose route table has a route to an Internet Gateway (IGW).
Example: 0.0.0.0/0 → IGW.
Resources such as a public-facing ALB can be placed in public subnets.
Important: Public subnet doesn't mean every resource inside it is accessible from the internet.

2. Private subnet: network which are completely isolated from direct internet access (i.e., inbound access) and communicate external internet(i.e., outbound access) via NAT gateway
To allow backend applications and databases to securely pull external things like installing packages or software updates or patches we route their outbound traffic through a NAT Gateway
Outbound Only (Blocks unauthorized inbound)
Backend Applications and Databases and NAT gateway deployed in public subnet

process : from vpc to private subnet(inside that ec2):
In our VPC, we have public subnets and private subnets. The Internet Gateway (IGW) is attached to the VPC, and the public subnet's route table has a route 0.0.0.0/0 → IGW, so resources in the public subnet can communicate with the internet when they have the required public IP and security rules. 
In the private subnet, we have EC2 instances without public IPs, so they cannot directly access the internet through the IGW. If the private EC2 needs to download packages like Nginx using yum install nginx, we create a NAT Gateway in the public subnet and assign an Elastic IP to it. 
Then, in the private subnet's route table, we add the route 0.0.0.0/0 → NAT Gateway. Now, when the private EC2 tries to download Nginx, the traffic goes from EC2 → Private Subnet Route Table → NAT Gateway in Public Subnet → Internet Gateway → Internet → Nginx Repository. 
The response comes back through Internet → IGW → NAT Gateway → Private EC2. In this way, the private EC2 can access the internet for downloading packages and updates, but the internet cannot directly initiate connections to the private EC2 through the NAT Gateway.

- The most specific matching route is generally selected using longest-prefix match.
- The route table controls the network path; it does not replace security groups or NACLs.

Security Groups :
----------------------
A Security Group is a stateful virtual firewall attached to resources/network interfaces, such as EC2 instances, load balancers, and RDS databases.

A Security Group is a stateful virtual firewall that controls inbound and outbound network traffic for your EC2 instances. It operates at instance level.
By default, everything is blocked for EC2 in an vpc. You can only define rules in SG to explicitly allow traffic.
Stateful means if you allow an inbound traffic request into your server (e.g., a user opening your website on port 80), the Security Group will automatically allow the response traffic to go back out to that user, regardless of what your outbound rules say.

Network ACLs(Access Control List) :
---------------------------------------------
It an optional layer of security for your VPC that acts as stateless, subnet-level firewall to control inbound and outbound traffic. Network ACLs operate at the subnet level.
stateless : If you allow an inbound packet on port 80, you must explicitly write a corresponding outbound rule to let the response packet back out. If you forget, the traffic is dropped.

A NACL rule applies to every single resource inside an entire subnet
Before a packet can even reach on an EC2 instance's Security Group, it must first pass through the subnet's Network ACL.
NACLs allows you to define explicit Deny rules. This makes NACLs your primary weapon to block malicious traffic or blacklisted IP addresses at the front door
Rules are numbered (e.g., 100, 200, 300). AWS processes them in strict numerical order, starting from the lowest number. The moment a packet matches a rule, evaluation stops.

Interview answer for your experience
VPC Peering is a private network connection between two VPCs that allows resources to communicate using private IP addresses without requiring an Internet Gateway, NAT Gateway, VPN, or public IP addresses. 
In our environment, we used VPC Peering for private connectivity between VPCs such as application and shared-services networks. After creating and accepting the peering connection, we configured routes in the relevant route tables on both sides and allowed only required traffic through Security Groups and NACLs. 
We ensured that the VPC CIDR ranges did not overlap because overlapping CIDRs cannot be peered. 
One important limitation is that VPC Peering is non-transitive and does not support edge-to-edge routing through a peer's NAT Gateway, Internet Gateway, or VPN connection. For environments with a small number of VPCs, peering is simple and cost-effective, while for larger hub-and-spoke networks with many VPCs and on-premises connectivity, we generally use Transit Gateway for centralized connectivity and routing.

Merge function :
----------------------
merge function takes two or more maps and combines them into a single map. 
If the same key/data exists in multiple maps, the map that is right/last in the list will overwrite the previous ones.

Ex: merge(var.common_tags, var.vpc_tags)      -- if common_tags has Name key and vpc_tags has Name key then vpc_tags will override the common_tags 

Slice function
------------------
The slice function extracts a subset of elements from a list based on a starting index (inclusive) and an ending index (exclusive).
Syntax : slice(list, start-index, end-index)

Ex: slice(listname, 0 , 2) -- means 0 and 1 index values it retrieves from list

Transit Gateway : 
-----------------------
AWS TGW is the managed networking service that acts as a one central point/hub to connect multiple vpc's, on-prime networks , VPNs, Direct Connect connections and other networks 
It makes network management simple, scalable and secure..Basically it works like a router in a regional level 
Transit Gateway is a regional resource not global. You can connect VPCs in same region to the TGW. And for connecting networks across regions, Transit Gateway peering can be used.

In VPC peering --> Without TGW as the number of VPCs increases, the number of connections also increase each vpc so it becomes difficult to manage.
								 In a multi-env this becomes complex   --->  (n * (n-1)/2)

Ex:
		
							 VPC-1
							   │
							   │
VPC-2 ─── Transit Gateway ─── VPC-3
							   │
							   │
						  On-Premises

Instead of creating many direct connections between VPCs, each VPC connects to the central Transit Gateway.

. Transit Gateway
. Attachments (VPC, VPN, DX, etc.)
. Transit Gateway Route Tables		---> for routing 
. Routes (static and propagated)
. Route Propagation.
. Association (to a route table)
. RAM (Resource Access Manager)	---> to share TGW with other accounts 
for cross-account sharing.

What exactly connects to TGW? 
TGW can have different attachments like --->  VPC , Site-to-Site VPN , Direct Connect Gateway , Connect attachment , Transit Gateway peering


Why do we need TGW?
Suppose your company has 10 VPCs 
--> Without TGW, you may need many VPC peering connections.
--> with TGW:

VPC-1 ─┐
VPC-2 ─┤
VPC-3 ─┤
VPC-4 ─┼── Transit Gateway
VPC-5 ─┤
VPC-6 ─┤
VPC-7 ─┤
VPC-8 ─┤
VPC-9 ─┤
VPC-10─┘

This is called a hub-and-spoke architecture. The major benefit is centralized connectivity and routing.
Hub → Transit Gateway
Spokes → VPCs/networks

How does traffic actually flow?
Suppose:
VPC-A: 10.0.0.0/16
VPC-B: 10.1.0.0/16
EC2 in VPC-A wants to communicate with EC2 in VPC-B.

Flow :  EC2 in VPC-A ---> VPC-A Route Table ---> Transit Gateway ---> TGW Route Table ---> VPC-B Attachment ---> VPC-B ---> EC2
Both the VPC route table and TGW routing need to know where the destination network is.


What is a TGW Attachment?
An attachment is basically ---> connection between TGW and a network.
VPC-A ---> VPC Attachment ---> TGW

What is a TGW Route Table?
The Transit Gateway needs to know: For this destination network, where should I send the traffic?

| Destination    | Target           |
| -------------- | ---------------- |
| 10.0.0.0/16    | VPC-A attachment |
| 10.1.0.0/16    | VPC-B attachment |
| 10.2.0.0/16    | VPC-C attachment |
| 192.168.0.0/16 | VPN attachment   |

So if traffic arrives at TGW for: 10.1.0.25 ---> TGW looks at its route table and finds: 10.1.0.0/16 ---> VPC-B attachment Then it sends the traffic toward VPC-B.


TGW Route Table vs VPC Route Table 
1. VPC Route Table Controls traffic inside/from the VPC.
		Example: 10.1.0.0/16 → TGW ---> This tells the VPC: "To reach 10.1.0.0/16, send traffic to TGW."
2. TGW Route Table : Controls traffic after it reaches TGW ---> 10.1.0.0/16 → VPC-B attachment

			VPC A route table ---> reaches TGW ---> looks for TGW Route Table ---> VPC-B


Very important: TGW is not the same as Internet Gateway 
Internet Gateway ---> used for VPC ↔ Internet (Ex:  EC2 → Internet Gateway → Internet)
Transit Gateway --->  TGW = Network-to-network connectivity
			VPC ↔ VPC
			VPC ↔ On-Premises
			VPC ↔ VPN
			VPC ↔ other connected networks

Flow :  Requestor VPC A sends traffic ---> traffic reaches to TGW ---> TGW uses route tables ---> based on the routes traffic routes to ---> Target VPC B or on-prime or other networks



What is AWS Transit Gateway and have you worked with it?
--> AWS Transit Gateway is a managed regional networking service that acts as a central hub for connecting multiple VPCs, on-premises networks, VPNs, and Direct Connect environments. 
--> In a multi-VPC enterprise architecture, instead of creating many point-to-point connections, we use a hub-and-spoke model where VPCs attach to the Transit Gateway. Routing is controlled using Transit Gateway route tables and attachments. This simplifies network connectivity, centralized routing, and scalability.

flow
How Ec2 knows where to search the destination ec2 response 
--> VPC-A --> we have EC2-A (10.0.1.10) --> wants to communicate with EC2-B (Private IP: 10.1.1.20 -- destination address) --> EC2-A creates a packet (contains destination details) --> EC2 checks in his own routing CIDR range (route table info) if not found it says it is outside of my network --> VPC-A route tables we configure TGW route --> Then the packet goes toward TGW --> TGW has its own route table it will check the matching Destination IP --> if ip matches So TGW sends the packet through the VPC-B attachment.

or 

flow 
EC2-A (10.0.1.10) --->  Destination = 10.1.1.20 ---> VPC-A Route Table we have TGW ip (10.1.0.0/16) → TGW ---> Transit Gateway ---> Looks at destination IP ---> 10.1.1.20 matches (10.1.0.0/16) ---> TGW Route Table ---> 10.1.0.0/16 → VPC-B ---> EC2-B (10.1.1.20)

Above example in content 
--> When an EC2 instance wants to communicate with another network, the packet contains a destination IP address. 
--> The source VPC route table determines that the destination network should be reached through the Transit Gateway. 
--> Once the packet reaches TGW, the Transit Gateway checks its route table and finds the route whose destination CIDR matches the packet's destination IP. 
--> That route points to the appropriate VPC or network attachment, so TGW forwards the packet there.

user_data :
---------------
User Data is an Amazon EC2 bootstrapping mechanism that allows you to automate scripts or configuration commands to run locally inside the virtual machine during its initial boot process

We use user_data for mainly 
--> install and update packages (Ex: nginx, Apache, git etc.. & ansible node &agent, SSM agent  or DataDog for external tools can manage the server downstream)  
--> create directories and users & configure the server
--> mounting secondary AWS EBS volumes at particular directories like /data 

Crucial Rules 
1. It only runs once --> By default, User Data scripts execute only once during the very first boot time of the instance and it is executed by cloud-init. 
	If you stop the EC2 instance and start it again tomorrow, the User Data script will not execute again.
2. If ur script contains error or typo issue still terraform apply shows "green or success" because AWS job ended the moment AWS allocated the server hardware	
3. Logs location --> If your User Data fails inside the machine we have to check cloud-init boot log (i.e., /var/log/cloud-init-output.log) after login to ec2 instance

Load Balancer :
--------------------
Load Balancer (LB) is a service that sits between the client and your ec2 servers(either frontend or backend). It receives incoming requests and distributes them across multiple health servers eqully.
Client talks only to the LB . LB decides which server should handle the request based o health and load and rules.

LB distributes traffic equally to multiple servers
LB will not send the traffic to unhealthy instances instead it will manage through healthy instances 
LB forwards traffic to Target Group which has multiple Servers configured
LB continuously monitors health of the servers using health checks and Supports for Auto Scaling 
The load balancer uses a cookie to keep sending the same client to the same backend for a configurable duration.

ex: 
1. Users (from internet ) accessing  ----> server        --> here request directly goes to server
but in LB 
2. Users (from internet ) accessing  ----> load balancer ---> server1 or 2 or 3
The client talks only to the load balancer. The load balancer decides which server should handle each request.

Why do we need a Load Balancer?
Imagine you have only one server ------------------->  10000 users ----> accessing --->Web Server
Problems:
Server becomes overloaded.
If the server crashes, the application goes down.
Scaling requires manually replacing the server.

With a load balancer:
		10000 users
			  |
			  |
		 Load Balancer      ---> distributes the load across multiple servers 
		  /    |     \
		Web1 Web2 Web3

Benefits: Better performance, High availability,Fault tolerance,Easy scaling

imp : if any server failes it will not redirect any request/traffic to that ec2 ...it will manage all requests with remaining servers

Flow : Client ------> Route53 DNS -----> Load Balancer -------> Target Group ----> EC2 Instances

steps :

The LB never sends traffic directly to EC2s.It always forwards traffic to the Target Group. In target groups we will add instances based on category like frontend,backend or database etc


Types of Load Balancers (AWS)
-----------------------------------------
1. Application Load Balancer (ALB) --->  Layer 7
		Works with: HTTP,HTTPS ... Can route based on: URL,Path,Host,Headers

2. Network Load Balancer (NLB) ---> Layer 4
		Works on: TCP,UDP,TLS ---> Used when: Very high performance,Millions of requests,Gaming,Streaming

3. Gateway Load Balancer Layer 3/4 ---> Used for: Firewalls,IDS,IPS,Network appliances
4. Classic Load Balancer Layer 4/7 ---> It supports HTTP , HTTPS , TCP and SSL..Old generation. Mostly replaced by ALB and NLB. 


Layer 4 vs Layer 7 diff
----------------------------
Layer 4 ---> 
1. Transport Layer (TCP / UDP) 
2. Only reads the destination IP and Port.and it Cannot inspect HTTP URLs.
3. Static packet forwarding.
4. Consumes minimal CPU and Scales to millions of requests per second.
5. Passes raw encrypted packets down or terminates purely at the TCP level.

Layer 7 --->
1. Application Layer (HTTP / HTTPS)
2. Reads URLs, Cookies, Headers, Paths.
3. Dynamic smart routing (e.g., path-based).  (Ex: /ui , /app etc..)
Example: GET /cart , GET /user , GET /payment ---> Can route based on paths.
4. Slowerr than Layer 7 
5. Handles SSL certificates natively, decrypting traffic at the load balancer gate.


Why ALB for microservices?
Because it supports path-based routing. i.e., Layer 7

Load Balancing Algorithms :
-------------------------------------
1. Round Robin – Requests are distributed equally across all servers (Server A, then B, then C, then back to A)
2. Weighted Routing – Servers with higher weights receive more traffic.
3. Least Outstanding Requests – Sends new requests to the servers which are handling less requests(if one server serving less requests compare to other severs based on the load it will send more request to server which is dealing with less servers)
4. IP Hash (common in some load balancers like NGINX/HAProxy) – Same client IP tends to reach the same backend.

AWS ALB primarily uses algorithms such as round robin and least outstanding requests depending on the target type and protocol.

1. Round Robin Algorithm :
lets say i have 3 servers and 5 requests so --> 1st request to server 1 , 2nd request to server 2, 3rd request to server 3, 4th request to server 1, 5th request to server 2 if one server fails it will manage with 2 servers only

2. Weighted Routing
You assign weights to servers based on capacity. A t3.medium instance might have a weight of 3, while a tiny t3.micro has a weight of 1. The load balancer sends three requests to the medium server for every one sent to the micro server.

3. Least Outstanding Requests or Least Connections 
The load balancer tracks active connections and automatically routes new users to whichever server is currently handling the least amount of active work. This is the best practice for heavy database queries or long-lived processing tasks.

4. IP Hash :
The load balancer uses a mathematical hashing function on the user's IP address to tie them to a specific backend server. 
This ensures that a specific user always hits the exact same server, which is critical for legacy applications that store user login sessions in local server memory (Sticky Sessions)

How Application Load Balancers work ?
--> Clients make requests to your application.
--> The listeners in your load balancer receive requests matching the protocol and port that you configure.
--> The receiving listener evaluates the incoming request against the rules you specify, and if applicable, routes the request to the appropriate target group. 
--> You can use an HTTPS listener to offload the work of TLS encryption and decryption to your load balancer.
--> Healthy targets in one or more target groups receive traffic based on the load balancing algorithm, and the routing rules you specify in the listener.


Common 4+ Years Interview Questions

Q: Why use an ALB instead of exposing EC2 instances directly?
A: It provides a single entry point, distributes traffic, performs health checks, supports SSL termination, and integrates with Auto Scaling.

Q: What is the difference between a Target Group and a Load Balancer?
A: The Load Balancer accepts client traffic. A Target Group is the collection of backend targets (EC2, IPs, Lambda) that receive forwarded requests.

Q: How do health checks work?
A: The load balancer periodically calls a configured endpoint (for example, /health). If an instance fails consecutive checks, it is marked unhealthy and stops receiving traffic.

Q: Where do you attach the SSL certificate?
A: On the ALB listener (typically port 443) using AWS Certificate Manager.

Q: How does Auto Scaling work with ALB?
A: New instances automatically register with the target group and start serving traffic only after passing health checks. Instances being terminated are deregistered gracefully.

launch template:
-----------------------
An AWS Launch Template is a reusable blueprint that stores the complete configuration/parameters required to launch an EC2 instance. 
Instead of specifying the AMI, instance type, security groups, IAM role, storage, user data, and other settings every time we create an instance, we define them once in a Launch Template. 
AWS services like Auto Scaling Groups use this template to launch identical EC2 instances automatically whenever required.

It ensures every instance is created with the same configuration and is commonly used by Auto Scaling Groups to automatically launch consistent, production-ready servers.

What information does a Launch Template store?
It stores almost everything needed to launch an EC2 instance.
AMI ID,Instance Type,Security Groups,IAM Instance Profile,Key Pair,User Data Script,Root Volume Size,EBS Configuration,Monitoring,Tags,Metadata Options,Network Interfaces,Shutdown Behavior

What does it do?
It does not create EC2 instances. Instead, it tells AWS Auto scaling group :  Whenever you need to create a new EC2, create it exactly like this. AWS then follows the Launch Template and creates identical EC2 instances.

Relationship with Auto Scaling :
Launch Template ----> Stores EC2 Configuration ----> Auto Scaling Group fetches it ----> Launches EC2 Instances

purposes :
The Launch Template defines how to create an EC2. 
The Auto Scaling Group decides when to create or terminate EC2 instances(ex : we are doing based on CPU utilization).

What is an Auto Scaling Policy?
An Auto Scaling Policy is a set of rules that tells the Auto Scaling Group when to add or remove EC2 instances.

Think of it like a manager.

Launch Template → tells AWS how to create an EC2.
Auto Scaling Group (ASG) → manages EC2 instances.
Scaling Policy → tells the ASG when to scale.

Suppose your Catalogue service has:

Types of Scaling Policies :
---------------------------------
1. Target Tracking Scaling (Most Common)
Example :
Maintain CPU around 50% .. Suppose Current CPU = 80%
---> AWS automatically launches EC2s until CPU comes back near 50%.

target_tracking_configuration {
  predefined_metric_specification {
    predefined_metric_type = "ASGAverageCPUUtilization"
  }

  target_value = 50
}

AWS automatically maintains a target metric such as CPU utilization without manually defining separate scale-out and scale-in rules.

2. Step Scaling : Here we define multiple thresholds.

Example :

CPU > 60%
Add 1 EC2

CPU > 80%
Add 2 EC2

CPU > 90%
Add 3 EC2

Scale depends on severity.

3. Simple Scaling ---> Old approach.

Example : CPU > 70% ---> Launch one EC2 ---> Wait 5 minutes ---> Check again.. Very basic.

Mostly replaced by Target Tracking.

4. Scheduled Scaling : Useful when traffic is predictable.

Example : Every day --> Morning --> 9 AM --> Increase servers --> Desired = 8 --> Night --> 11 PM --> Reduce --> Desired = 2 --> No CloudWatch needed.

ACM (AWS Certificate Manager)
------------------------------------------
AWS Certificate Manager (ACM) is a managed AWS service that provisions, stores, renews, and manages SSL/TLS certificates. 
These certificates are used to enable HTTPS communication between clients and AWS services such as Application Load Balancers, CloudFront, and API Gateway.

Solution : Encrypt the communication. Use HTTPS instead of HTTP


What is HTTPS : HTTPS means ------>  HTTP + SSL/TLS Encryption
flow:
Username --> Encrypted --> Internet --> Encrypted --> Web Server ---> Now nobody can understand the data.


But how do we encrypt?
We need SSL/TLS Certificate

Example : www.roboshop.com ------> gets a certificate for this domain. That certificate proves Yes I am the real roboshop.com and is used during the TLS handshake to establish an encrypted connection.

ACM --creates---> Certificate --attachd to --------> Application Load Balancer

Port 443 is the standard port reserved for HTTPS. The port itself does not perform encryption. The application (using TLS) does.



Why is the certificate attached to 443?

When browser connects ----> https://roboshop.com ----> Browser immediately says ---> Show me your certificate ---> ALB replies --> Here is my certificate ---> Browser verifies --> Trusted CA?,Correct domain?,Not expired? -----> If all checks pass, TLS handshake completes. Only then Encrypted communication starts. Without certificate Browser cannot establish HTTPS.

flow :
Browser ---> HTTPS --->443 ---> ALB ---> Certificate from ACM ---> TLS Handshake ---> Encrypted Connection Established ---> Forward request ---> Catalogue ---> User ---> Redis ---> MongoDB

The certificate is attached to the ALB

Why? Because ALB terminates SSL. This is called SSL Termination

https://web.arundevops.online
DNS resolves the domain to the ALB via Route53.
Browser connects to the ALB on port 443.
ALB presents the ACM certificate.
Browser validates the certificate.

The application processes the request and the response is returned through the same secure connection.

Cloud Front :
---------------

Amazon CloudFront is AWS's Content Delivery Network (CDN). It caches and delivers  web content globally from edge locations close to users, reducing latency, improving application performance, decreasing load on origin servers, and enhancing security.

Why was CloudFront introduced?
Example
Let's imagine your Roboshop application is hosted in:     AWS Region --- US-East-1 (Virginia)

Suppose you're sitting in Hyderabad.
When you open:  https://www.roboshop.com

The request travels:
Hyderabad ---> Indian ISP ---> International Internet ---> USA ---> Virginia ---> ALB ---> Web Server

Distance: Nearly 13,000 KM This takes time.

Example: Images, CSS, JavaScript, Videos, Fonts, ---> Every request travels to the USA. Result: Slow Website

Solution : Instead of sending every request to Virginia, AWS says "I have servers across the world." These servers are called Edge Locations 
Ex: Hyd,mumbai delhi 
Instead of users reaching Virginia, they reach the nearest AWS Edge Location. an the request will be delivered from the edge location

What is an Edge Location -----> An Edge Location is a small AWS data center whose job is to cache content.

When users request the data at first time the request goes to Virginia(origin server). The response is stored in Mumbai ,hyd ro dahi edge location server if some user request the same data the request get the content from that edge local and deliver request not goes to virginia(origin server) i.e., cached copy of data 

lets say if 10000 user accessing the videos or images the load on server will be high now with cloud front based on their location content will be delivered from edge location server 

If requested data not present in cached copy(in edge location servers) the server sends the request to the origin server --> alb --> ec2 and the request returned to edge location from origin server so data will be cached and the response to user at first time 

What is Origin?

Origin means "The original source of content."

Examples : S3 Bucket, Application Load Balancer, EC2 ,API Gateway ,Nginx Server

In your project ---> Origin is Application Load Balancer

Interview Questions
What is CloudFront?

CloudFront is AWS's Content Delivery Network that caches and serves content from edge locations closest to users, reducing latency and improving performance.

What is an Origin?

Origin is the backend source from which CloudFront retrieves content. It can be an S3 bucket, ALB, EC2 instance, API Gateway, or another HTTP server.

What is a Cache Hit?

The requested object is already stored in the edge location, so CloudFront serves it without contacting the origin.

What is a Cache Miss?

The object isn't available in the edge cache, so CloudFront fetches it from the origin, returns it to the user, and stores it for future requests.

Why use CloudFront with ALB?

CloudFront reduces requests reaching the ALB by caching static content, improves global performance through edge locations, provides HTTPS termination, integrates with AWS WAF, and helps protect the origin from excessive traffic.

What is TTL?

TTL (Time To Live) determines how long CloudFront keeps an object in its cache before requesting a fresh copy from the origin.

Can CloudFront cache dynamic content?

Yes. By configuring cache behaviors, cache policies, headers, cookies, and query strings appropriately, CloudFront can cache certain dynamic responses when it makes sense.
