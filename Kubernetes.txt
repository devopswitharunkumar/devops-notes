Kubernetes Introduction
----------------------------------
Kubernetes is a open source container orchestration platform used to automate the deployment , scaling , networking , and management of containerised applications.

It groups machines into a cluster and runs containers efficiently across them 
It hepls manage containers in prod environments 
it monitors application health and restarts failed containers 
it can scale application up or down based on need
it supports delcarative management using YAML files
 
Features of Kubernetes
. Automates deployment and scaling and management
. Scalability --> easily scale applications up or down based on demand 
. Self-healing (restarts failed containers) - --> Automatically restarts , replaces , reschedules failed containers
. Load balancing (distributes traffic across containers) and service discovery(automatically discovers and endpoints)
. Rolling updates and rollback -- updates app without downtime and roll back if needed 
. Storage orchestration
. Secret and configuration management and high availability and reliability.
. Efficient resource utilization and Runs on any environment (On-prem, Cloud, Hybrid)






Docker and Kubernetes are not competitors.

They solve different problems.
Docker builds and runs containers. (Builder + Runner)
Kubernetes manages thousands of containers. (Like Manager)

Before Docker
Earlier applications were deployed directly on Virtual Machines. (Like Java , NodeJS and python appln's). Everything was installed manually.
Problems: difficult to scale , difficult to recover from failures , manual deployments , downtime , manual monitoring
AWS solved some of these problems using : Auto Scaling Group , Launch Templates , Target Groups , Load Balancer but that was for VMs.

Then Docker came : Docker solved a major problem instead of saying Install java, nodejs and python and configure.. we simply create and image and run container and Now application runs exactly the same everywhere.

So Docker solved

What happens  ---> All containers disappear. Application becomes unavailable. Even if volumes exist, the volumes are stored on the same machine. Server gone ---> Volume gone ---> Application unavailable. Docker cannot move containers automatically to another server.

Problems with docker :
Single Host Failure :  One Docker Host --> if host creashed ---> All containers stopped. Docker cannot automatically recreate containers on another machine. 
Auto Scaling : Docker will not automatically create containers if traffic increases u should manually run so Not practical in production.
Load Balancing : Suppose if u have 3 container.. How will requests be distributed ...Docker itself doesn't provide production-grade load balancing between multiple application containers.
Self Healing : Suppose Container crashes. Docker stops it. Now what? Docker doesn't continuously monitor application health and replace failed containers across a cluster. Someone has to restart it (or configure simple restart policies on the same host). Production requires much more.
Multi Host Management :  Suppose company has multiple hosts 
Each host has 50 containers. Total 250 containers. Who will manage them? How do we know which host has free CPU? which host has free memory? where should a new container run? Docker doesn't provide cluster-wide scheduling.
Rolling Updates : if Application currently running with v1 if i want v2 version to deploy Without orchestration You manually Stop Run Check Repeat Risk of downtime.
High Availability : If one machine dies Application should still work. Docker alone cannot provide this across multiple machines.
Configuration Management  :  Where should Database URL, Username ,Password ,API Keys be stored? Hardcoding is not good. Need centralized configuration.
Service Discovery : Suppose Cart needs Catalogue. If Catalogue IP changes What happens? Applications shouldn't depend on IP addresses. Need service discovery.
Desired State : Production says Always run 5 containers. One crashes. Docker won't ensure the desired number of running containers across the environment. Someone has to intervene.

Problems with Docker Alone

. Hard to manage multiple containers manually was very difficult and error prone 
. No auto scaling and high risk of downtime and failures
. No self-healing if container fails
. No load balancing
. No rolling updates and service discovery
· Difficult to manage networking and storage


So what do we need?  ---> Orchestration


orchestration:
Orchestration means automatically coordinating and managing the lifecycle of workloads according to a desired state.

Container orchestration: 
Container orchestration means automatically managing the deployment, scheduling, scaling, networking, health, recovery and lifecycle of containers across multiple machines in a cluster.

Orchestration means Kubernetes automatically managing tasks such as deploying Pods, scheduling them on worker nodes, maintaining the required number of replicas, restarting or replacing failed Pods, scaling applications, providing service discovery and load balancing, and performing rolling updates and rollbacks. 

What exactly does orchestration handle?
The main responsibilities are deployment, scheduling, scaling, networking, health monitoring, self-healing, updates, rollback, and lifecycle management.


Tasks of orchestration
. Deploy: Create and deploy containers.
. Schedule: Decide where containers will run.
. Monitor: Check the health and status.
. Scale: Increase or decrease the number of containers.
. Heal: Restart, replace, and recover containers.
. Network: Connect containers and expose services.
. Update: Roll out updates and roll back if needed.





In our project, we used Kubernetes as the container orchestration platform to manage our microservices running across multiple worker nodes. Docker was mainly used for building and packaging the application images, which we pushed to the container registry, while Kubernetes handled the deployment and containers through Pods. We used Deployments and ReplicaSets to maintain the desired number of replicas and provide self-healing, Services for service discovery and load balancing, ConfigMaps and Secrets for externalized configuration and sensitive data, and resource requests and limits to control CPU and memory usage. Kubernetes also helped us with scaling, rolling updates, high availability, and automatic recovery when Pods failed, so we didn't have to manually manage individual containers across the cluster.

Why don't you use Docker alone in production?
Docker is excellent for building and running containers, 
but it is not designed to orchestrate containers across multiple servers. 
In production we need high availability, automatic scaling, self-healing, rolling updates, service discovery, load balancing, and centralized management. Kubernetes provides these orchestration capabilities while Docker is primarily used to build container images.


Docker can absolutely run containers. In fact, that's its primary job. However, Docker alone is not sufficient for managing large-scale production environments with hundreds or thousands of containers across multiple servers. That's where Kubernetes comes in.

Ex:
Now suppose you want to block traffic to the backend to frontend this services names..apply network policies ......Just blocking incoming traffic from every pod in that namespace

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: deny-backend-ingress
  namespace: prod
spec:
  podSelector:
    matchLabels:
      app: backend
  policyTypes:
  - Ingress
  
#we are controlling incoming traffic to those Pods. it will not allow the incoming traffic from backend service prod namespace to dev namespace ..
NetworkPolicy with no ingress allow rule → selected Pods' incoming traffic is denied.	
this code completely blocks all incoming network traffic to any pod labeled app: backend inside the prod namespace, while still allowing it to send outgoing traffic.

Another Example: 
Now that everything is blocked, you must explicitly whitelist allowed traffic pathways.For example, let's say you want to allow a Frontend application located in a namespace called frontend-ns to connect to a Database pod inside your backend-ns namespace on port 5432 (PostgreSQL).


apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-db-access
  namespace: backend-ns               # The destination namespace being protected
spec:
  podSelector:
    matchLabels:
      app: postgres-database          # Target only the database pods
  policyTypes:
  - Ingress										# 2. Lock down all incoming traffic!
  ingress:
  - from:
    - namespaceSelector:
        matchLabels:
          access-role: frontend-apps 			# Step A: Allow traffic coming from this namespace
      podSelector:
        matchLabels:
          app: frontend-web        			   # Step B: Allow only this specific app inside that namespace
    ports:
    - protocol: TCP
      port: 5432                     					 # Step C: Only open this exact communication port

3.Apply a Default Deny All policy to isolate the namespace completely.

3)lets say we dont know no of namespaces and pods present in the cluster i want to block communication from all namespaces and services and from prod to my frontend service and dev namespace i.e., You have many namespaces in the cluster, but you want your namespace to be completely isolated from other namespaces.
You don't need to list every other namespace.
Instead, you create a default-deny NetworkPolicy in your namespace.
Ex: apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-all
  namespace: my-app
spec:
  podSelector: {}							#Apply this policy to ALL Pods in my-app. or # An empty selector matches EVERY pod in this namespace
  policyTypes:
    - Ingress										 # we are blocking both incoming ingress and outgoing egress both and if we use only ingress it will block only incoming requests like that 
    - Egress
it doesnt allow both incoming and outgoing traffic to our pods in production env we will write network policies to allow the required traffic 
If I have many namespaces in a cluster and want to completely isolate my application's namespace, I don't need to create a deny rule for every other namespace. I apply a default-deny NetworkPolicy to my namespace using an empty podSelector and deny both ingress and egress. Then I create separate allow policies only for the traffic my application actually requires, such as DNS, database access, or specific application services. Everything not explicitly allowed remains blocked.

Pod :

A Pod is the smallest deployable unit in Kubernetes. 
A pod can contain one or more containers that share the same network (namespace, network ip and nodeport ), storage volumes , and configuration.
Pods are ephemeral i.e., can be created, destroyed or recreated and allow multiple container work together 

Types of pods:
Single Container pod ----> contains only one container 
Multi Container pod  ----> contains multiple containers 
Init container and side car container 


Pod States/lifecycle:
--------------------------
1)Pending   		----> 	The Pod has been accepted by Kubernetes, but one or more containers have not yet started
This can include:

Waiting for scheduling
Waiting for resources
Pulling the image
Waiting for volumes

2)Running			----> The Pod has been bound to a node, and all containers have been created; at least one container is still running or starting/restarting.
Because Pod phase Running does not necessarily mean the application is healthy. A container can be running while its readiness probe is failing.

3)Succeeded    			----> All containers in the Pod have terminated successfully and will not be restarted. 
This is common with Jobs/batch workloads rather than continuously running microservices.
4)Failed 				----> All containers in the Pod have terminated, and at least one container terminated unsuccessfully.
5)Unknown 				----> The Kubernetes control plane cannot obtain the current state of the Pod, usually because it cannot communicate with the node/Kubelet.



Scheduled    	---> It means the Scheduler has selected a node for the Pod.
Pulling 			---> images are being pulled by kubelet

Interview Answer (5 Years)
A Pod is the smallest deployable unit in Kubernetes and a pod can have one or more containers. Containers within a Pod share the same network namespace, IP address, storage volumes, and lifecycle. so they can communicate with each other using localhost and access the same shared files/storage. In our project, we typically used one container per Pod for each microservice. We managed Pods through Deployments, which ensured the desired number of replicas, supported rolling updates, and automatically recreated Pods if they failed.



Why multiple container in pod :
 
Multi-container patterns :
---------------------------------
1)Side-car pattern:
		Sidecar pattern. Suppose the main container is running the Catalogue application and continuously serving user requests. We don't want the main application container to spend CPU and memory pushing log files to ELK because that affects application performance. 
		Instead, we add a second container called a Sidecar container(Fluent Bit sidecar container) in the same Pod. The main container simply writes logs to the shared volume, and the Sidecar container reads those logs from the shared storage and pushes them to ELK. 
		This keeps the main application focused only on serving requests while the Sidecar handles log collection. Since both containers are in the same Pod, they can easily share the same network and storage. 


Manifest files:
Main Container → Catalogue Application
Sidecar Container → Fluent Bit (push logs to ELK)

apiVersion: v1
kind: Pod
metadata:
  name: catalogue-pod

spec:
  volumes:
    - name: log-volume
      emptyDir: {}

  containers:
  - name: catalogue
    image: catalogue:v1
    volumeMounts:
      - name: log-volume
        mountPath: /app/logs

  - name: fluent-bit
    image: fluent/fluent-bit:latest
    volumeMounts:
      - name: log-volume
        mountPath: /app/logs

How it works :  Catalogue Container ---> write logs to /app/logs/app.log ---> in shared volume ---> Fluent Bit pushes logs to ---> ELK 

2)Proxy pattern: 
		Suppose our main container is running the Catalogue application, and we want every incoming request to be validated before it reaches the application. Instead of implementing authentication, authorization, rate limiting, SSL termination, or request filtering inside the application, we deploy a Proxy container in the same Pod it sits bw the user and main application container. 
		All client requests first reach the Proxy container, which inspects and validates them. If the request is valid, it forwards it to the main application container using localhost(multiple containers in same pod communicate using localhost); otherwise, it rejects the request. Since both containers share the same network namespace and IP address, communication between them is very fast. 
		This approach keeps the application code simple while the Proxy container handles security and traffic management. 
In production environments, technologies such as Envoy or NGINX are commonly used as Proxy containers in a Pod.

Instead of coding all this inside the application, we deploy an Envoy or NGINX proxy.

			Init container runs only once before the main application container starts. Suppose our Catalogue application requires a database connection, configuration files, or some initialization scripts before it can start successfully.

			Only after the Init container completes successfully Kubernetes start the main application container. If the Init container fails, the main container never starts. This ensures the application always starts in a ready and consistent state. 
			In production, Init containers are commonly used for database readiness checks, configuration setup, schema migrations, and downloading required files before the application starts.

An Init container performs initialization tasks before the application starts.

What are Labels?
Labels are key-value pairs attached to Kubernetes objects for identification, organization, and selection. They are used by Kubernetes resources like Services and Deployments to locate matching Pods.

What are Annotations?
Annotations are key-value pairs used to store descriptive metadata such as build numbers, Git commits, deployment timestamps, or owner information. They are intended for tools and humans, not for selecting resources.

Give one production use case for Labels.
"In our project, we labeled Pods with values such as app=catalogue, env=prod, and version=v1. Kubernetes Services used these labels to route traffic to the correct Pods, and we also used them to filter resources during troubleshooting."

Give one production use case for Annotations.
We stored deployment metadata such as Jenkins build number, Git commit ID, deployment timestamp, and deployment owner in annotations. This made it easy to trace which build was running in production.


If labels are changed, what happens?"
If a Pod's labels no longer match a Service's selector, the Service immediately stops routing traffic to that Pod. Similarly, if a Deployment's selector doesn't match its Pods, it may create new Pods because it believes the desired ones don't exist. That's why labels must be planned carefully and not changed arbitrarily in production.

Resource requests and limits : 
---------------------------------------
Resource Requests and Limits define how much CPU and Memory a container requires and the maximum amount it is allowed to use.
Resource requests and limits are configured on containers, not directly on Pods.

There are two terms:
Requests
Limits


Why do we need Resource Limits?
Suppose one Kubernetes Worker Node has:  8 CPU and 16 GB RAM
Now you deploy three applications ---> catalogue, cart and user 
Suppose the Cart application suddenly consumes: 90% CPU and 15 GB RAM so other application and node performance will go down 

To prevent one container from consuming all resources, Kubernetes allows us to define Requests and Limits.

Request : Request is the minimum amount of CPU and Memory that Kubernetes guarantees to a container.
Example
resources:
  requests:
    cpu: "500m"               # 0.5 CPU 
    memory: "512Mi"   #512 mb 
	
Scheduler says: I will place this Pod only on a node that has at least 0.5 CPU and 512Mi memory available.


Limit:   Limit is the maximum amount of CPU and Memory a container is allowed to consume.
Example
resources:
  limits:
    cpu: "1"
    memory: "1Gi"        #1 CPU and 1 GB RAM


Example:
spec:
 container:
 - name: resourcerequestandlimitcontainer
   image: nginx
   ports:
   - containerPort: 80
   resources:
    requests:
      cpu: "100m"
      memory: "68Mi"
    limits:
      cpu: "200m"
      memory: "100Mi"
	  
	  
What happens during Scheduling?
Suppose

Worker-1 : Available
CPU = 200m
Memory = 400Mi

But in manifest file u mention 
Request
CPU = 500m
Memory = 512Mi

Scheduler says ❌ Cannot schedule. Need another node.

What happens if Limit is crossed?

CPU 

Suppose
Limit ---> 1 CPU
Application tries ---> 2 CPU

Kubernetes ---> Throttles CPU.Application becomes slower. Pod is not killed.

Memory

Suppose
Limit --- > 1Gi
Application uses  ----> 2Gi

Kernel ---> OOM Killer ---> Container terminated. Pod restarts.

Interviewer
CPU ---> Throttle
Memory ---> OOMKilled


How to Check container resources :    kubectl describe pod catalogue

Requests and Limits are configured on individual containers. Since a Pod can contain multiple containers, each container can have different resource requirements.
Request is the minimum guaranteed resource used by the Kubernetes Scheduler to place the Pod on a node. Limit is the maximum resource the container can consume during execution.
What happens if CPU Limit is exceeded ----> Kubernetes throttles the CPU.
What happens if Memory Limit is exceeded ----> The container is terminated by the Linux OOM Killer and Kubernetes restarts it (if managed by a Deployment/ReplicaSet).
If a Pod has two containers, where do you configure resources ---> for each container we will specify 

In our Kubernetes deployments, we configured CPU and memory requests and limits for each container. Requests ensured that the Kubernetes Scheduler placed Pods only on nodes with sufficient resources, while limits prevented a container from consuming excessive CPU or memory. If CPU usage exceeded the limit, the container was throttled, whereas exceeding the memory limit resulted in an OOMKilled event and Kubernetes recreated the container. Configuring appropriate requests and limits helped us achieve stable resource utilization and prevented one application from impacting others on the same worker node.

Why do we need Services?
Pods are ephemeral, so their IP addresses change when they are recreated. Services provide a stable endpoint, service discovery, and load balancing, allowing applications to communicate reliably without depending on Pod IPs.

How does a Service identify Pods?
Using Labels and Selectors. The Service selector matches Pod labels and automatically routes traffic to the matching Pods.

Does a Service create Pods?
No. Deployments create Pods. Services only expose and load balance them.

In our Kubernetes deployments, every microservice was exposed through a Kubernetes Service instead of accessing Pods directly. Since Pods are ephemeral and their IP addresses change after restarts or rollouts, Services provided a stable Cluster IP and DNS name for communication between microservices. Services used label selectors to identify the appropriate Pods and automatically distributed traffic across healthy replicas, ensuring reliable service discovery and load balancing within the cluster.

imagePullPolicy :   imagePullPolicy controls when the container runtime should pull an image from the registry before starting a container.
Types: 
by default  : 

| Policy         | Meaning                                                |
| -------------- | ------------------------------------------------------ |
| `Always`       | Check/pull the image every time a container starts     |
| `IfNotPresent` | Pull only if the image isn't already available locally |
| `Never`        | Never pull; image must already exist on the node       |


Always : When the container starts, Kubernetes contacts the registry and checks for the image and pull the image 
Important: Always doesn't necessarily mean the entire image is downloaded every time. The runtime can use cached image layers if the resolved image digest is already present.

IfNotPresent   --->  Kubernetes checks whether the image already exists on the node.it will pull the image from registry if image is not present in local..if image exists it will not pull ....
Scenario:
Suppose if u update the instructions in docker file and build a new image with new changes when u run manifest again... if image present locally it will not pull the updated image it will use old image instead.

Never  :   Kubernetes does not pull anything. The image must already exist on the worker node.


⭐ Very Important Interview Point: Default Policy
You don't always have to explicitly write imagePullPolicy. Kubernetes has defaulting behavior based on the image tag.
If image tag is mentioned as ---> latest or not mentioned version ----> Kubernetes by default uses the Always policy only for latest tag 
example:   
image: catalogue:latest 
image: catalogue    ---> because it automatically pulls latest images ryt so thats y 


other than latest tag all remaining by default ----> IfNotPresent     ---> u have to mention explicity u want policy

In static provisioning, we create the storage before/first and then make it available to Kubernetes through a PersistentVolume(PV).

How did you handle persistent storage in Kubernetes?

For applications that required persistent data, we used external persistent storage instead of relying on the worker node's local storage. In AWS EKS, we used EBS with the EBS CSI driver. Kubernetes represented the storage through PersistentVolumes, and applications requested storage using PersistentVolumeClaims. The Pod mounted the PVC into the required container path. This allowed the application data to survive Pod restarts or Pod recreation because the data was stored on the persistent EBS volume rather than inside the temporary Pod filesystem. We also used appropriate access modes such as ReadWriteOnce and handled the storage provisioning based on the application requirement.





Kubernetes Storage — EBS + PV + PVC + Pod
In our AWS EKS environment, we should not store important application data directly inside the worker node because worker nodes and Pods are temporary. If the Pod or node is deleted, local data can be lost. So we use external persistent storage such as AWS EBS. First, we create an EBS volume in the same Availability Zone where the worker node can access it. Then Kubernetes uses a PersistentVolume (PV) as the Kubernetes representation of that external storage. The application does not directly request the EBS volume; instead, it creates a PersistentVolumeClaim (PVC), which is basically a request for storage. Kubernetes binds the PVC to a suitable PV, and the Pod uses the PVC in its volume definition. So the overall flow is AWS EBS → PV → PVC → Pod → Container.

1. Create EBS volume in AWS console ---> EBS is the actual physical/cloud storage
2. Install the EBS CSI Driver                   ---> Kubernetes needs a storage driver to communicate with AWS EBS. In cluster we need to install driver The CSI driver allows Kubernetes to create, attach, mount and manage EBS volumes for Pods.
3. IAM permissions   ---> The EBS CSI Driver needs permission to perform operations on EBS. Attach proper role which has permision to perfoem operations like CreateVolume , DeleteVolume , AttachVolume , DetachVolume , DescribeVolume
4. PV represents storage that is available to Kubernetes ---> means the PV provides 10 GB of storage.

AWS EBS CSI Driver: 
-------------------------
It will create a bridge i.e., communication bw kubernetes and AWS EBS 
The CSI driver handles storage operations such as provisioning and attaching/mounting volumes to nodes

The Kubernetes storage workflow uses the AWS EBS CSI driver to provision and attach EBS volumes.


1) create a Storage Class manifest file 
Ex:
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: ebs-gp3								#name of the StorageClass.

parameters:
  type: gp3											#This tells the provisioner what kind of EBS volume to create.	gp3 -- General Purpose SSD volume type.
reclaimPolicy: Delete						
volumeBindingMode: WaitForFirstConsumer			#

kubectl get storageclass or sc

reclaimPolicy: Delete			#by default it is Delete
#ReclaimPolicy defines whether the dynamically provisioned storage should be deleted or retained after the PVC is deleted.
1)Delete --> if pvc deleted both pv and ebs can be deleted  
2)Retain --> underlying storage is retained for manual recovery/cleanup.


volumeBindingMode: WaitForFirstConsumer			
Instead of immediately creating the EBS volume when the PVC is created, Kubernetes waits until a Pod actually uses the PVC then provisions the EBS volume considering the Pod's scheduling/AZ.


Imagine your EKS cluster has: 3 nodes in 3 different AZ zones 1a,1b and 1c 
If Kubernetes creates the EBS volume too early, it might create it in the wrong AZ.

With: WaitForFirstConsumer ---> Kubernetes can consider where the Pod will run before provisioning the volume.
PVC created ---> Wait ---> Pod created ---> Scheduler determines suitable node/AZ ----> EBS volume provisioned appropriately ---> Volume attached ---> Pod starts


Important fields
provisioner → tells Kubernetes which CSI driver creates the storage.
parameters → specifies storage properties such as gp3.
reclaimPolicy → tells what happens to storage after PVC deletion.
volumeBindingMode → controls when the volume should be provisioned/bound.

Interview
When a PVC references a StorageClass, Kubernetes uses the configured CSI provisioner to dynamically provision the underlying storage. In EKS, the AWS EBS CSI driver provisions the EBS volume and Kubernetes creates/binds the corresponding PV.

Dynamic provisioning is a Kubernetes mechanism that automatically creates persistent storage when an application requests it through a PersistentVolumeClaim. Instead of an administrator manually creating the underlying storage and PersistentVolume, we define a StorageClass that specifies the storage provisioner and parameters. In our EKS environment, we can use the AWS EBS CSI driver with a StorageClass, for example using gp3 volumes. When a PVC requests storage, Kubernetes uses the StorageClass and CSI driver to provision the EBS volume and automatically create and bind the corresponding PersistentVolume. The Pod then consumes the storage through the PVC. This reduces manual work and provides self-service, standardized and automated storage provisioning.

PVC ---> StorageClass ---> EBS CSI Driver ---> Creates 10Gi gp3 EBS ---> Creates PV ---> PVC ---> Bound

In dynamic provisioning, the application creates a PVC referencing a StorageClass. The StorageClass uses the EBS CSI driver to automatically provision the required EBS volume and corresponding PV, and once the PVC is bound, the Pod mounts the PVC and uses the persistent storage

EBS vs EFS
EBS(Elastic Block Store) = a hard disk for a server/application.
EFS(Elastic File System) = a shared network filesystem that multiple servers/Pods can access.

EBS:
EBS is block storage. it is like hard disk we are attaching it to ec2 instance 

When do we use EBS?
Use EBS when your application needs:
Persistent storage
High-performance block storage
Database storage
One Pod/node needs read-write access to its own volume
Data that should survive Pod replacement

Flow: pod ---> PVC ---> PV ---> EBS

Ex: MYSQL pod ---> EBS data 
If the MySQL Pod is deleted and recreated on a suitable node, it can mount the same persistent EBS-backed volume.
And where ever the node present we should create volume in same availability zone it is zone specific.. and most commonly it is used with RWO(ReadWriteOnce) access mode i.e., means one node/pod can access at a time

Good for:
Database, application-specific persistent data, block-storage workloads.
Good when the data primarily belongs to one application/node and you don't need multiple nodes mounting the same filesystem simultaneously.

EFS:
EFS is file storage. It is like shared Network Folder(ex:google drive)
Multiple Worker nodes can access the same filesystem at a time 
Flow :
Pod-1 ──┐
Pod-2 ──┼──→ PVC → PV → EFS
Pod-3 ──┘

And if pod-1 uploads some thing now pod 2 & 3 can access that files also and commonly used with access mode ReadWriteMany (RWX)
Good for:
Good when multiple Pods/nodes need to access the same/shared files simultaneously.

When do we use EFS?
Use EFS when multiple Pods/servers need to access the same files simultaneously.

| EBS                                							  |                        EFS                                          |
| ------------------------------------------------- | -----------------------------------------------------|
| Block storage Like a hard disk                | File storage Like a shared network folder|
| Usually used by one node at a time  	| Multiple nodes can access simultaneously |
| Commonly RWO(ReadWriteOnce)        | Commonly RWX(ReadWriteMany)              |
| AZ-Zone specific                   						| Designed for shared access across AZs    |
| Good for databases                                  | Good for shared files                    |
| High-performance block storage            | Shared filesystem                        |
| Example: MySQL data                               | Example: shared uploads                  |


EX:
Suppose i have 3 pods in my application 
scenario 1: Database
I have mysql and i want data to be persisted, so we use EBS because the database needs block storage and its own persistent volume.

scenario 2: Shared files
Your application allows users to upload: photos, files, documents and reports etc..and if u want to access them by all 3 pods we use EFS because EFS provides shared file access.

Interview answer:
EBS and EFS are both AWS persistent storage services, but they solve different problems. 
EBS is block storage, similar to a persistent hard disk, and is commonly used for databases and applications that need high-performance persistent storage, typically with ReadWriteOnce access. 
EFS is a shared file system that multiple EC2 instances or Kubernetes Pods can access simultaneously, typically using ReadWriteMany. 
In Kubernetes, I would use EBS for application-specific or database storage, while I would use EFS when multiple Pods across different nodes need to share the same files

diff bw deployment vs statefulset
Deployment is mainly for stateless applications; StatefulSet is for applications where each Pod needs its own identity and/or persistent storage.

StatefulSet:
---------------
StatefulSet is a Kubernetes workload controller used to run stateful applications that need stable Pod identity/name, stable network identity, and persistent storage.

Ex: Mysql, mongodb, postgraceSQL , Elasticsearch, Zookeeper, Kafka etc....


Why do we need StatefulSet?
Suppose you deploy an application using Deployment with 3 replicas and of Pod A dies it will be recreated and new identity.For a stateless application, that's fine.
But imagine a database cluster: 3 mysql replicas
mysql-0
mysql-1
mysql-2
Each instance may have a specific identity and data. u dont want if mysql-0 dies rondomly create new pod.
You want Kubernetes to recreate: mysql-0 with its associated storage. That's where StatefulSet comes in.


Main features of StatefulSet:
1. Stable Pod identity/names ---> Pods get predictable names like mysql-0, mysql-1 etc...
2. Stable network identity ---> Each Pod can have a stable DNS identity.
3. Stable persistent storage ---> Each Pod can get its own persistent volume.
4. Ordered deployment/scaling ---> Pods are generally created and managed in an ordered manner.


| Deployment                           | StatefulSet                            |
| ------------------------------------ | -------------------------------------- |
| Mainly stateless applications        | Stateful applications                  |
| Pods have interchangeable identities | Pods have stable identities            |
| Pod names are not predictable        | Pod names are predictable              |
| `app-xxxxx`                          				| `app-0`, `app-1`, `app-2`              |
| Storage generally shared/optional    | Each Pod can have dedicated storage    |
| Pods are interchangeable             | Pods are individually identifiable     |
| Common for APIs/microservices        | Common for databases/clustered systems |

RBAC --> Role-Based Access Control.
RBAC controls who can perform what actions on which Kubernetes resources.

Kubernetes RBAC controls who can perform , what actions on which resources, using Roles/ClusterRoles for permissions and RoleBindings/ClusterRoleBindings to assign those permissions.

So RBAC answers three questions: WHO can perform ? ----> WHAT actions can they do? ----> ON WHICH resources?

Why do we need RBAC?
Imagine everyone in your Kubernetes cluster has full access. A developer could accidentally run --->  kubectl delete deployment payment ==> and production could go down. Instead, we give only the permissions they need like get pods or get deployments or other resources etcc...

This follows the security principle: Least privilege — give users only the permissions they actually need.

Interview answer — "What is RBAC?"
RBAC stands for Role-Based Access Control and is used in Kubernetes to implement authorization. It controls which users, groups, or ServiceAccounts can perform specific actions on Kubernetes resources. We define permissions using Role or ClusterRole, and assign those permissions using RoleBinding or ClusterRoleBinding. For example, we can create a Role that allows a developer to get, list and watch Pods only in a particular namespace and bind it to their identity. In production, we follow least privilege and avoid giving unnecessary permissions such as cluster-admin.
	
Interview answer — "How did you use RBAC?"
We used Kubernetes RBAC to control access based on team responsibilities and application requirements. For namespace-level access, we created Roles with only the required resources and verbs and assigned them through RoleBindings. For workloads that needed to interact with the Kubernetes API, we used dedicated ServiceAccounts and granted them limited permissions through RoleBindings instead of using highly privileged accounts. For cluster-level operations, we used ClusterRoles and ClusterRoleBindings where required. During troubleshooting, we used kubectl auth can-i and inspected Roles and RoleBindings to identify authorization issues

OOM(Out of Memory Killed) Error:
---------------------------------------------
OOMKilled error --> the system completely ran out of available memory if system resources not enough

1)Pod memory limit exceeded ---> An exceeded pod memory limit causes (OOMKilled) termination
2)Node out of memory		---> Node out of memory causes a (MemoryPressure) and pod eviction.

OOM kill happens when Pod is out of memory and it gets killed because you've provided resource limits to it.
When Node itself is out of memory or resource, it evicts the Pod from the node and it gets rescheduled on another node. Evicted pod would be available on the node for further troubleshooting.

OOMKilled will only for containers that have been terminated by the kernel OOM killer.container that exceeds its memory limit that gets terminated (and by default restarted) as opposed to the whole pod (which can very well have other containers).

Ex: Suppose your application normally has: 2 pods but But traffic suddenly increases to 100 users → 10,000 users

Two common approaches are:
Horizontal Scaling → increase number of Pods
Vertical Scaling   → increase CPU/memory of existing Pods

Horizontal Scaling: Horizontal scaling means increasing or decreasing the number of servers/application instances(pods).
-------------------------
Ex: we have 2 pods currently serving the request but traffic increases so increase the pods...The application gets more capacity by running more replicas.

To increase we have two ways 
1)manually scale servers/application instances==> Command :  kubectl scale deployment payment --replicas=5
2)Kubernetes can do it automatically using HPA.

Adv:
Adds/removes Pods i.e., creating more instances 
Good for stateless applications
Better for handling increased traffic

CPU    → 500m

After Increase resources:

HPA (Horizontal Pod Auto-scaler):
--------------------------------------------
HPA automatically increases or decreases the number of Pods based on resource utilization or other configured metrics. So HPA performs horizontal scaling.
Ex: 
Normal traffic ---> 2 Pods ---> CPU increases ---> HPA detects high CPU ---> 4 Pods
When traffic decreases: CPU decreases ---> HPA detects lower utilization ---> 4 Pods → 2 Pods

HPA architecture : Metrics ---> Metrics Server ---> HPA ---> Deployment / ReplicaSet ---> Pods increase or decrease
For CPU-based scaling: Pod CPU usage ---> Pod CPU usage ---> HPA ---> Desired replicas (mentioned in manifest file ) ---> Deployment ---> More/Fewer Pods

Ex:  Suppose our application normally runs on replicas 2 but we want 
Minimum Pods = 2
Maximum Pods = 10
Target CPU = 70%

Ex:

  name: shipping
  namespace: roboshop
  labels: # these labels are deployment labels
  etc......

  name: payment-hpa

  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: payment					# it is refering to payment deployment above 
  minReplicas: 2
  maxReplicas: 10
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70

Above code if CPU reaches to 70 percent, then hpa will create the pods automatcally based on traffic


What happens internally?
Suppose: Current replicas = 2 and CPU = 40% ....HPA doesn't need to scale: we have 2 Pods

HPA sees that the average CPU is above the configured target. It increases the desired number of replicas: 2 → 4 If traffic continues: 4 → 6 until it reaches: maxReplicas = 10

When traffic decreases it reduces the pods to : 10 → 8 → 5 → 2 .... subject to HPA's scaling behavior and stabilization rules.

HPA interview answer 
HPA stands for Horizontal Pod Autoscaler. It automatically adjusts the number of replicas of a Kubernetes workload based on metrics such as CPU, memory, or custom application metrics.
Ex: if our application normally runs with three Pods and CPU utilization increases beyond the configured target, HPA increases the desired replica count up to the configured maximum. When the workload decreases, it scales the replicas back down to the minimum.
In our EKS environment, HPA handled application-level scaling, while cluster-level scaling was handled separately through the node autoscaling mechanism.

Horizontal vs Vertical

Horizontal scaling means increasing or decreasing the number of application instances/servers/pods, so in Kubernetes it usually means adding or removing Pods. HPA is used for this. 
Vertical scaling means increasing or decreasing the CPU and memory resources allocated to an individual Pod using resource block, which can be handled using VPA.	
For highly available and stateless microservices, horizontal scaling is generally preferred because additional replicas can handle traffic and provide better availability.

Ingress controller:
-----------------------

First, what problem does Ingress solve?
Suppose you have multiple applications inside Kubernetes like catalogue, cart, user, mongodb etc....
You want users outside the cluster to access them
https://example.com/catalogue
https://example.com/cart
https://example.com/user    etc.......

One option is to expose every service using a separate LoadBalancer so that we need to create seperate LoadBalancer foe every component...This can become expensive and difficult to manage.

Instead, we can use Ingress:
Users/Clients ---> load Balancer ---> Ingress Controller ---> diff components like catalogue , cart , user etc... ---> diff service for each component catalogue, cart etc.... ---> pods 
One external entry point can route traffic to multiple internal Services.

Ingress: Ingress is a Kubernetes API resource that defines HTTP/HTTPS routing rules for external traffic going to Services inside the cluster.

For example:
example.com/catalogue  → catalogue-service
example.com/cart   → cart-service   etc.........
But there is an important point: Ingress itself does not process traffic. This is where Ingress Controller comes in.

Ingress Controller : An Ingress Controller is the component that actually watches Ingress resources and configures a load balancer/proxy to route incoming HTTP/HTTPS traffic to the appropriate Kubernetes Services

Ex:
NGINX Ingress Controller , AWS Load Balancer Controller , Traefik , HAProxy

For AWS EKS = AWS Load Balancer Controller
It can provision and configure AWS load balancers based on Kubernetes resources.

Ingress vs Ingress Controller

Ingress Defines: "Where should this request go?"
Example:
/payment → payment-service
/orders  → order-service

Ingress Controller  : Actually implements those rules ===> Receives request -----> Reads Ingress rules -----> Routes request -----> to Correct Service

Explain Kubernetes architecture :

Kubernetes follows a control-plane and worker-node architecture. 
-> The control plane is responsible for managing the cluster and maintaining the desired state. The main components are the kube-apiserver, etcd, scheduler and controller manager. The API server acts as the central communication layer, etcd stores the Kubernetes cluster state, the scheduler assigns Pods to suitable worker nodes, and controllers continuously work to maintain the desired state.

-> Worker nodes are responsible for running the application workloads. Each node has a kubelet, container runtime and networking components such as kube-proxy. The kubelet communicates with the control plane and ensures that the Pods assigned to the node are running, while the container runtime actually runs the containers.
Ex: 
-> when I deploy an application using kubectl, the request reaches the API server, the desired state is stored in etcd, controllers create the required workload objects usinf deployment and replicaset controllers, the scheduler selects suitable worker nodes to schedule newly created pods , and the kubelet on those nodes works with the container runtime to start the application containers. 
In our AWS environment using EKS, AWS manages the Kubernetes control plane, while we manage the worker-node capacity and the workloads running on it.

Jenkins triggers the CI/CD pipeline, where we build the application, perform SonarQube analysis, create the Docker image and push it to Amazon ECR. During deployment, we use Helm to deploy or upgrade the microservice in EKS. Helm communicates with the Kubernetes API server, and Kubernetes then creates or updates the required resources such as Deployment, Service, ConfigMap, Secret and Ingress.

Deployment strategy means how we release a new application version into an environment while maintaining application availability and minimizing deployment risk. 
We mainly used Kubernetes Rolling Updates for regular releases, and for critical or higher-risk releases we followed a Blue-Green deployment approach.

1)Rolling update/Ramped Strategy -- it zero downtime/minimal downtime deploment startegy 
----------------------------------------------
Rolling deployment was our normal deployment strategy for microservices. If we had four pods running version V1 and a new V2 image was released, Kubernetes gradually created V2 pods and terminated V1 pods while maintaining the required availability. We used readiness probes and resource configuration to make sure traffic was sent only to healthy new pods.

Interview Answer
For our regular application releases, we primarily used the Kubernetes Rolling Update strategy. Our microservices were deployed as Kubernetes Deployments, and when a new Docker image version was available in ECR, we updated the image version through our Helm deployment. Kubernetes gradually replaced the old Pods with the new Pods instead of stopping all the Pods at once.

We configured parameters such as maxUnavailable and maxSurge based on the application requirement, and we used readiness probes so that a new Pod received traffic only after the application was ready. During the deployment, we monitored the Pod status, application health, logs and metrics. If the new version had an issue, we could stop the rollout and perform a rollback to the previous Deployment revision.

What exactly did YOU do during Rolling Update? and What was your responsibility?
My responsibility was to update and manage the deployment through the CI/CD pipeline, verify that the new image was available in ECR, update the Helm values with the required image tag, deploy it to the target Kubernetes environment, and monitor the rollout. I checked Pod readiness, deployment status, application logs and monitoring dashboards. If the rollout wasn't healthy, I investigated the issue and, depending on the impact, rolled back to the previous stable version.



How did you perform rollback?
First I check the Deployment rollout status and identify whether the issue is with the new Pods, image, configuration, readiness probe or application itself. 
If the issue cannot be resolved within the release window, I roll back/undo to the previous stable revision.

explain this as your higher-risk release strategy
For higher-risk releases, we followed a Blue-Green deployment approach. We maintained the currently stable version as Blue and deployed the new version separately as Green. We validated the Green environment before directing production traffic to it. Once the new version passed our validation, we switched the traffic from Blue to Green. The advantage was that the previous stable version was still available, so if we identified a critical issue after the switch, we could quickly route traffic back to Blue.

What would you say you actually did for Blue-Green?
I was involved in preparing the new application version, deploying the Green version separately, validating the Pods and application health, and coordinating the traffic switch after approval. We monitored the application after the switch, and the previous Blue version was retained for quick rollback if required.

How was Blue-Green implemented?
We used labels to distinguish the versions and controlled which version received traffic through the Service/Ingress layer. The new version was deployed and validated independently, and after approval the traffic was switched to the new version.

For major releases where we wanted a safer deployment and fast rollback, we used the Blue-Green approach. Blue represented the currently running version and Green represented the new version. We deployed the new version separately, validated application health and functionality, and then switched traffic to the Green environment. If issues were detected after the switch, we could route traffic back to Blue.

----------------------------
Canary means --> Don't send everyone to the new version immediately.
lets say we have version A (old version) and version B (new version)
now they will release the some percentage of traffic to new version like 
ex : 
step 1 : 5% of users to new version or some regions locations and 95% of users to old version ---> if everything looks good monitor : errors, cpu, memory , metrics, latency , logs and bussiness metrics if healthy
step 2 : 25% of users to new version and 75% of users to old version ---> if everything looks good
step 3 : 50% of users to new version and 50% of users to old version ---> if everything looks good
step 4 : 100% of users to new version and 0% of users to old version ---> here full rollout to new version 


The idea is to deploy the new version to a small percentage of traffic first, monitor its behavior, and gradually increase traffic if the metrics remain healthy.

For high-risk releases, we can use Canary deployment. Instead of moving all traffic to the new version, we initially expose a small percentage of traffic to V2, monitor application and infrastructure metrics, and gradually increase traffic if everything is healthy. If we observe errors or performance degradation, we stop the rollout and route traffic back to V1.

Explain Kubernetes architecture based on your project ? 
In my project, we used Amazon EKS for container orchestration of multiple microservices. Architecturally, the Kubernetes cluster consists of the control plane and worker nodes. The API server is the central communication point, and we interact with it using kubectl and Helm. The scheduler assigns newly created pods to suitable worker nodes, while the controller manager continuously reconciles the desired state with the actual state. Cluster state and configuration are persisted in etcd.

On the worker nodes, kubelet communicates with the API server and makes sure the assigned pods are running, kube-proxy handles Kubernetes Service networking, and the container runtime runs the containers.

From our CI/CD pipeline, after building and validating the application image, we push it to Amazon ECR and deploy it to EKS using Helm. Kubernetes then creates or updates resources such as Deployments, Services, ConfigMaps, Secrets and Ingress. For availability and scaling, we use multiple replicas, readiness/liveness probes, resource requests and limits, and HPA where required.

I have worked on Kubernetes-based deployments in EKS, mainly around application deployment, troubleshooting, scaling and release management.
