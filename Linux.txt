Operating System (OS) :
--------------------------------
OS --> windows or Linux 

OS  --> The OS is a software that sits between the physical hardware and the software applications it manages both of them to work together without needing to know low-level hardware details(meaning applications can ask to "save a file" without needing to know how a physical storage drive works) or which is the core software that manages a computer's hardware and software resources
--> It interacts directly with physical computer parts to controlling the processor cycles, saving data files to your storage disk and Manages computer resources such as allocating CPU, partitioning memory, and tracks storage files.
--> It creates the stable, isolated environment needed for you to install and run apps like Google Chrome, WhatsApp, or Microsoft Word without them crashing each other.
--> Provides a User Interface: It Acts as an interactive interface between user and hardware (translating human inputs into system commands)
--> Handles File Storage: It keeps track of where your photos, documents, and system files are stored so they do not get lost or mixed up.

Compiler or interpreters converts the human text into 0s and 1s. Once code is already turned into 0s and 1s,the OS acts as the manager to load and run those binary instructions on the physical hardware chips
In linux --> Bash acts as the interpreter 
The Interpreter (Bash): Acts as the command-line interface environment. It takes your typed input, interprets what you want, maps it to the right pre-compiled binary, and tells the kernel to run it.
The Kernel: The ultimate core that loads those binary 0s and 1s into RAM and runs them on the physical CPU.

Kernel :
----------
A kernel is the core computer program inside an operating system that acts as a bridge between a computer's hardware and its software applications.

functionalities : 
Resource Management(CPU) 	--> Splits up precious computer power, like CPU time and network speed, fairly among running programs.
Memory Management 				--> Controls the computer's RAM, assigning space to each app while preventing programs from crashing or reading each other's private data. 
Device Control 								--> Uses device drivers to talk directly to hardware peripherals like mice, keyboards, and displays
Process Management 				-->  Decides which program runs, when it runs, and how long it gets to use the processor
Security

Kernel is part of OS it is not a total OS (This i sin kernel space)
What the Kernel Does (The Core Operations) : The kernel stays hidden in the background and handles the raw, physical tasks : 
Talking directly to the physical hardware (CPU, RAM, hard drives) and Deciding which app can use the processor next and Making sure apps don't steal memory from each other.

What the Rest of the OS Does (The User Space Experience) 
Shell / Command Line Interface (CLI), Graphical User Interface (GUI) ,  Initialization & Service Managers , System Utilities/Libraries (API layer) and System Daemons & Standard Utilities.
The OS is the complete package that you interact with. The kernel is the engine under the hood doing the deep technical work. You need both for a computer to function!

Daemon --> A daemon is a background process in Linux that runs continuously without user interaction to handle system tasks like log collection (rsyslogd), job scheduling (crond), or network connections (sshd).

System Management & Core Operations
1. systemd manages the processes: It is the master system manager (PID 1) that starts, stops, and monitors all background daemons on your server.
2. crond / atd: The time-based job schedulers that execute automated background backup or cleanup scripts.

Networking & DNS Daemons
1. sshd manages secure remote login: It is a single worker daemon whose only job is to listen for incoming secure shell (SSH) connections so you can access the server remotely.
2. NetworkManager: Dynamically configures network interfaces, IP routing tables, and Wi-Fi connections.

Logging & Monitoring
rsyslogd / syslogd: The main system logger that streams text-based kernel and application logs into /var/log/.systemd-journald: Collects structured, binary execution data from systemd service units.

Storage & File Systems
dockerd / containerd: The orchestration runtimes that manage execution contexts, namespaces, and cgroups for containers.
nfsd / rpcbind: Handles Network File System exports, allowing external servers to mount local storage over the network.

To list all running daemons (services)
systemctl list-units --type=service --state=running

2. piping ( | ) : 
-------------------
Piping is used to pass the output of one command as input to another command using the pipe(|) operator
or
Basically one command output will became input of another command and kernel creates temporary data stream. So command 1 writes output to stdout(standart output) and pipe operator redirects that output as input stdin(standard input ) to command 2 and go on if anothe command is there 

*It enables efficient command chaining for filtering, processing, and automating tasks, and internally works through inter-process communication between stdout and stdin.

Ex: command1 | command2  --> ls | grep txt

Why Pipes Are Powerful

Instead of:
saving output to file
reading manually.Linux directly transfers data between commands.
Efficient and fast.

--
Internally (Important for Interview)
Pipe creates: 
inter-process communication (IPC)		--> is a set of kernel mechanisms that allows separate running processes to safely share data, synchronize activities, and pass messages to one another without crashing the system.
Kernel creates temporary data stream:       stdin : input, stdout: normal output, stderr: error output
stdout of command1 → stdin of command2      ==> stdout → stdin

About stderr 
By default, the pipe operator | only redirects stdout to stdin. It completely ignores stderr (Standard Error, File Descriptor 2)
If command1 throws an error message, that error will bypass the pipe symbol and print directly error to your terminal monitor, rather than being passed into command2.
To pipe both standard output and error messages together into your next command, we can use the |& operator
   Ex:	systemctl status nginx |& grep "failed"		# Pipes both normal output AND crash errors to grep

Depending on which command you are using, the -m option acts slightly differently

sudo usermod -d /new/home/path -m bob

When you run a command like kill -9 <pid>
your kill command doesn't touch the target program/process directly. Instead, it makes a system call to the OS kernel, saying: "Please deliver this signal to Process 1234." 
The kernel receives this request, finds the process in system memory, and forces it to react according to signal type.
The Linux Kernel is the entity that actually kills, pauses, or restarts the process.

Scenarios of handling :
------------------------------
Scenario 1 : Uncatchable Signals    -- kernel will perform actions based on SIGNAL TYPE before even reaching that signal to the process and process cannot ignore the signal 
SIGKILL and SIGSTOP    --> in this signal's kernel will do all the work and The process has no say in the matter.

When you send a SIGKILL (kill -9) or a SIGSTOP (kill -19), the Linux kernel intercepts the signal before it ever reaches the application.The kernel immediately stops or destroys the process from the outside. The process cannot block, ignore, or handle these signals. It doesn't even know they are coming

and SIGCONT --> SIGCONT: While the kernel always forces a stopped process to resume when it receives SIGCONT, an application is allowed to have a custom handler for SIGCONT if it wants to perform specific actions right after waking up—like resetting a timer or refreshing a screen. However, it cannot block the resumption itself

SIGKILL (Signal 9)		: The kernel immediately stops scheduling CPU time for the process, tears down its memory space, and destroys it. The process cannot block, catch, or ignore this.
SIGSTOP (Signal 19)	: The kernel instantly freezes the process in place. The process is paused and cannot execute any instructions until it receives a resume signal.

Scenario 2 :  Catchable Signals  -- the kernel acts as the messenger(send signal to the process), but the application's signal handler does the actual work
For other signals, the kernel(acts like a messenger) delivers a signal to the process. The process must stop what it is doing and execute a specific piece of code called a application Signal Handler.

SIGTERM (Signal 15 - Default kill): The kernel tells the process to terminate. The process's/applications signal handler catches this, allowing it to gracefully close open files, save database states, and clean up temporary files before shutting down.

SIGHUP (Signal 1 - Hangup/Restart): The kernel delivers the signal to the process. Many background daemons (like web servers) write their signal handlers to respond to this by reloading their configuration files and restarting internal services without fully shutting down.

Aplication signal handler -- An application signal handler is a custom function written inside a program's code that intercepts incoming operating system notifications (like SIGTERM), and it is used to give the application a chance to cleanly save data, reload settings, or shut down safely without breaking things

Process :  when i type --> sudo yum install nginx 
Step 1: Read the Repository File Locally
Before hitting the internet, yum reads the local text files in /etc/yum.repos.d/ to see which server it needs to talk to and If you are using the official NGINX repo, it opens a file like /etc/yum.repos.d/nginx.repo and reads a line that looks like this:baseurl=https://nginx.org/packages/centos/$releasever/$basearch/

/etc/yum.repos.d/ :  This directory contains text files ending in .repo (e.g., nginx.repo or centos.repo). Inside these files are URLs (baseurl) pointing to the official remote servers where the software is hosted.

Step 2: Resolve the Dynamic Variables
yum automatically swaps out the internal Linux variables ($releasever and $basearch) from that URL.
yum automatically reconstructs the URL into a hard internet address

Step 3: Connect to the Remote Server (The Download Source)
Your server connects out over the network to that specific web server (in this case, nginx.org or an OS mirror). It targets the RPMS/ folder on that server, which is essentially a massive online directory filled with thousands of software files.

Step 4: Download the Main Package & Dependencies
yum grabs the exact files it needs over HTTPS and downloads them. It copies down nginx-1.24.0-1.el7.ngx.x86_64.rpm (example version).
The Dependencies: It asks the remote server, "What does NGINX need to run?" The remote server replies that it needs tools like pcre and openssl. yum then pulls those .rpm files from the same server or your OS core repositories as well.

Step 5: Land in the Local Temporary Cache
The downloaded .rpm files land directly into your local storage cache at:📁 /var/cache/yum/x86_64/7/nginx/packages/

/var/cache/yum/ (or /var/cache/dnf/ on newer systems).  By default, yum automatically deletes these temporary .rpm files the moment the installation finishes to save disk space. If you want to keep them, you have to change keepcache=0 to keepcache=1 in your /etc/yum.conf file.

Step 6: Unpack, Install, and Clean Up
The system extracts the packages from the temporary cache directory and installs them to their permanent folders across the root filesystem (like /usr/sbin/nginx and /etc/nginx/). As the final step, yum deletes the temporary .rpm files from the cache directory to save your disk space.

The Executable Program  		: /usr/sbin/nginx (This is the actual binary that runs the server).
Configuration Files					: /etc/nginx/ (Where you edit nginx.conf to manage your websites).
Web Files									: /usr/share/nginx/html/ or /var/www/ (Where your default HTML web pages sit).
Logs											: /var/log/nginx/ (Where it tracks server traffic and errors).

3-Tier Architecture :
---------------------------
3-tier architecture is a design pattern that divides into diff tiers of an application like presentation layer, application layer, and database layers. 
This improves scalability, security, maintainability, and availability. 
In production environments, frontend servers handle user requests, backend services process business logic, and databases manage persistent storage.”

scalability 				--> Each tier can scale independently on its own dedicated infrastructure
										Example: add more web servers,scale APIs separately,scale DB vertically
Security					--> Direct access to the database is blocked, as clients must pass through the application layer only application layer has access to database layer
Maintainability 	--> Separate teams can develop, update, or replace individual layers without breaking other parts of the system like front end and backend teams can work seperately 

1. Presentation Layer (Frontend/Web Layer) ---> This is top-most layer or users interface where users interact with the application via a web browser or mobile app.
Examples: web UI,mobile app,React/Angular frontend,web server

Responsibilities ---> receives user requests ---> displays some default UI info/products data ---> sends requests to backend ---> handles basic validations
Examples : nginx webserver 

Real time example: 
User opens: amazon.com
Frontend displays: -> product pages -> login page -> cart UI etc..

2. Application Layer (Business Logic Layer) ---> The middle layer that handles business logic, data processing, calculations, and command execution.
Contains: business logic,APIs,authentication,processing

Responsibilities ---> processes requests ---> validates business rules ---> communicates with DB ---> Take data from DB ---> returns responses to Presentation layer 

Component	Example
Java App	Spring Boot

Real time example: 
When user clicks: Place Order
Application layer: -> validates stock -> calculates price -> processes payment -> updates database 

3. Database Layer : The back-end layer that stores, manages, and retrieves data using database management systems or cloud storage.

Responsibilities : data storage,retrieval,transactions,backups

Examples
Database	Example
Relational	MySQL, PostgreSQL
NoSQL	MongoDB

Real-Time Example : Stores: users,orders,payments,products info/data


Full Request Flow: 
Step 1 — User Request 				--> User access website example.com
Step 2 — Presentation Layer 	--> Nginx/web server receives request and open basic UI page and  send request to the backend
Step 3 — Application Layer 		--> Backend API processes logic a  communicate with db and retrives the data 
Step 4 — Database Layer 			--> Database stores/fetches data.
Step 5 — Response Back 			--> Response travels back to user.

Cloud Example in Amazon Web Services
Layer				AWS Service
Presentation		ALB + EC2
Application			EC2/EKS
Database			RDS




Here is how a simple action—checking your account balance—flows through the three tiers:
1. Presentation Tier (The User Interface)
What it is: The mobile banking app on your phone or the website open in your desktop browser (built using HTML, CSS, JavaScript, or React/Flutter).
What it does: It displays a clean dashboard with a button that says "View Balance".
The Action: You tap the button. The presentation tier captures this click and sends a secure HTTPS request (e.g., GET /account/balance) over the internet to the next layer.

2. Application Tier (The Logic Engine)
What it is: The backend servers running on cloud infrastructure (built using languages like Java, Python, or C#).
What it does: This layer contains the strict rules and logic of the bank.
The Action: The server receives your request and performs several checks:
		Authentication: Is this user actually logged in?
		Authorization: Does this user have permission to view this specific account?
		Processing: It formats a query to securely ask the database for the exact numbers.

3. Data Tier (The Storage)
What it is: A secure, relational database management system (like Oracle, PostgreSQL, or MySQL).
What it does: It acts as the ultimate source of truth, storing user profiles, transaction histories, and account balances.
The Action: The database receives the highly secure query from the application tier, locates your account row, pulls the figure (e.g., $1,250.00), and passes it back up to the application tier.


The Return Journey
Once the data tier provides the balance, the application tier formats it into a standard format (like JSON). 
Finally, the presentation tier receives that data and renders it beautifully on your screen so you can see your balance.

NAT(Network Address Translation) :
-----------------------------------------------  
NAT (Network Address Translation) is a networking technique that allows multiple devices on a private local network to share a single public IP address to access the internet.

How NAT Works (Step-by-Step)
The Request		: Your laptop (Private IP: 192.168.1.5) requests a webpage from Google.
The Translation	: The request hits your router and checks in modem cache if already omain is available or not. if not The router strips away your laptop's private IP, replaces it with your ISP-assigned Public IP (e.g., 203.0.113.1), assigns a unique port number to the request, and logs this connection in a NAT Translation Table.
The Response	: Google sends the webpage back to your router's Public IP and that specific port.
The Delivery		: The router looks at its translation table, matches the port number back to your laptop (192.168.1.5), and delivers the data.

The 3 Main Types of NAT :
1. PAT (Port Address Translation / NAT Overload):  It maps thousands of private internal IPs to one single public IP by assigning unique tracking ports to each connection.
2. Static NAT				: Maps one private IP to one permanent public IP on a 1:1 basis. This is used when an internal server (like a web server) needs to be consistently reachable from the outside world.
3. Dynamic NAT		: Maps private IPs to a pooled group of multiple public IP addresses on a first-come, first-served basis.

HTTP Status Codes :
---------------------------

| Range | Meaning       |
| ----- | ------------- |
| 1xx   | indicates Informational codes |
| 2xx   | indicates Success codes       |
| 3xx   | indicates Redirection codes  |
| 4xx   | indicates Client Errors codes|
| 5xx   | indicates Server Errors codes |

1xx — Informational codes -> Request received and continue, processing  --> Example:100	Continue
100 Continue  					-->  The server has received the request headers, and the client should proceed to send the request body
101 Switching Protocols --> The requester has asked the server to switch protocols and the server has agreed to do so.
102 Processing 				--> An interim response used to inform the client that the server has accepted the complete request but has not yet completed it
103 Early Hints 				--> Used to return some response headers before the final HTTP message.

2xx  —  indicates Success codes    
200 OK 					--> shows request succeessful along with response data  --> Example: webpage loaded and API returned success
201 Created 			--> new resource/data created --> POST APIs
202 Accepted		--> the request is accepted and request is in (queued for background processing)
204 No Content 	--> Request successful but:❌ no response body or (success with empty response) 
206 Partial Content

3xx — Redirection Codes
Means: resource moved/redirection required.
301 Moved Permanently 			 --> Used for: URL redirects --> HTTP → HTTPS redirect  or The requested resource has been assigned a new permanent URL.Any future requests should use this new URL. 
302 Found	(Moved Temporarily) --> Temporary URL redirect or  The resource is temporarily located at a different URL, but the client should continue using the original URL for future requests
304 Not Modified 			 				--> if the url is not modified same url load from Browser cache and Improves performance.
Tells the browser that the cached copy of the file it holds is still identical to the server's version. The server sends no body data, allowing the browser to load the page instantly from local storage(i.e., caching) to save bandwidth.

4xx — Client side Errors Codes --> Means: issue from client/request side
400 Bad Request 					--> Invalid request body syntax/data
401 Unauthorized 				--> Authentication required is missing.
403 Forbidden 						--> Authenticated but Access denied --> Example:permission issue and nginx restriction
404 Not Found	 					--> Requested resource/page doesn't exist
405 Method Not Allowed 	-->  Wrong HTTP method used. --> Example: if we give GET instead of POST request 
429 Too Many Requests (rate limited)


5xx — Server Side Error Codes  --> Means : the client's request is fine but Server Side failed errors issue
500 Internal Server Error --> Generic server failure means server encountered an unexpected condition which server doesnt know how to handle the issue basically in backend application code crash/unhandled exception
502 Bad Gateway --> Usually: reverse proxy issue and backend server down and common with Nginx and Load Balancers 
		The server was acting as a gateway or proxy (like web)and received an invalid response from the upstream server(catalogue) it tried to contact. 
		This usually happens when your web server (like Nginx) is running fine, but your backend application process (like java or Node application) has completely crashed or timed out.
503 Service Unavailable --> The server is currently unable to handle the request. --> Reasons server may be: down for scheduled maintenance and overloaded with traffic  
504 Gateway Timeout --> The server was acting as a gateway or proxy(like web) and timed out waiting for a response from the upstream server(This means your backend application took too long to process the request ).  --> (e.g., a massive database query running past the allowed limit)
505 HTTP Version Not Supported: The server does not support the HTTP protocol version that was used in the request.

500 is an unhandled backend code crash
502 means the proxy is up but the backend app is completely dead/unresponsive
503 means the server is temporarily overloaded or down for maintenance
504 means the backend app is running but took too long to finish a heavy task like a slow database query.

Synchronous communication : Application A sends a request to Application B and waits for B's response before continuing.
----------------------------------------
Ex : 
User --> Order Service request --> Payment Service --> process payment --> payment succeessful response --> Order Service continues to place/create order --> User gets response

The Order Service is waiting for the Payment Service confirmation and If Payment Service takes 5 seconds, Order Service waits roughly those 5 seconds for the response.

Common Techologies : REST API , HTTP etc..

Asynchronous communication :
------------------------------------------
Application A sends a message/event and does not need to wait for Application B to finish processing it immeadiately it can do later also like when they have time they will respond.
Asynchronous : The caller doesn't have to wait for the operation to complete.

Ex: Order Service -- Messaging broker(Like RabbitMQ , kafka ) --> payment service 

Order Service can continue after publishing the message or creating an event so the payment service will respond based on their availability. and the request from kafka will be delivered to payment service 
Common technologies : Kafka , RabbitMQ , Amazon SQS , Amazon SNS

In Synchronous caller has to wait and expects the immediate response and basically request --> response and it is like tight coupling 
In Asynchronous caller doesn't wait and they can do their remaining work meantime after sending message/event to the middle broker and response will be delayed and request --> message broker --> response and loose coupling

Hard link and Soft link :
-------------------------------
A hard link creates another file pointing/bound to the same inode and data blocks, so data remains accessible even if the original file is removed. 
A soft link or symbolic link is a shortcut pointing to another filename and has a different inode; it breaks if the original file is deleted.

File Descriptors : 
----------------------
A file descriptor is a number that Linux assigns to an open file or I/O resource so a process can access it.
Linux treats many things as files, including regular files, sockets, pipes, and devices.

Standard file descriptors : 
FD      Name		   Meaning
0			stdin			Input
1			stdout			Normal output
2			stderr			Error output

ls /tmp > output.txt 2> error.txt       -- send normal output to output.txt and error output to error.txt 

lsof -p 1234 			:	This shows the files and other resources opened by process 1234.
ls /proc/1234/fd   : This shows the file descriptors currently opened by that process.

tar(Tape Archive) :  It is used to Combine multiple files/directories into a single archive file.
------------------------
imp :  tar alone does not compress.

example : we have a directory called /app in that we have diff files
/app

file1.txt
file2.txt
logs/

Create tar archive   ---> tar -cvf app.tar /app   -->  it creates app.tar

-c = create
-v = verbose(show files)
-f = filename

Extract tar file --> tar -xvf app.tar     --> -x = extract
View tar content --> tar -tvf app.tar

tar with compression (.tar.gz)
ex: tar -czvf app.tar.gz /app
-c create
-z gzip compress
-v show process
-f filename

Extract tar.gz
tar -xzvf app.tar.gz

Real example:
-------------
Backup : tar -czvf backup.tar.gz /var/log
Restore: tar -xzvf backup.tar.gz

     zip -r app.zip /app       --> recursive means include inside files also

tar vs zip vs gzip

Very important interview question.

| Feature | tar | zip | gzip |
|-|-|-|
| Archive multiple files | Yes | Yes | No(single file) |
| Compression | No by default | Yes | Yes |
| Original removed | No | No | Yes |
| Extension | .tar | .zip | .gz |

gzip
Compress: gzip app.log
Creates: app.log.gz


Common DevOps Usage
--------------------
Application backup : tar -czvf app-backup.tar.gz /app
Compress logs      :gzip application.log
Package code	   :zip -r code.zip project/
View large logs    : more /var/log/messages
Count errors       : grep ERROR app.log | wc -l

------------------------

zip    → archive + compress files into .zip
